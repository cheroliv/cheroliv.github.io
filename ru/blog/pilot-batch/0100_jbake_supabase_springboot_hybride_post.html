Гибридная архитектура: лучшее из двух миров с Supabase и Spring Boot

Опубликовано 14 January 2026

время чтения : 12 minutes

Вместо того чтобы выбирать между простотой Supabase и мощью Spring Boot, почему бы не объединить их? Узнайте о гибридной архитектуре, которая использует лучшее от каждой технологии.

toc

[]

Ложная дилемма современной архитектуры

Когда мы создаём современное приложение со статическим фронтендом, мы часто сталкиваемся с бинарным выбором:

  • Ставь всё на решение Backend-as-a-Service(Supabase, Firebase) - простая, но ограниченная

  • Создать полностью готовый бэкенд(Spring Boot, Node.js) - мощный, но сложный

Это выбор — ложная дилемма. Гибридная архитектура предлагает третий путь: использовать каждую технологию там, где она преуспевает.

Архитектурное видение

Традиционная архитектура: монолитная

@startuml
skinparam backgroundColor #FEFEFE
skinparam componentStyle rectangle

package "Традиционная архитектура" {
  actor Utilisateur as user
  component "Фронтенд" as frontend #LightBlue
  component "монолитный бэкенд" as backend #LightCoral {
    [Authentification]
    [CRUD]
    [Logique Métier]
    [Jobs]
    [APIs Tierces]
  }
  database "База данных" as db #LightGray

  user --> frontend
  frontend --> backend : Toutes les requêtes
  backend --> db
}

note right of backend
  Tout passe par le backend
  même les opérations simples

  ⚠️ Point de congestion unique
  ⚠️ Complexité dès le départ
  ⚠️ Couplage fort
end note
@enduml

В этом подходе даже самые простые операции (чтение статьи, создание комментария) должны проходить через ваш бекенд. Вы платите за сложность уже с первого дня.

Архитектура BaaS: Все делегаты

@startuml
skinparam backgroundColor #FEFEFE
skinparam componentStyle rectangle

package "Архитектура BaaS Pure" {
  actor Utilisateur as user
  component "Фронтенд" as frontend #LightBlue
  cloud "Supabase / Firebase" as baas #LightGreen {
    [Auth]
    [Database]
    [Storage]
    [Edge Functions]
  }

  user --> frontend
  frontend --> baas : Toutes les opérations
}

note right of baas
  Développement rapide
  Pas de serveur à gérer

  ⚠️ Limité pour logique complexe
  ⚠️ Vendor lock-in
  ⚠️ Edge Functions contraintes
end note
@enduml

Напротив, делегировать всё в BaaS кажется привлекательным вначале, но быстро показывает свои ограничения, когда бизнес-логика усложняется.

Гибридная архитектура: разделение ответственности

@startuml
skinparam backgroundColor #FEFEFE
skinparam componentStyle rectangle

actor Utilisateur as user #LightBlue

package "Слой Frontend" {
  component "Статический сайт JBake" as frontend #SkyBlue
}

package "Простой слой (Supabase)" #LightGreen {
  component "Аутентификация" as auth
  component "CRUD Базовый" as crud
  component "Хранилище Файлы" as storage
  component "Реальное время" as realtime
}

package "Слой бизнес-логики (Spring Boot)" #Coral {
  component "Сложная логика" as logic
  component "оркестровка" as orchestration
  component "Запланированные задания" as jobs
  component "Интеграции" as integrations
}

database "PostgreSQL совместно используемый" as db #LightGray

user --> frontend

frontend --> auth : OAuth2, JWT
frontend --> crud : Articles, Profils
frontend --> storage : Images, Fichiers
frontend --> realtime : Notifications

frontend --> logic : Calculs, Rapports
frontend --> orchestration : Workflows
logic --> integrations : Stripe, APIs
orchestration --> db
jobs --> db

crud --> db
auth --> db

note bottom of db
  **Une seule source de vérité**
  Partagée entre Supabase et Spring Boot
end note

note right of auth
  **Gratuit jusqu'à 50k users**
  Configuration en quelques clics
  OAuth2 multi-providers
end note

note right of logic
  **Activé seulement si nécessaire**
  Kotlin + Coroutines
  Transactions complexes
end note
@enduml

Гибридная архитектура четко разделяет ответственность в зависимости от сложности и характера операций.

Оркестрирование потоков

Flux 1 : централизованная аутентификация

@startuml
skinparam backgroundColor #FEFEFE
autonumber

actor "Пользователь" as user
participant "JBake" as jbake
participant "Supabase Auth" as auth
participant "Spring Boot" as spring
database "PostgreSQL" as db

== Authentification ==
user -> jbake : Clique "Войти"
jbake -> auth : Redirect OAuth2 (Google/GitHub)
auth -> user : Consent screen
user -> auth : Autorise
auth -> auth : Génère JWT
auth -> jbake : Retourne JWT + Refresh Token
jbake -> jbake : Stocke tokens (sessionStorage)

== Accès aux Ressources ==
group Opération Simple (CRUD)
  user -> jbake : Crée un article
  jbake -> db : POST avec JWT
  note right: Supabase Row Level Security\nvérifie le JWT automatiquement
  db -> jbake : Article créé
end

group Opération Complexe (Métier)
  user -> jbake : Génère un rapport
  jbake -> spring : POST /api/reports\navec JWT
  spring -> spring : Valide JWT Supabase
  spring -> spring : Extrait claims (user_id, roles)
  spring -> db : Requêtes complexes
  spring -> jbake : Rapport généré
end

note over auth, spring
  **Le JWT est universel**
  Valide par Supabase ET Spring Boot
  Pas de double authentification
end note
@enduml

Ключевой пункт: Один процесс аутентификации, один JWT, пригодный для использования везде.

Поток 2: Оркестровка сложного бизнес-процесса

@startuml
skinparam backgroundColor #FEFEFE
autonumber

actor "Клиент" as user
participant "JBake" as jbake
participant "Spring Boot" as spring
participant "Supabase БД" as supadb
participant "Stripe API" as stripe
participant "Служба инвентаризации" as inventory
participant "Служба электронной почты" as email
database "PostgreSQL" as db

user -> jbake : Passe commande
jbake -> spring : POST /api/orders/create

== Orchestration Spring Boot ==
spring -> db : BEGIN TRANSACTION

par Vérifications Parallèles
  spring -> inventory : Vérifier stock
  inventory -> spring : Stock OK
else
  spring -> db : Vérifier profil client
  db -> spring : Client vérifié
end

spring -> stripe : Créer Payment Intent
stripe -> spring : Intent créé (ID: pi_xxx)

spring -> db : Créer Order (status: PENDING)
db -> spring : Order créé

spring -> stripe : Confirmer paiement
stripe -> spring : Paiement confirmé

spring -> db : Update Order (status: PAID)
spring -> inventory : Décrémenter stock
spring -> db : COMMIT TRANSACTION

par Notifications Asynchrones
  spring -> email : Email confirmation
else
  spring -> supadb : Insert notification
  note right: Notification temps réel\nvia Supabase Realtime
end

spring -> jbake : Order confirmé
jbake -> user : Affiche confirmation

note over spring
  **Responsabilités Spring Boot :**
  • Transaction ACID
  • Orchestration multi-services
  • Rollback automatique si erreur
  • Gestion des cas limites
end note
@enduml

Что приносит Spring Boot: Надёжная оркестровка сложных процессов, вовлекающих несколько систем, с транзакционной гарантией.

Flux 3: Запланированные задачи и синхронизации

@startuml
skinparam backgroundColor #FEFEFE

participant "Планировщик
(Spring Boot)" as scheduler
participant "Служба отчетов" as report
participant "PostgreSQL" as db
participant "внешний API" as api
participant "Сервис электронной почты" as email
participant "Хранилище Supabase" as storage

== Job Quotidien : 2h00 ==
activate scheduler
scheduler -> report : Déclenche génération rapport

activate report
report -> db : Récupère données\ndes dernières 24h
db -> report : Dataset

report -> report : Calculs & Agrégations
report -> report : Génération PDF

report -> storage : Upload PDF
storage -> report : URL publique

report -> email : Envoie aux admins\navec lien PDF
deactivate report

== Job Hebdomadaire : Dimanche 3h00 ==
scheduler -> report : Synchronisation externe

activate report
report -> api : Fetch données externes
api -> report : Nouvelles données

report -> db : Mise à jour tables
report -> db : Nettoyage données obsolètes
deactivate report

== Job Mensuel : 1er du mois ==
scheduler -> report : Facturation

activate report
report -> db : Liste clients actifs
report -> report : Calcul montants
report -> api : Génération factures (Stripe)
report -> email : Envoi factures
deactivate report

deactivate scheduler

note right of scheduler
  **Impossible avec Supabase seul**
  Edge Functions non adaptées
  pour jobs longs et récurrents
end note
@enduml

Что приносит Spring Boot: Надёжные запланированные задачи с управлением состоянием, автоматическим повтором и гарантированным выполнением.

    endif
  endif
endif

@enduml

Когда стоит выбрать эту архитектуру?

✅ Эта архитектура идеальна, если :

  • Вы хотите быстро начать (MVP за дни, а не за месяцы)

  • Вы ожидаете роста сложности бизнеса

  • Вы хотите минимизировать начальные расходы

  • Вы любите PostgreSQL и хотите единственный источник истины

  • Вы цените Kotlin и корутины для бизнес-кода

  • Вы хотите избежать полной привязки к поставщику

❌ Эта архитектура НЕ подходит если:

  • Ваш проект прост и останется простым (личный блог → 100% Supabase достаточно)

  • У вас уже есть сложившийся бэкенд-стек, которым вы владеете

  • Вы предпочитаете традиционный монолит

  • Вам нужен .NET, Python или другой язык для бекенда

❌ Не делать :

  • Реализовать аутентификацию самостоятельно

  • Использовать Spring Boot для простого CRUD

  • Игнорировать уровень безопасности строк Supabase

✅ Лучше сделать :

  • Разделять одну базу PostgreSQL

  • Использовать Spring Boot только для сложности

  • Начать просто, постепенно развиваться

Горизонтальное масштабирование

Когда ваше приложение растет, гибридная архитектура естественно масштабируется :

Supabase :

  • Автоматически масштабируется до миллионов операций

  • Реплики чтения для производительности чтения

  • Восстановление по точке во времени для обеспечения безопасности

Spring Boot :

  • Множество экземпляров за балансировщиком нагрузки

  • Безсостоятельный дизайн облегчает горизонтальное масштабирование

  • Kubernetes для оркестрации при необходимости

PostgreSQL:

  • Разбиение для больших таблиц

  • Пул соединений (PgBouncer)

  • Sharding, если это действительно необходимо (редко)

Архитектурные свидетельства

Стартап SaaS (50k пользователей)

_ Мы начали с 100% Supabase. При 5 тыс. пользователей мы добавили Spring Boot только для выставления счетов Stripe и ежемесячных отчетов. Через год 80% наших операций по‑прежнему проходят через Supabase. Spring Boot управляет только критически важной частью. Такое разделение позволило нам масштабироваться без переработки. _

Платформа E-learning (10 тыс. пользователей)

</think> Аутентификация OAuth2 Supabase сэкономила нам три недели разработки. Автоматически сгенерированные API управляют всем нашим каталогом курсов. Spring Boot используется только для PDF-сертификатов и писем о прогрессе. Простая, поддерживаемая, масштабируемая архитектура. __

Маркетплейс B2B (3k пользователей)

_ Spring Boot управляет транзакциями между покупателями и продавцами (критично). Supabase управляет всем остальным: профили, обмен сообщениями в реальном времени, документы. То, что они используют одну и ту же базу PostgreSQL, избавляет нас от сложной синхронизации. Лучший архитектурный выбор, который мы сделали. _
