Ложная дилемма современной архитектуры

При построении современного приложения со статическим фронтендом мы часто сталкиваемся с бинарным выбором:

  • Ставь всё на решение Backend-as-a-Service(Supabase, Firebase) - простая, но ограниченная

  • Создать полноценный бэкенд(Spring Boot, Node.js) - мощный но сложный

Этот выбор — ложная дилемма. Гибридная архитектура предлагает третий путь: использовать каждую технологию там, где она преуспевает.

Архитектурное видение

Традиционная архитектура: монолитная

В этом подходе даже самые простые операции (чтение статьи, создание комментария) должны проходить через ваш бекенд. Вы платите за сложность уже с первого дня.

Архитектура BaaS: Любой делегат

С другой стороны, делегировать всё BaaS кажется привлекательным в начале, но быстро проявляет свои ограничения, как только бизнес-логика усложняется.

Гибридная архитектура: разделение обязанностей

Гибридная архитектура четко разделяет ответственности в зависимости от сложности и характера операций.

Принципы проектирования

Принцип 1 : Начать просто, развиваться умно

Не стройте Spring Boot, если вам это не нужно.Начните с Supabase, добавьте Spring Boot, когда сложность оправдывает это.

Принцип 2: Разделение по характеру операции

Принцип 3 : Единственный источник истины

Используя один и тот же экземпляр PostgreSQL, Supabase и Spring Boot работают с одними и теми же данными без сложной синхронизации.

Оркестрование потоков

Поток 1: Централизованная аутентификация

Ключевой пункт: Один процесс аутентификации, один JWT, пригодный для использования везде.

Поток 2: Оркестрация сложного бизнес-процесса

Что Spring Boot приносит: Надёжная оркестровка сложных процессов, затрагивающих несколько систем, с гарантией транзакционной целостности.

Поток 3 : Запланированные задания и синхронизации

Что Spring Boot предоставляетНадёжные запланированные задачи с управлением состоянием, автоматической попыткой повторного выполнения и гарантированным выполнением.

Когда выбирать эту архитектуру?

✅ Эта архитектура идеальна, если :

  • Вы хотите начать быстро (MVP за дни, а не за месяцы)

  • Вы предвидите рост сложности бизнеса

  • Вы хотите минимизировать начальные затраты

  • Вам нравится PostgreSQL и вы хотите единый источник истины

  • Вы цените Kotlin и корутины для бизнес‑кода

  • Вы хотите избежать полной привязки к поставщику

❌ Эта архитектура НЕ подходит, если :

  • Ваш проект прост и останется таким (личный блог → 100% Supabase достаточно)

  • У вас уже есть настроенный бэкенд-стек, которым вы владеете

  • Вы предпочитаете традиционный монолит

  • Вам нужен .NET, Python или другой язык бекенда

Антипаттерны, которых следует избегать

❌ Не делать :

  • Дублировать данные между Supabase и Spring Boot

  • Создать две отдельные базы PostgreSQL

  • Реализовать аутентификацию самостоятельно

  • Использовать Spring Boot для простого CRUD

  • Сразу переусложнять архитектуру

  • Игнорировать Row Level Security Supabase

✅ Сделать лучше:

  • Поделиться одной базой PostgreSQL

  • Оставить Supabase управлять аутентификацией

  • Использовать Spring Boot только для сложности

  • Начать просто, развиваться постепенно

  • Использовать сильные стороны каждой технологии

  • Защитить с помощью RLS на уровне базы данных

Добавление новых возможностей

Горизонтальное Масштабирование

Когда ваше приложение растёт, гибридная архитектура масштабируется естественно :

Supabase :

  • Автоматически масштабируется до миллионов операций

  • Реплики чтения для производительности чтения

  • Восстановление на момент времени для безопасности

Spring Boot:

  • Множество экземпляров за балансировщиком нагрузки

  • Безсостояющий дизайн облегчает горизонтальное масштабирование

  • Kubernetes для оркестрации при необходимости

PostgreSQL:

  • Разбиение для больших таблиц

  • Пул соединений (PgBouncer)

  • Шардинг действительно необходим (редко)

Архитектурные свидетельства

Стартап SaaS (50 тыс. пользователей)

__ Мы начали на 100% с Supabase. При 5k пользователей мы добавили Spring Boot только для Stripe-биллингa и ежемесячных отчётов. Через год 80% наших операций по-прежнему проходят через Supabase. Spring Boot управляет только критической частью. Это разделение позволило нам масштабироваться без переработки. (Empty)

Платформа электронного обучения (10k пользователей)

B2B маркетплейс (3 тыс. пользователей)

_ Spring Boot управляет транзакциями между покупателями и продавцами (критично). Supabase управляет всем остальным: профили, обмен сообщениями в реальном времени, документы. То, что они используют общую базу PostgreSQL, избавляет нас от сложной синхронизации. Это лучший архитектурный выбор, который мы сделали. _

Синтез : Современная архитектурная парадигма

Гибридная архитектура Supabase + Spring Boot представляет новую парадигму:архитектурная специализация.

Правило 80/20

В большинстве приложений:

  • 80% операцийявляются стандартным CRUD → Supabase

  • 20% операцийтребуют бизнес-логики → Spring Boot

Это естественное правило оправдывает гибридную архитектуру.

Гибридная архитектура — это не технический компромисс, этостратегическое решение.

Ваш следующий шаг

Если эта архитектура вам знакома, вот с чего начать:

  1. Создайте аккаунт Supabase(бесплатный)

  2. Определите вашу минимальную схему данных

  3. Настройте аутентификацию OAuth2

  4. Создайте свою первую страницу JBake, которая использует API

  5. Разверните на GitHub Pages

Вы получите работоспособный MVP внесколько дней.

Spring Boot появится естественно, когда он вам понадобится. Не раньше.
