foundry/— функциональная зона, в которой находится код моего рабочего пространства — Содержит 18 проектов. Восемь являются open source под лицензией Apache 2.0. Только один закрытый исходный код — SaaS Edster. На протяжении нескольких месяцев эти девять проектов сосуществовали в той же папке, разделённые только…​ ничем. Их публичный/приватный статус Это была информация в моей голове, а не в файловой системе.

И потом я захотел подключить RAG. И тогда всё рухнуло.

Авария, которая ждала случиться

В апреле 2026 года я начал реализовывать RAG pgvector для slider-gradle. Принцип: индексировать все репозитории de`foundry/, производить какие-то embeddings, и внедрить их в контекст LLM, чтобы у него было восприятие" дела`foundry/.

Пайплайн был простым:

val repos = fileTree(rootDir) {
    include("**/*.adoc", "**/*.kts", "**/*.kt", "**/*.json", "**/*.yml")
}
val chunks = repos.map { chunk(it) }
val embeddings = chunks.map { embed(it) }
pgvector.insert(embeddings)

Простой. Эффективный. Иопасный.

Потому что это`fileTree`ne делает различий между`plantuml-gradle/` (Apache 2.0, public) и`edster/`(closed source, private). Он проглатывает всё. И если однажды я опубликую эти эмбеддинги — на дашборде, в ответе LLM, в наборе данных для обучения — утекает проприетарный код Edster.

Проблема не в том, что LLM читает закрытый исходный код. Проблема, чтобы этот код оказался в векторном эмбеддинге public — необратимый, неудаляемый, неаудируемый

Настоящий вопрос

Это не "как не допустить утечки кода LLM ?". Это "как Сделать побег структурно невозможным?

Ответ не является запросом. Ответ — это разрезать папку пополам.

Решение: OSS/ и CSS/

Перед :

foundry/
├── plantuml-gradle/       ← public
├── bakery-gradle/         ← public
├── magic-stick/           ← public
├── edster/                ← PRIVÉ
├── slider-gradle/         ← public
└── ...                    ← mélange invisible

После :

foundry/
├── OSS/                   ← tout est Apache 2.0
│   ├── plantuml-gradle/
│   ├── bakery-gradle/
│   ├── magic-stick/
│   ├── slider-gradle/
│   └── ...
└── CSS/                   ← tout est closed source / private
    └── edster/

Le `fileTree`становится:

val ossRepos = fileTree(File(rootDir, "OSS")) {
    include("**/*.adoc", "**/*.kts", "**/*.kt", "**/*.json", "**/*.yml")
}
val cssRepos = fileTree(File(rootDir, "CSS")) {
    include("**/*.adoc", "**/*.kts", "**/*.kt", "**/*.json", "**/*.yml")
}

// Embeddings publics — OSS seulement
pgvectorPublic.insert(ossRepos.map { chunk(it) }.map { embed(it) })

// Dataset fine-tuning privé — CSS seulement
fineTuningDataset.insert(cssRepos.map { chunk(it) })  // jamais publié

Публичный RAG никогда не видит`CSS/`. Код closed source питает набор данных без дообучения — внутренняя модель, которая никогда не покидает мой дом. La разделение механическое, не декларативное.

Почему "OSS" и "CSS" и не "Public" и "Private

Выбор аббревиатур OSS (Open Source Software) и CSS (Closed Source Software) Умышленно :

  • Public"/"Private" описываетвидимость(что видит GitHub)

  • OSS"/"CSS" описываетприродаду кода (что LLM должен знать)

Видимость GitHub является метаданными удалённого репозитория. Природа кода Свойство содержимого. LLM не имеет доступа к API GitHub — но у него есть доступ в файловой системе.CSS/ lui dit "attention, ce code n’est pas sous licence свободно" без необходимости читать одно`LICENSE`или парсить`package.json`.

Имя папки — самая надёжная метаданные, которую вы можете дать одна LLM. Она не может быть неправильно разобрана, проигнорирована или неправильно истолкована. LLM видит`CSS/edster/`в пути к файлу — он знает

Полное дерево — Четыре зоны, не три

Грануляция OSS/CSS дополняет трёхзонную онтологию. Зона `foundry/`переходит с 1 до 2 функциональных подзон:

@startuml
skinparam backgroundColor #FEFEFE
skinparam defaultTextAlignment center
skinparam wrapWidth 260

title Организация foundry/ — Грануляция OSS/CSS
package "литейное производство/" {

  package "Круг 0 — Корень" #FFCCCC {
    rectangle "PICTURE_ME_ROLLIN_*.adoc" as STIM
    rectangle "WORKSPACE_*.adoc" as VISION_DOC
    note right of STIM
      Brain dump libre
      Jamais versionné
      [LLM : interdit d'indexer]
    end note
  }

  package "Круг 1 — конфигурация/" #FFD9CC {
    rectangle "Секреты, токены" as SECRETS
    rectangle "Spring Cloud Config" as SCC
    note right of SECRETS
      Privé-CVS, solo access
      [LLM : INTERDIT]
    end note
  }

  package "Круг 2 — office/" #FFFFCC {
    rectangle "Статьи, кадрирование" as DATA
    rectangle "Формирования, SPG/SPD" as FORM
    note right of DATA
      Privé-CVS
      [LLM : filtré Vision/Opinion]
    end note
  }

  package "Круг 3 — литейный цех/" #CCE5FF {
    package "OSS/ — Apache 2.0" #CCFFCC {
      rectangle "Плагины Gradle" as PLUGINS
      rectangle "двигатель" as ENGINE
    }
    package "CSS/ — Закрытый исходный код" #CCDDFF {
      rectangle "edster/" as EDSTER
    }
  }
}

@enduml

| Зона | ООПД | Индексация RAG публичный | Набор данных дообучение | | Корень | Уровень 0 — Интимный | ✗ | ✗ | | configuration/| Уровень 1 — Ограниченный | ✗ | ✗ | |office/| Уровень 2 — Совместный | ✓ Отфильтрованный | ✓ Отфильтрованный | |

|foundry/private/| Уровень 3 — условно открытый | ✗ | ✓ Приватный | | foundry/public/| Уровень 4 — Нативная аудитория | ✓ Свободно | ✓ Публично |

Особый случай : cheroliv.com

Пока я был там, я исправил другую несоответствие. Мой сайт cheroliv.com`жил в`foundry/`как программный проект полноценный — со своей собственной сборкой Gradle, своим собственным CI, своей собственной управление.agents/`.

Но посты в блоге не являются кодом. Это данные редакционные Cercle 2 — наравне с кадрированием de`office/pilotage/` или формирования`office/formations/`.

AVANT                            APRÈS
foundry/                office/
  cheroliv.com/                    sites/
    site/jbake/content/blog/         cheroliv.com/
      2026/0117_....adoc               2026/0117_....adoc

Что меняется :

  • Статьи находятся в`office/`→ конфиденциальность Круга 2

  • Задача`publishSite`становится одна capability of`engine`

через`bakery-gradle`— плагин получает`FileTree`, он не знает что статьи приходят из`office/`

  • Одна CI, одна система управления — нулевое дублирование

  • Классификатор Vision/Opinion (Правило 2bis) применяется автоматически :

статьи в`office/` sont filtrés avant publication

bakery-gradle ему всё равно

И это прекрасно. Плагин`bakery-gradle`не был изменён. Он получает каталог содержимого AsciiDoc, генерирует HTML и пушит на GitHub Pages. Как называется этот каталог`site/jbake/content/` ou office/sites/cheroliv/— плагин пофигу.

// engine/build.gradle.kts
task("publishBlog") {
    doLast {
        val articles = fileTree("../../office/sites/cheroliv/2026/")
        bakery.generate(articles)  // ← bakery ne sait pas d'où ça vient
    }
}

Контракт интерфейса — это задача Gradle. Не API REST. Не вебхук. Задача — типизированная, тестируемая, исполняемая локально и в CI.

Влияние на агент управления

Гранулирование OSS/CSS изменяет управление агентом в трёх пунктах:

  1. RAG public : периметр индексации переходит от`foundry/**`

à foundry/public/`Please provide the French text you would like translated to Russian.`office/Vision/. Закрытый исходный код Исключается из индекса по настройке задачи, а не по запросу.

  1. Knowledge Graph : graphify-gradle производит два графа :

*office/graph.json(public) — отношения между артефактами OSS + office/Vision *configuration/graph_private.json(gitignored, приватный) — отношения между артефакты CSS, никогда не опубликованы

  1. Dataset fine-tuning :`codebase-gradle`теперь имеет два источника:

*OSS/→ публичные наборы данных (модели сообщества, бенчмарки) * CSS/→ частные наборы данных (внутренняя модель, собственная донастройка)

Единственная стоимость : один`git mv`глобальный на 17 репозиториях OSS + рефакторинг де build.gradle.kts de engine. Это холодная миграция — нет данных в полёте, нет пострадавших пользователей

Вывод: Физический сигнал бьёт логический сигнал.

Что я сделал этим после полудня — заменить невидимую конвенцию через видимое разделение в зоне`foundry/. Раньше, вы должны были знать что`edster/`был закрытым исходным кодом. Теперь вы это видите — папка называется`CSS/.

Это тот же принцип, что и разрешения Unix, сетевые VLAN или противопожарные отсеки в базе данных. Безопасность не должна Это информация, которую вы должны запомнить. Она должна быть свойством. физикасистемы.

Гранулярность OSS/CSS — это применение этого принципа в данной области управления LLM. LLM не нужно знать, что Edster является конфиденциально. Ему нужно быть неспособным проиндексировать это.

И это именно то, что`CSS/`гарантирует.
