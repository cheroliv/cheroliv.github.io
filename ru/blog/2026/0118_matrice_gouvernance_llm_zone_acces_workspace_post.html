В течение месяцев я накопил правила управления агентом. Файлы EAGER, контрольные списки LAZY, шестиэтапные протоколы завершения сеанса. И всё же один вопрос оставался открытым: как LLM знает, что оно У него есть право делать с файлом ?

Ответ не в подсказке. Он находится в файловой системе.

Вот спецификация архитектуры, которая делает ответ пригодным для использования — la матрица управления LLM.

Проблема: Инженерия промптов — это песочный замок.

Когда вы даёте файл LLM, вы даёте ему всё. Содержание, да — но и отсутствие средств защиты. LLM не знает, содержит ли этот файл Секрет, гипотетическое мнение или закрытый исходный код. Он проиндексирует его. резюмировать, цитировать, смешивать с другими данными — и потенциально опубликовать его в публичном embedding или ответе пользователя

Классический парад, это подсказка:

"Tu es un assistant sécurisé. Ne divulgue jamais d'informations confidentielles.
Si tu détectes un secret, ignore-le. Si tu détectes une opinion, ne la répète pas."

Этот промпт имеет три проблемы:

  1. Он полагается на добрую волю LLM. Достаточно большая модель для

Решение сложных багов достаточно велико, чтобы обойти инструкцию. безопасности, утопленной в 200k токенах контекста.

  1. Он контекстуальный, а не структурный. Смените запрос, смените LLM,

переключитесь на другую сессию — и правило исчезает.

  1. Он не масштабируется. Каждый новый тип файла, каждый новый уровень

конфиденциальность требует нового пункта. Ваш запрос становится регламентированный текст, который никто не читает полностью.

Безопасность системы никогда не должна зависеть от инструкции, которую может забыть, обойти или не загрузить. Она должна зависеть от барьер, который невозможно преодолеть без явного намерения

Мой ответ: Матрица 4×4

Пять зон (Пространственная размерность — RGPD)

Каждая область рабочего пространства имеет уровень GDPR, который определяет где файл может быть маршрутизированным :

Зона

Уровень ОЗПД

Содержание

Право доступа RAG публичный

Корень

0 — интимный

Дампы мозга, беседы LLM

Запрещено— никогда не индексировался

configuration/

1 — Ограниченный владелец

Секреты, токены, ключи API

ЗАПРЕЩЕНО— никогда не индексировался

office/

Редакционные данные, кадрирование, обучение

отфильтрованный— Только видение

foundry/private/

3 — Условно открыто

запрещено— частный набор данных исключительно

foundry/public/

свободный— полная индексация

Правило простое : путь к файлу определяет, что LLM может с ним делать. Нет метаданных, которые нужно поддерживать, нет тега, который нужно добавить во frontmatter, нет ручной классификации при каждом коммите. Файл находится в`OSS/? Он общедоступен. Он в`configuration/? Он недоступен.

Эпистемологическая классификация (второе измерение)

Пространственная размерность говорит куда маршрутизировать. Но есть вторая ось, перпендикулярная: quoi маршрутизатор. Некоторые файлы в авторизованной зоне содержат информацию которые не должны быть разбавлены как есть:

Как LLM потребляет эту матрицу

Матрица не является документом, который читает LLM. Это ограничение неявно** закодирована в составном векторе контекста (EPIC 9 — в процессе) реализации).

Вот что получает LLM в каждой сессии :

VECTEUR COMPOSITE DE CONTEXTE
├── RAG pgvector → OSS/ + office/Vision
│   (similarité sémantique sur contenu publiable)
├── Knowledge Graph graphify → OSS/
│   (relations exactes entre artéfacts publics)
├── Knowledge Graph privé → CSS/
│   (relations entre code closed source — jamais exporté)
├── Métadonnées de zone → chaque fichier taggé par zone physique
│   (le LLM sait s'il est dans office/ ou OSS/)
└── Historique des décisions → WORKSPACE_VISION.adoc
    (contexte temporel des arbitrages)

Конкретно, когда LLM мне говорит :

Je vais indexer le contenu de edster/ pour enrichir le knowledge graph...

Метаданные зоны отвечают, даже прежде чем LLM закончит свою фразу: edster/`находится в`CSS/, уровень 3 →Доступ к публичному knowledge graph запрещён. RAG не видит его. Граф его не касается. Ответ пользователя ne Он не цитирует его.

Пространственная онтология функционирует какразрешение Unixдля LLM. Вы не просите, чтобы процесс был осторожен с`/etc/shadow`— Вы ему отказываете в доступе для чтения. Тот же принцип.

Реализация: Типизированные задачи Gradle

Матрица — это не философия. Это код. Вот контракт задачи. Gradle, который это реализует:

abstract class ZoneAwareIndexer @Inject constructor(
    private val rootDir: DirectoryProperty,
    private val configServer: ConfigServerProperty  // → configuration/
) : DefaultTask() {

    @Input
    val zoneFilter: SetProperty<Zone> = project.objects.setProperty(Zone::class.java)

    @OutputFile
    val ragIndex: RegularFileProperty = project.objects.fileProperty()

    @TaskAction
    fun index() {
        val allowedPaths = zoneFilter.get().flatMap { it.resolve(rootDir.get()) }
        val forbiddenPaths = Zone.RESTRICTED.resolve(rootDir.get())
                            + Zone.INTIMATE.resolve(rootDir.get())
        // Le RAG ne voit jamais configuration/ ni la racine
        // CSS/ alimente un index privé, pas celui-ci
        // office/ est filtré par le classifieur Vision/Opinion
    }
}

enum class Zone {
    INTIMATE,      // Cercle 0 — racine
    RESTRICTED,    // Cercle 1 — configuration/
    EDITORIAL,     // Cercle 2 — office/
    CLOSED_SOURCE, // Cercle 3 — foundry/private/
    OPEN_SOURCE    // Cercle 3 — foundry/public/
}

Задача тестируемая. Вы можете написать тест, который проверяет:

@Test
fun `le RAG n'indexe jamais configuration`() {
    val index = ZoneAwareIndexer(rootDir, configServer)
    index.zoneFilter.set(setOf(Zone.OPEN_SOURCE, Zone.EDITORIAL))
    index.index()

    assertThat(index.ragIndex).doesNotContain("configuration/")
}

@Test
fun `le code closed source est exclu du RAG public`() {
    val index = ZoneAwareIndexer(rootDir, configServer)
    index.zoneFilter.set(setOf(Zone.OPEN_SOURCE))  // OSS only

    assertThat(index.ragIndex).doesNotContain("edster")
}

380 tests, 380 PASS. Как и для plantuml-gradle — безопасность тестируется, не ожидаемая.

Почему это манифест, а не просто спецификация

Этот документ является архитектурной спецификацией, поскольку он определяет:

  • Некоторыеразмеры(пространственная, эпистемологическая)

  • некоторыедетерминированные правила(zone → право доступа)

  • Un контракт на задачу(Типизированный Gradle, тестируемый)

  • Однаэталонная реализация(моя рабочая область)

Но это такжеявныйпотому что он занимает позицию в дебатах больше : как управлять доступом LLM к данным?

Ответ отрасли — это инжиниринг промптов + системы ограничений
пост-хок классификаторы. Мой ответ: расположите свои файлы в правильные папки. Остальное автоматически.

Этот манифест не говорит "LLM должны быть выровнены". Он говорит: "выравнивание Один LLM на ваши правила безопасности является следствием вашей системы файлы, не ваш запрос.

Полный каскад — от Brain Dump до блоговой статьи

Чтобы проиллюстрировать полный цикл, вот как эта идея матрицы возникла и была разбавлена :

Session 4 mai 2026 — Feedback global du workspace
  │
  ├→ Le LLM identifie : "la dualité public/privé est invisible"
  │   → Classifié VISION (constat architectural vérifiable)
  │
  ├→ PICTURE_ME_ROLLIN_MATRICE_4X4.adoc — STIMULUS (Cercle 0)
  │   → Brain dump structuré, classification VISION confirmée
  │
  ├→ DILUTION → WORKSPACE_AS_PRODUCT.adoc (section Matrice 4×4)
  │   → La spec vit dans les documents racine
  │
  ├→ DILUTION → WORKSPACE_ORGANIZATION.adoc (OSS/CSS)
  │   → La granularisation est documentée
  │
  └→ ARTICLE 0117 (ce document) → cheroliv.com
      → La VISION est publiée

Декларативный — промпт просит LLM быть осторожным

Testable — контракт задачи Gradle проверяется 380+ тестами

Не тестируемый — "Соблюдал ли LLM правило?" — это открытый вопрос.

Не масштабируемый — новый тип данных = новое условие промпта, новый риск регрессии

Вывод: Организуйте свои файлы, а не свои подсказки

Матрица управления LLM, которую я только что описал, не является продуктом. Это однаспецификация архитектуры— и это потому, что она пригодный для публикации.

Что делает её надёжной, так это то, что она ничего не требует от LLM. Она не ему Она не доверяет. Она не полагается на своё выравнивание, своё понимание. из французского, или её доброй воли. Она основана на файловой системе — самый нижний, самый стабильный, самый протестированный слой всего стека.

Когда я говорю своему LLM"ты можешь проиндексировать всё в`OSS/, ничего в `configuration/, et `office/`seulement если это классифицировано как Vision— Это фильтр — реализованный на Kotlin, проверено 380 тестами, выполнено до того, как LLM увидел данные.

Это разница между тем, чтобы сказать кому-то "не смотри в этот ящик и закрыть ящик с ключом. Управление агентом, которое я строю с месяцев — это ключ. Матрица — это план мебели.
