Диагностика: Три типа отношений, которые не видит ни один шаблон

Мой корпус статей — 23 поста за 4 месяца — имеет богатую структуру что хронологический шаблон полностью перезаписывает:

Решение: Gradle-пайплайн, не горячий вызов LLM

Первое соблазнение было бы вызвать LLM в момент bake: « Для эта статья, найди три наиболее похожих статьи в корпусе. Не делайте этого.

Один вызов LLM к каждому`./gradlew bake`стоит времени, денег, и вводит недетерминированность в вашу сборку. Ответ LLM может переключаться между двумя сборками без изменения содержимого. Ваша CI становится не воспроизводимые, ваши тесты становятся нестабильными.

Решение детерминировано: Gradle‑pipeline, который предварительно вычисляет граф о сходстве и сохраняет его в`graph.json`. Шаблон читает результат — Никогда он не запускает расчёт.

Архитектура: Bakery импортирует Graphify, не Engine

Это самый важный архитектурный пункт. Соблазн был бы подключать сотрудничество в`engine/build.gradle.kts`двигатель бра graphify для scan, bakery dla bake, и engine делает мост между оба.

Это антипаттерн. Engine является терминальным потребителем — он применяет о плагинах он не реализует бизнес-логику. Правило: Бремя доказывания лежит на проприетарном плагине.

Конвейер: Сканирование → Граф → Шаблон

Вот полный pipeline из трех этапов :

  1. Scan (graphify) :`graphify-plugin`сканирует рабочее пространство. В его

В текущей форме, он уже обнаруживает их`xref:`между`.adoc`и показывает в`graph.json`как ребра типа`reference`.
Его обогащают для редакционного контента: * Анализировать метаданные JBake (:jbake-tags:, :jbake-description:) каждого`.adoc`блога * Вычисляет совпадения тегов → рёбра`tag_cooccurrence`с весом * Извлекает именованные сущности из описаний с помощью TF-IDF → edges`entity_overlap` Внедрить раздел`blog_articles`в`graph.json`существующий

// Extrait de l'enrichissement graphify pour le blog
fun enrichBlogSection(graphJson: File, blogDir: File): GraphJson {
    val articles = blogDir.listFiles { f -> f.extension == "adoc" }
        .map { parseJbakeMetadata(it) }

    val nodes = articles.map { ArticleNode(it.slug, it.title, it.tags) }
    val edges = mutableListOf<GraphEdge>()

    // Couche 1 : xref (déjà fait par scanWorkspace)

    // Couche 2 : co-occurrences de tags
    for (a in articles) {
        for (b in articles) {
            if (a.slug == b.slug) continue
            val common = a.tags.intersect(b.tags)
            if (common.isNotEmpty()) {
                edges.add(GraphEdge(
                    source = a.slug,
                    target = b.slug,
                    type = "tag_cooccurrence",
                    weight = common.size.toDouble() / (a.tags.size + b.tags.size)
                ))
            }
        }
    }

    return graphJson.copy(
        blogArticles = BlogSection(nodes, edges)
    )
}

  1. Bake (bakery) : в момент`./gradlew bake`, `BakeryPlugin`кровать

`graph.json`и решает связанные статьи для каждого поста.

// BakeryPlugin — résolution des articles connexes
fun resolveRelatedPosts(
    currentSlug: String,
    graph: GraphJson,
    maxResults: Int = 4
): List<RelatedPost> {
    val edges = graph.blogArticles.edges
        .filter { it.source == currentSlug || it.target == currentSlug }

    return edges
        .sortedByDescending { it.weight }
        .take(maxResults)
        .map { edge ->
            val relatedSlug = if (edge.source == currentSlug) edge.target else edge.source
            graph.blogArticles.nodes.first { it.slug == relatedSlug }
        }
}

хронологический fallback

Si `graph.json`отсутствует (build local без предварительного сканирования, первый) развертывание, CI которая ещё не интегрировала скан graphify), шаблон должен плавно деградировать :

fun resolveRelatedPosts(currentSlug: String, graph: GraphJson?): List<RelatedPost> {
    if (graph != null && graph.blogArticles != null) {
        return resolveFromGraph(currentSlug, graph)
    }
    // Fallback chronologique — même comportement qu'aujourd'hui
    logger.warn("[bakery] graph.json absent — fallback chronologique")
    return resolveFromChronology(currentSlug)
}

Поведение по умолчанию совпадает с текущим поведением. Le движок рекомендаций является постепенным улучшением — не разрушительное изменение.

Эмерджентная онтология: когда статьи объединяются, не зная друг друга

Самый интересный слой — третий: возникающая онтология. Статьи, которые не цитируются, у которых нет одинаковых тегов, но которые говорят об одном и том же не знают об этом.

Возьмём конкретный пример. Три статьи из моего корпуса :

  1. 0119 — Benchmark DGX Spark vs Cloud подписка LLM

  2. 0121 — Плагин Gradle управляет двумя экземплярами Ollama Pro

  3. 0122 — Коэффициент эффективности 27x 45x Флот экспертов ИИ

Эти три статьи не имеют никаких перекрёстных ссылок между ними. Их теги не Соответствуют только 20% (« ollama », « llm » общие). Но лёгкий NLP в описаниях выявляет очевидный кластер : « стоимость », « подписка», облако », « GPU », « ключ API », « Ollama Pro », « эффективность », « отношение

Они образуют онтологический кластер: экономика самодостаточного LLM против cloud Этот кластер нигде не объявлен. Он возникает из корпуса.

NLP является намеренно лёгким — TF-IDF + косинусное сходство по описания. Не нужно BERT, не нужно языковой модели. Корпус содержит 23 статьи, матрица схожести помещается в файл JSON размером 50 КБ.

Сила NLP не исходит из сложности алгоритма, но от размера корпуса и качества описаний. Одна `:jbake-description:`хорошо написанная из 150 символов содержит больше сигнал для TF-IDF, что статья полностью состоит из 3000 слов

Договор DAG: кто кому важен

Перспективы: Блог как публичный граф знаний

Эта функция открывает более широкие перспективы: а если`cheroliv.com` Он становился самим knowledge graph navigable ?

Статьи являются узлами. Теги являются сообществами. xref являются Рёбра. Читатель больше не читает изолированную статью — он перемещается в граф знаний где текущая статья является точкой входа.

Представьте домашнюю страницу, которая отображает не хронологический список последних постов, но карта корпуса : онтологические кластеры, ключевые статьи (те, у которых наибольшее количество рёбер), пути чтения рекомендуемые (« Если вам понравилась статья о Graphify, читайте далее тот о Knowledge Graph как инструмент для понимания »)

Это уже не блог. Это семантический атлас.

И это не научная фантастика. Le`graph.json`уже существует. Ему не хватает только интерфейса навигации.

Вывод: Система файлов знает то, что игнорирует шаблон

Что я разработал в этот вторник вечером, это замена эвристики ленивая (хронологический порядок) верным представлением структура моего корпуса (Knowledge Graph)

Шаблон`post.thyme`не меняется. То, что меняется, это что мы Он его кормит. До: список Java, упорядоченный по`date`. После : взвешенный граф, полученный из трёх слоёв анализа — xrefs, co-occurrences тегов и возникающей онтологии с использованием NLP

Петля замкнута. graphify сканирует workspace. Bakery читает граф и заполняет шаблон. Читатель видит рекомендации релевантные. И двигатель — дирижёр — даже не знает что всё это существует.
