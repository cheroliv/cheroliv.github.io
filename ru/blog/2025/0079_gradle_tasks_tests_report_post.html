Оптимизация управления задачами Gradle с Kotlin DSL и buildSrc

Опубликовано 11 July 2025

Автоматизация задач сборки является критически важной для любого программного проекта, а Gradle, с его DSL Kotlin, предоставляет исключительную гибкость. В ходе нашего разговора мы изучили, как централизовать и переиспользовать логику сборки, в частности для отчетов о тестах, используявсепроекты, buildSrc, и пользовательские задачи на Kotlin.

Централизовать Конфигурации с allprojects и `subprojects

Блоки`allprojects` et `subprojects`в вашем`build.gradle.kts`Корень является фундаментальным для применения общих конфигураций в вашем мультимодульном проекте.

*allprojects { …​ }`Примените конфигурацию ккорневой проект и всем его подпроектам. Идеальный для определения`group, одна`version`, или некоторых`repositories`общие. *subprojects { …​ }: Примени конфигурациютолько к подпроектам, исключая корневой проект. Идеально подходит для применения плагинов, специфичных для модулей (как`java` ou kotlin-jvm) или общие зависимости для ваших библиотек.

Вот иллюстративный пример :

// build.gradle.kts (projet racine)
plugins {
    base // Appliqué au projet racine
}

allprojects {
    group = "com.example"
    version = "1.0.0"

    repositories {
        mavenCentral()
    }

    tasks.withType<org.gradle.api.tasks.testing.Test> {
        useJUnitPlatform() // Configuration commune des tests pour tous les projets
    }
}

subprojects {
    apply(plugin = "java")
    apply(plugin = "org.jetbrains.kotlin.jvm")

    dependencies {
        implementation("org.jetbrains.kotlin:kotlin-stdlib-jdk8")
    }

}

\==`buildSrc`Швейцарский нож логики сборки

Когда логика ваших задач становится сложной или должна быть переиспользована,buildSrcявляется предпочтительным решением. Это специальный модуль Gradle, который компилируется перед основными скриптами сборки, делая его классы доступными в classpath всей вашей сборки.

Почему использовать`buildSrc`для задач?

  • Повторное использование: Задача, определённая в`buildSrc`может быть применена к любому проекту сборки.

  • ОрганизацияЦентрализует код сборки, делая его более чистым и поддерживаемым.

  • безопасность типов и автодополнение: Код Kotlin в`buildSrc`Он компилируется, обеспечивая проверку ошибок и автодополнение вашего IDE, улучшая опыт разработки.

Создание абстрактных задач отчёта

Для управления отчётами о тестах мы разработали модульный подход, используя абстрактный класс задачи в`buildSrc`. Согласно вашим потребностям, этот класс может наследовать`DefaultTask` ou de Exec.

\=== Абстрактная задача`OpenTestReportTask`(наследующий от`DefaultTask`)

Такой подход рекомендуется, если вам нужна пользовательская логика Kotlin, которая взаимодействует с файловой системой или другими API Gradle, а затем запускает внешнюю команду.

[source,kotlin]

package com.yourpackage

import org.gradle.api.DefaultTask import org.gradle.api.tasks.Input import org.gradle.api.tasks.TaskAction import java.io.File

абстрактный класс OpenTestReportTask : DefaultTask() {

----
----
init {
    group = "verification"
    description = "Opens a test report in Firefox."
    dependsOn("check") // Assure que les rapports sont générés
}

@get:Input
abstract var reportPath: String

@TaskAction
fun openReport() {
    val separator = File.separator
    val reportFile = project.layout.projectDirectory.asFile.toPath()
        .resolve(reportPath.replace("/", separator))
        .toAbsolutePath()
        .toFile()

    if (!reportFile.exists()) {
        logger.warn("Report file does not exist: $reportFile. Ensure 'check' ran.")
        return
    }

    project.exec {
        commandLine("firefox", "--new-tab", reportFile.absolutePath)
    }
    logger.lifecycle("Opened test report: ${reportFile.absolutePath}")
}
----

## }

Абстрактная задача`AbstractJbakeExecTask`(наследующий от`Exec`)

Если ваша задача сводится в основном к выполнению внешней команды с переменными аргументами, наследовать напрямую от**Exec**более прямой.

## [source,kotlin]

пакет com.yourpackage

import org.gradle.api.tasks.Exec import org.gradle.api.tasks.Input import java.io.File

abstract class AbstractJbakeExecTask : Exec() {

----

init { group = "verification" description = "Opens a Jbake project report in Firefox." dependsOn("check") }

@get:Input abstract var reportRelativePath: String

override fun exec() { val separator = File.separator val reportFile = project.layout.projectDirectory.asFile.toPath() .resolve(reportRelativePath.replace("/", separator)) .toAbsolutePath() .toFile()

if (!reportFile.exists()) { logger.warn("Report file does not exist: $reportFile. Ensure 'check' ran.") return }

commandLine("firefox", "--new-tab", reportFile.absolutePath) logger.lifecycle("Attempting to open report: ${reportFile.absolutePath}") super.exec() // Appelle la méthode exec() de la super-classe Exec }

\== Видимость задач`buildSrc`

Задачи и классы, которые вы определяете в**buildSrc**являются:

***Видимы и пригодны**для всех проектов вашей основной сборки (корень и подпроекты). Поэтому вы можете использовать`com.yourpackage.ReportUnitTestsTask`в`allprojects { ... }`. ***Неисполняемые**непосредственно в качестве задач buildSrc(например,`gradle :buildSrc:reportTests`не будет работать, если задача не будет записана специально в`buildSrc/build.gradle.kts`).`buildSrc`Это модуль компиляции, а не модуль исполняемого приложения для этих задач основной сборки.

\=== Запустить отчёт для тестов`buildSrc`сам

Si `buildSrc`у него есть свои тесты и он генерирует отчёты, вы можете записать задачу отчёта прямо в`buildSrc/build.gradle.kts` :

## [source,kotlin]

plugins { `kotlin-jvm` }

репозитории { mavenCentral() }

tasks.withType\<Test\> { useJUnitPlatform() reports.html.outputLocation.set(layout.buildDirectory.dir("reports/tests")) }

import com.yourpackage.ReportJbakeTestsTask // Импортируйте ваш класс задачи

tasks.register<ReportJbakeTestsTask>("reportBuildSrcTests") { // Путь уже определён в классе, он будет указывать на отчёты buildSrc }

Вы сможете затем выполнить :`./gradlew :buildSrc:test`за которым следует`./gradlew :buildSrc:reportBuildSrcTests`.

Применяя эти практики, вы создадите системы сборки Gradle на Kotlin DSL, которые не только мощны, но и невероятно модульны, поддерживаемы и легко понятны.
