Okuma süresi : 12 minutes

Kod tabanınız büyüyor. Modüller arasındaki bağımlılıklar artıyor. Mimari dokümantasyon, hâlâ yazılmadan önce eski hale geliyor. Gradle build’iniz automatiquement kodun gerçek yapısından güncel diyagramlar üretebilseydi? Bu, Graphify + PlantUML Gradle Plugin pipeline’inin tam olarak yaptığı şey:`graphify . --no-viz`Knowledge Graph’ı çıkarır,`./gradlew generateKnowledgeGraphDiagram`onu PlantUML diyagramlarına dönüştürür. Sıfır LLM, sıfır kılavuz, %100 deterministik.

Sorun: diyagramlar her zaman kodun gerisinde

Binlerce satırı aşan her proje bu sendromu yaşar:

  1. Proje başında bir mimari diyagramı çizeriz.

  2. Kod evrim geçiriyor, bağımlılıklar değişiyor

  3. Şema süslenmiş bir yalana dönüşür.

  4. Kimse onu güncellemez çünkü zor

  5. Yeni gelenler ona dayanır ve hatalar yapar

Adım 1: Graphify’i kurun ve Knowledge Graph’i çıkarın

Kurulum

Graphify, kod tabanınızı analiz edip yapılandırılmış bir bilgi grafiği oluşturan bir Python aracıdır:

# Méthode recommandée
uv tool install graphifyy && graphify install --platform opencode

# Alternative avec pip
pip install graphifyy && graphify install --platform opencode

İstisnaları yapılandır

Bir dosya oluştur`.graphifyignore`proje kök dizininde, iş mantığına ait olmayan dosyaları hariç tutmak için :

# Secrets — JAMAIS dans le graphe
*-context.yml
*.env

# Fichiers générés
build/
.gradle/

# Tests fonctionnels
src/functionalTest/

Knowledge Graph’yi çıkar

graphify . --no-viz

bayrak`--no-viz`HTML oluşturulmasını atlar (Gradle pipeline’inde gereksiz). Sonuç bir dosyadır.`graphify-out/graph.json`içeren :

  • düğümler: sınıflar, fonksiyonlar, dosyalar — türleri ve toplulukları ile

  • kenarlar: düğümler arasındaki ilişkiler (EXTRACTED koddan, INFERRED LLM tarafından)

  • topluluklar: bağlı düğümlerin otomatik grupları

Örnek yapı`graph.json`
{
  "nodes": [
    {"id": "0", "label": "LlmService", "file_type": "code", "community": 0},
    {"id": "1", "label": "ApiKeyPool", "file_type": "code", "community": 0},
    {"id": "2", "label": "PlantumlService", "file_type": "code", "community": 1}
  ],
  "links": [
    {"source": "1", "target": "0", "relation": "uses", "confidence": "EXTRACTED", "weight": 0.9},
    {"source": "0", "target": "2", "relation": "calls", "confidence": "INFERRED", "weight": 0.7}
  ]
}

Kaynak kod (.kt, .java) yerel olarak analiz edilir tree-sitter,itiraz edilemez LLM. Sadece dokümantasyon dosyaları (.adoc, .md) Bir LLM çağrısı gerekir semantik çıkarma için. Bu yüzden`--update`Kotlin kodu üzerinde neredeyse aniden

Adım 2 : Gradle eklentisi, Knowledge Graph’i PlantUML’e dönüştürür.

pipeline mimarisi

plugin`com.cheroliv.plantuml`bir görevi entegre eder`generateKnowledgeGraphDiagram`kim dönüştürür`graph.json`PlantUML diyagramlarında bir şekildetamamen deterministik:

@startuml
skinparam backgroundColor #FEFEFE

participant "Gradle" as G
participant "GenerateKnowledgeGraphDiagramTask" as Task
participant "KnowledgeGraphParser" as Parser
participant "KnowledgeGraphRenderer" as Renderer
participant "PlantumlService" as PS

collections "graphify-out/graph.json" as JSON

G -> Task : execute
Task -> JSON : read
Task -> Parser : parse(graph.json)
Parser --> Task : KnowledgeGraph\n(noeuds + arêtes + communautés)
Task -> Renderer : render(graph, filters)
Renderer --> Task : code PlantUML\n(déterministe)
Task -> PS : validateSyntax(plantumlCode)
alt syntaxe valide
    Task -> PS : generateImage → .png
else syntaxe invalide
    Task -> Task : save .puml avec warning
end

@enduml

İç bileşenler

Bileşen Rol

KnowledgeGraphParser

ayrıştırmak`graph.json`— destekler 3 format : graphify yerli (nodes+links), legacy (communities), flat. Sayısal ID’leri etiketlere çözümler.

KnowledgeGraphRenderer

deterministik olarak bir dönüştür`KnowledgeGraph`PlantUML kodunda. Türüne göre gruplar, paketlerde topluluklar, otomatik açıklama.

GenerateKnowledgeGraphDiagramTask

Parse → render → validate → PNG’i düzenleyen Gradle görevi. Gradle özellikleri üzerinden yapılandırılabilir.

kgmodels.kt

Veri modelleri :`KnowledgeGraph`, KnowledgeGraphNode, KnowledgeGraphEdge, KnowledgeGraphCommunity, EdgeType.

PlantumlService

Sözdizimi doğrulaması + PNG oluşturma (pluginden tüm görevler tarafından yeniden kullanılır).

Render kuralları

Renderer, deterministik görsel kurallar uygular:

Kenar tipi PlantUML Notasyonu Anlam

çıkarılmış

-→(sabit çizgi, siyah)

Kaynak koddan çıkarılan ilişki (kesinlik)

ÇIKARILMIŞ

..> (trait pointillé)

Relation inférée par l’LLM (score de confiance)

belirsiz

--x (trait rouge pointillé)

Belirsiz ilişki (doğrulanacak)

Topluluklar, otomatik renk paleti olan PlantUML paketleri olarak gösterilir.

Adım 3 : Günlük kullanım

Diagramme complet

# Générer le diagramme du Knowledge Graph complet
./gradlew generateKnowledgeGraphDiagram

Çıktı:`diagrams/knowledge-graph/knowledge-graph-full.puml` + .png

Filtrer par communauté

# Une seule communauté
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.community=community_0

# Limiter le nombre de noeuds (lisibilité)
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.community=community_0 \
  -Pplantuml.kg.maxNodes=15

Kenar tipine göre filtrele

# Uniquement les relations certaines (EXTRACTED)
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.edgeTypes=EXTRACTED

# Relations certaines + inférées
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.edgeTypes=EXTRACTED,INFERRED

Filtrer par type de noeud et confiance

# Uniquement les classes de code
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.nodeTypes=code

# Seuil de confiance minimum (pour les INFERRED)
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.minConfidence=0.7

Répertoire de sortie personnalisé

./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.outputDir=docs/architecture

Référence complète des propriétés

Propriété Défaut Açıklama

plantuml.kg.community

(tüm)

Filtrer les communautés par nom (correspondance sous-chaîne)

plantuml.kg.edgeTypes

(tous)

Types d’arêtes séparés par virgules : EXTRACTED, INFERRED, AMBIGUOUS

plantuml.kg.minConfidence

0.0

Seuil minimum de confiance pour les arêtes

plantuml.kg.maxNodes

(illimité)

Nombre maximum de noeuds à afficher

plantuml.kg.nodeTypes

(tous)

Types de noeuds séparés par virgules (ex. class, code)

plantuml.kg.outputDir

diagrams/knowledge-graph

Répertoire de sortie pour les fichiers .puml et .png

Le pipeline complet dans un workflow Gradle

Workflow type

@startuml
skinparam backgroundColor #FEFEFE
skinparam ActivityBackgroundColor #E8F4FD
skinparam ActivityDiamondBackgroundColor #FFF3CD
skinparam ActivityBorderColor #2C3E50

start

partition "EXTRACTION" {
    :graphify . --no-viz;
    note right: Analyse le code source\ntree-sitter (local, pas de LLM)

    :graphify-out/graph.json;
    note right: Noeuds + arêtes\n+ communautés
}

partition "GÉNÉRATION" {
    :./gradlew generateKnowledgeGraphDiagram;
    note right: Pipeline déterministe\nparse → render → validate → PNG

    if (Filtres actifs ?) then (Oui)
        :Appliquer filtres\n(community, edgeTypes,\nmaxNodes, nodeTypes);
    else (Non)
        :Diagramme complet;
    endif

    :diagrams/knowledge-graph/\nknowledge-graph-full.puml\nknowledge-graph-full.png;
}

partition "INTÉGRATION" {
    :git add diagrams/knowledge-graph/;
    :git commit;
    note right: Diagrammes versionnés\ntoujours à jour avec le code
}

stop

@enduml

Le pipeline s’intègre naturellement dans les étapes clés du développement :

[*] --> dev
dev --> extract : Code modifié
extract --> generate : graph.json à jour
generate --> commit : .puml + .png générés
commit --> dev : Diagrammes dans le repo

  Quasi instantané sur du code Kotlin
  (tree-sitter, pas de LLM)
end note

note right of generate
  Déterministe
  Pas de LLM
  Résultat reproductible
end note

@enduml

Mise à jour incrémentale

Quand le code change, on ne reconstruit pas tout le graphe depuis zéro :

# Mise à jour incrémentale (fichiers modifiés uniquement)
graphify . --update

# Puis régénérer les diagrammes
./gradlew generateKnowledgeGraphDiagram

--update re-extrait uniquement les fichiers modifiés (détectés par SHA256 dans graphify-out/cache/). Sur du code Kotlin, c’est quasi instantané car tree-sitter travaille localement sans appel LLM.

Le dogfooding : le plugin se documente lui-même

Le plugin PlantUML existe pour transformer des prompts en diagrammes. Il peut aussi transformer le Knowledge Graph de sa propre codebase en diagrammes de documentation. C’est du dogfooding : le plugin consomme son propre service.

@startuml
skinparam backgroundColor #FEFEFE
skinparam componentStyle rectangle

package "Pipeline normal\n(utilisateur → diagrammes)" as normal {
    [Fichier .prompt] as prompt
    [LlmService\n+ ApiKeyPool] as llm1
    [ProcessPlantumlPromptsTask] as task1
    [Diagramme PNG] as out1

    prompt --> task1
    task1 --> llm1
    llm1 --> out1
}

package "Pipeline Knowledge Graph\n(déterministe, pas de LLM)" as kg {
    [graphify-out/graph.json] as kgjson
    [KnowledgeGraphParser] as parser
    [KnowledgeGraphRenderer] as renderer
    [PlantumlService] as ps
    [Diagramme PNG\n(documentation du plugin)] as out2

    kgjson --> parser
    parser --> renderer
    renderer --> ps
    ps --> out2
}

package "Pipeline Dogfooding\n(LLM → documentation du plugin)" as dogfood {
    [GraphifyPromptAdapter] as gpa
    [Fichiers .prompt\nauto-générés] as auto_prompt
    [LlmService\n+ ApiKeyPool] as llm2
    [ProcessPlantumlPromptsTask] as task2
    [Diagramme PNG\n(documentation LLM)] as out3

    kgjson --> gpa
    gpa --> auto_prompt
    auto_prompt --> task2
    task2 --> llm2
    llm2 --> out3
}

note "Même LlmService, même ApiKeyPool,\nmême PlantumlService\n— ZÉRO duplication" as N

@enduml

Tâches Gradle associées :

Tâche LLM ? Description

generateKnowledgeGraphDiagram

Non

Transforme graph.json en PlantUML (déterministe)

generateDiagramDocs

Oui

Génère des .prompt depuis le graphe, les traite via LLM (dogfooding)

 
# Documentation déterministe (rapide, pas de LLM)
./gradlew generateKnowledgeGraphDiagram

# Documentation LLM (plus riche, consomme des tokens)
./gradlew generateDiagramDocs

Pourquoi c’est déterministe (et pourquoi ça compte)

Le point clé du pipeline generateKnowledgeGraphDiagram : il n’appelle aucun LLM. La transformation graph.json → PlantUML est une fonction pure.

@startuml
skinparam backgroundColor #FEFEFE
skinparam componentStyle rectangle

rectangle "Pipeline DÉTERMINISTE\n(generateKnowledgeGraphDiagram)" as det {
    [graph.json] as json
    [KnowledgeGraphParser] as parser
    [KnowledgeGraphRenderer] as renderer
    [PlantUML code] as puml

    json --> parser : parse
    parser --> renderer : KnowledgeGraph
    renderer --> puml : render (fonction pure)
}

rectangle "Pipeline LLM\n(processPlantumlPrompts)" as llm {
    [.prompt] as prompt
    [LlmService] as llmSvc
    [ChatModel] as model
    [PlantUML code] as puml2

    prompt --> llmSvc
    llmSvc --> model : API call
    model --> puml2 : réponse non-déterministe
}

note bottom of det
  Même entrée → même sortie
  Pas de latence réseau
  Pas de coût en tokens
  Reproductible en CI
end note

note bottom of llm
  Même entrée → sortie variable
  Latence réseau (1-5s)
  Coût en tokens
  Nécessite une clave API
end note

@enduml

Les avantages concrets :

Avantage Impact

Reproductibilité

Même graph.json → même diagramme. Exactement. Tous les fois.

Zéro coût

Pas d’appel LLM = pas de tokens = pas de facture API.

Zéro latence

Parse + render prend ~100ms, pas 1-5 secondes.

Compatible CI

Pas de clé API nécessaire. Pas de flaky test dû à une réponse LLM variable.

Versionnable

Le .puml généré est du texte. On peut le diff, le reviewer en PR, le versionner dans Git.

Intégration dans la gouvernance de projet

Dans notre projet, ce pipeline s’intègre dans une stratégie de gestion de contexte EAGER/LAZY pour l’agent IA. Le Knowledge Graph remplace la documentation architecture manuelle par un graphe structuré, queryable, et auto-mis à jour.

@startuml
skinparam backgroundColor #FEFEFE
skinparam componentStyle rectangle

package "EAGER\n(toujours chargé)" as eager {
    [PROMPT_REPRISE.adoc\n(contexte session)] as pr
    [INDEX.adoc\n(vue d'ensemble)] as idx
    [GRAPH_REPORT.adoc\n(~50 lignes)] as gr
}

package "LAZY — Stratégie\n(sur demande)" as lazy_strat {
    [Méthodologies] as meth
    [Archives sessions] as sessions
}

package "LAZY — Graphify\n(requêtes ciblées)" as lazy_graph {
    [graph.json] as gj
    [Queries\n(query/path/explain)] as queries
}

package "Pipeline PlantUML\n(auto-généré)" as puml {
    [generateKnowledgeGraphDiagram] as kgTask
    [generateDiagramDocs] as ddTask
    [Diagrammes PNG] as diagrams
}

Agent --> eager : Lit en début de session
Agent ..> lazy_strat : Charge si type détecté
Agent ..> lazy_graph : Query si besoin structurel
kgTask --> diagrams : Déterministe
ddTask --> diagrams : Via LLM

note right of gr
  Condensé du Knowledge Graph
  God nodes + communautés
  Remplace ECOSYSTEM_OVERVIEW
  (225 lignes → 50 lignes)
end note

@enduml

Le mariage des deux systèmes est complémentaire :

  • La stratégie gère le QUAND et le COMMENT — gouvernance, workflow, archivage

  • Graphify gère le QUOI et le OÙ — structure du code, relations, requêtes ciblées

_ La stratégie de session gère le QUAND et le COMMENT (gouvernance, workflow, seuils), Graphify gère le QUOI et le OÙ (structure du code, relations, requêtes ciblées). Le pipeline PlantUML gère le AVEC QUOI (diagrammes déterministes, versionnés, toujours à jour). _

Pièges et mitigations

Piège Description Mitigation

Graphe trop dense

Un gros projet génère des centaines de noeuds illisibles

Utiliser -Pplantuml.kg.maxNodes=30 et filtrer par communauté

Exclusions trop larges

Trop de fichiers dans .graphifyignore réduit la valeur du graphe

Commencer par exclure seulement credentials et build

Direction des flèches

Les arêtes INFERRED peuvent avoir une direction ambiguë

Filtrer par -Pplantuml.kg.edgeTypes=EXTRACTED pour les relations certaines uniquement

Graphe obsolète

Le code change mais le graphe n’est pas reconstruit

Utiliser graphify . --update régulièrement ou le hook git graphify hook install

Coût mis à jour

Les mises à jour incrémentales sont quasi gratuites (tree-sitter local)

Seules les docs (.adoc) consomment des tokens LLM
