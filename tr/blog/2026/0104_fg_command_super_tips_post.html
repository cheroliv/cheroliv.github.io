Sorun: meşgul bir terminal

Her geliştirici bu durumu yaşamıştır :

$ ./gradlew build
> Building...

Terminal kilitlendi. Artık hiçbir komut yazamazsınız. Ve bir dosyayı görüntülemek, birini çalıştırmak ihtiyacınız var.git status, veya bir meşgul portu kontrol et.

@startuml
skinparam backgroundColor #FEFEFE

actor Développeur as dev
participant "terminal" as term
participant "Gradle
 ( süreç )" as gradle

dev -> term : ./gradlew build
term -> gradle : Lance le build
gradle -> term : Occupe le terminal\n(pas de prompt)
dev -> term : veut taper une commande
term --> dev : ❌ Terminal bloqué

note right of dev
  Le développeur est
  paralysé pendant
  toute la durée du build
end note
@enduml

Çoğu geliştirici yeni bir terminal açar. Ancak daha zarif, daha hızlı ve yerli bir çözüm vardır: iş yönetimi.

Üç zorunlu komut

Ctrl+Z — Askıya alma (SIGTSTP)

`Ctrl+Z`sinyal gönderir`SIGTSTP`süreç ön planda. süreçaskıya alınmışölmedi — ve terminal komut istemini yeniden alır.

$ ./gradlew build
> Building...
^Z
[1]+  Stoppé    ./gradlew build
$

Köşeli parantezler arasındaki sayı`[1]`diriş numarası. Le `+`varsayılan işi gösterir.

fg — Öne al

`fg`askıya alınan işi ön plana getirir. İşlem, durduğu yerden tam olarak devam eder.

$ fg
./gradlew build
> Building... (reprend où il en était)

Belirli bir iş numarasıyla :

$ fg %2

bg — Arka planda devam et

`bg`Terminali bloke etmeden işlemi devam ettir. Uzun derlemeler için ideal.

$ bg
[1]+ ./gradlew build &
$

Le `&`sonunda, işlemin arka planda çalıştığı anlamına gelir.

jobs` — Shell işlerini listelemek

$ jobs
[1]-  Stoppé    vim README.md
[2]+  En cours   ./gradlew build

skinparam defaultFontName sans-serif

state "Ön plan\n(bloke terminal)" as fg #LightCoral

[*] --> fg : Lance une commande
fg --> stopped : Ctrl+Z\n(SIGTSTP)
stopped --> fg : fg\nreprend en avant-plan
stopped --> bg_ : bg\nreprend en arrière-plan

fg --> [*] : Commande terminée

  Le processus est figé
  mais _pas_ tué
end note

note left of bg_
  Le terminal est libre
  le build continue
end note
@enduml

İleri düzey ipuçları

fg ile en güncel iş ve alternasyon

fg`argüman olmadan işaretli işi getirir+(en son). Ama başka bir şey de kullanabilirsiniz.%-`önceki işi hedeflemek için :

$ vim file1.txt
^Z
[1]+  Stoppé    vim file1.txt

$ vim file2.txt
^Z
[2]+  Stoppé    vim file2.txt

$ fg      # ramène job [2] (le plus récent)
$ fg %-   # ramène job [1] (le précédent)

bir işi düzgünce öldürmek

$ jobs
[1]-  Stoppé    vim config.yml
[2]+  Stoppé    ./gradlew test

$ kill %2       # envoie SIGTERM au job 2
$ kill -9 %1    # envoie SIGKILL au job 1 (force)

désown : kabuktan ayır

disown`Bir işi shell’in işler tablosundan çıkarır. İşlem çalışmaya devam eder ancak daha önceki şekilde geri getirilemez.`fg :

$ ./gradlew build &
[1] 12345

$ disown %1
# Le processus continue mais n'est plus lié au shell
# Ça survives à la fermeture du terminal

Combiner avec nohup pour les longs processus

Bir işlemin terminal kapatma sonrası hayatta kalması için:

$ nohup ./gradlew build &
[1] 12345
$ disown %1
# Le build continue même si vous fermez le terminal

Pièges et erreurs courantes

Bu en sık yapılan hatadır.Ctrl+C`İşlemi öldürür.`Ctrl+Z le suspend. Si vous appuyez sur Ctrl+C par réflexe, tout l’état est perdu — fichiers ouverts, sessions LLM, builds en cours.

Les jobs sont locaux au shell

jobs, fg et bg ne fonctionnent que dans le shell qui a lancé les processus. Si vous ouvrez un nouveau terminal, vous ne verrez pas les jobs de l’autre.

# Terminal 1
$ vim file.txt
^Z
[1]+  Stoppé    vim file.txt

# Terminal 2 (nouveau)
$ jobs
# (rien — les jobs sont locaux au shell)

Pour voir les processus system-wide, utilisez ps ou htop :

ps aux | grep vim

Les jobs ne survivent pas à la fermeture du shell

Si vous fermez le terminal, tous les jobs suspendus ou en arrière-plan sont détruits. Pour qu’un processus survive, utilisez nohup + disown :

$ nohup ./gradlew build &
[1] 12345
$ disown %1
# Fermer le terminal → le build continue

Les processus interactifs et fg

Certains programmes interactifs ne se portent pas bien après un Ctrl+Z + fg. C’est rare mais ça arrive :

  • Certains programmes qui utilisent des signaux (vim, htop, less gèrent bien Ctrl+Z)

  • Les programmes réseau longs (ssh, opencode) récupèrent généralement correctement

  • Les programmes qui modifient le terminal (ncurses) peuvent parfois laisser le terminal dans un état inattendu

En cas de terminal corrompu après un fg, tapez :

reset

Pourquoi fg est sous-estimé

La plupart des développeurs modernes découvrent fg tard, voire jamais. Quelques raisons :

  1. Les IDE cachent le terminal : VS Code propose un terminal intégré, mais les onglets multiples rendent fg moins nécessaire en apparence

  2. Les outils graphiques remplacent les CLI : les gestionnaires de fichiers, les moniteurs système, les clients Git graphiques

  3. tmux et screen : ces multiplexeurs résolvent le même problème différemment, mais fg est plus simple et toujours disponible

Pourtant, fg est :

  1. Universel : présent dans tous les shells POSIX (bash, zsh, fish…​)

  2. Sans dépendance : pas besoin d’installer tmux ou screen

  3. Instantané : deux frappes (Ctrl+Z puis fg) pour suspendre et reprendre

  4. Préservateur de contexte : l’état du processus est intact

Conclusion

fg n’est pas un tips obscur — c’est un mécanisme fondamental du shell Unix, disponible depuis les années 70. Le fait que la plupart des développeurs l’ignorent est un symptôme de notre époque : les IDE et les multiplexeurs nous ont éloignés des bases.

Mais quand vous êtes sur un serveur SSH, dans un terminal minimal, ou simplement en train d’utiliser opencode et que le LLM est en plein travail — Ctrl+Z, fg, bg, jobs sont vos meilleurs amis.

_ Ctrl+Z suspend, fg reprend. C’est la pause-play du terminal. _
