Yerel siteniz hiçbirşey gibi görünüyor ama çevrimiçi olarak dağıtıldıktan sonra her şey mükemmel oluyor, bu anı hatırlıyor musunuz? Bu, Gradle JBake eklentimle bana gerçekleşti. Görev`serve`kare düğmeler gösteriyordu, siyah arka plana koyu metin ve bir CSS olağandışı olarak eksikti. Ancak`publishSite`aynı siteyi oluşturuyordu, mükemmel. Suçlu CSS değildi, tarayıcı değildi, önbellek değildi. Bir Kotlin kodu satırıydı — ve komut satırı argümanlarıyla ilgili bir kötü alışkanlık.

Tanılama: serve doğru klasöre işaret etmiyordu

Gradle eklentim`bakery`iki ana görevi var :

  • bake: statik siteyi içinde oluşturur`build/bake/`

  • serve: yerel bir web sunucusu başlatır

  • publishSite: büyür`build/bake/`GitHub Pages’e

Farklılık sadece oradan gelebilirdi.serve. Si publishSite`doğru içeriği yayınlıyordu, şu ki`build/bake/`iyiydi. Eğer`serve`başka şey gösteriyordu, çünkü işe yaramıyordu`build/bake/.

Kodu görelim. İçinde`SiteManager.kt`, görev`serve`tanılır böyle:

SiteManager.kt — La tâche serve (version buggy)
tasks.register("serve", JavaExec::class.java) { task ->
    task.apply {
        mainClass.set("org.jbake.launcher.Main")
        classpath = jbakeRuntime
        environment("GEM_PATH", jbakeRuntime.asPath)
        jvmArgs(/* ... */)
        args = listOf(
            "-b", file(site.bake.srcPath).absolutePath,
            "-s", layout.buildDirectory.get()
                .asFile.resolve(site.bake.destDirPath)
                .absolutePath
        )
    }
}

org.jbake.launcher.Main`JBake 2.7.0 CLI’sinin giriş noktasıdır. Fikir: geçmek-b`kaynak klasörü için ve`-s`hedef klasör için, ardından sunucu modunu başlat. Fakat…​

Kök neden: JBake CLI böyle çalışmıyor

JBake 2.7.0 bekliyorpozisyonel argümanlarkaynak ve hedef için, ardından isteğe bağlı bayraklar. İmza şu şekildedir:

jbake <source> <destination> [options]

Or dans mon code, j’écrivais :

args = listOf("-b", "/path/to/site", "-s", "/path/to/build/bake")

JBake interprétait ça comme :

  1. -b → parse le flag "bake" (booléen), consommé

  2. /path/to/site → devient argument positionnel 1 (source)

  3. -s → parse le flag "serve" (booléen), serveur lancé immédiatement

  4. /path/to/build/bake→ bir emek argümanı olur, yoksayılır veya yanlış yorumlanır

Résultat : JBake prenait /path/to/site comme source, ne tenait pas compte de la destination fournie (build/bake), et utilisait son répertoire par défaut (souvent ./output ou une copie temporaire). Le fichier css/styles.css du build était donc écrasé ou ignoré, et c’est un vieux CSS par défaut (sans les variables custom, sans les arrondis, sans les ombres) qui était servi.

En comparaison, bake et publishSite utilisent le Resmi Gradle JBake eklenti (jbake-gradle-plugin) qui écrit proprement dans build/bake/ via l’API Gradle. Ils ne passent pas par la CLI.

Çözüm: konumsal argümanlar, bayraklar değil

La correction est triviale — une fois qu’on sait. Il suffit de passer source et destination comme arguments positionnels, puis -s en dernier :

SiteManager.kt — La tâche serve (version corrigée)
args = listOf(
    file(site.bake.srcPath).absolutePath,
    layout.buildDirectory.get()
        .asFile.resolve(site.bake.destDirPath)
        .absolutePath,
    "-s"
)

İşte bu. Üç satır değiştirildi, hata çözüldü.

Après publication locale du plugin (publishToMavenLocal), un ./gradlew serve lance JBake avec la syntaxe correcte :

jbake /home/user/project/site /home/user/project/build/bake -s

Et cette fois-ci, le serveur Jetty intégré à JBake sert bien le contenu de build/bake/— çevrimiçi olarak yayınlananla aynı

@startuml
!define RECTANGLE class

package "ÖNCE (bug)" {
  RECTANGLE JBakeCLI1 {
    + args = ["-b", "site", "-s", "build/bake"]
  }

  RECTANGLE Source1 {
    + site/
  }

  RECTANGLE Dest1 {
    + ??? (dossier temporaire)
  }

  RECTANGLE Jetty1 {
    + sert mauvais fichiers
  }

  JBakeCLI1 --> Source1 : lit
  JBakeCLI1 -[#red]x Dest1 : destination ignorée
  Jetty1 --> Dest1 : sert
}

package "APRÈS (fix)" {
  RECTANGLE JBakeCLI2 {
    + args = ["site", "build/bake", "-s"]
  }

  RECTANGLE Source2 {
    + site/
  }

  RECTANGLE Dest2 {
    + build/bake/
  }

  RECTANGLE Jetty2 {
    + sert les bons fichiers
  }

  JBakeCLI2 --> Source2 : lit
  JBakeCLI2 --> Dest2 : écrit dans
  Jetty2 --> Dest2 : sert OK
}
@enduml

Vérification rapide avec curl

Pour s’assurer que le serveur sert bien le bon contenu, un simple curl confirme que index.html contient data-bs-theme="light" et que build/bake/css/styles.css pèse bien 31 402 octets — identique au fichier généré par bake.

$ ./gradlew serve
# Dans un autre terminal :
$ curl -s http://localhost:8820/ | grep data-bs-theme
<html ... data-bs-theme="light" ...>

$ curl -I http://localhost:8820/css/styles.css
HTTP/1.1 200 OK
Content-Length: 31402
Content-Type: text/css

Le rendu local est désormais pixel-identique au rendu déployé.

Pourquoi ce bug était vicieux

Vous voyez pourquoi c’était difficile à attraper ?

  1. Pas d’erreur explicite : JBake ne crashait pas. Il "fonctionnait", simplement avec un mauvais dossier.

  2. Le build fonctionnait : ./gradlew bake générait correctement les fichiers dans build/bake/.

  3. Le déploiement fonctionnait : publishSite poussait le bon contenu en ligne.

  4. Seul serve était cassé : la tâche de développement, celle qu’on utilise constamment pour itérer.

  5. L’habitude du -key value : en tant que développeur, on est conditionné par des années de CLI Unix (-o output, -i input). JBake CLI bir istisnadır — kaynak ve hedef pozisyonel.

Conclusion

Si vous maintenez un plugin Gradle qui wrappe JBake (ou tout outil CLI), lisez la doc des arguments même si vous pensez les connaître. Une hypothèse implicite (-s = "set destination") peut vous coûter des heures de debugging visuel.

Ici, le fix était littéralement de changer :

args = listOf("-b", src, "-s", dest)   // ❌ BUG

en :

args = listOf(src, dest, "-s")         // ✅ FIX

Trois tokens déplacés, et mon site local redevient aussi beau que le site en production.

Leçon : quand le rendu diffère entre local et prod sans raison évidente, suspectez d’abord le pipeline — pas le CSS, pas le navigateur, et encore moins le framework. C’est souvent l’étape juste avant le rendu qui triche.
