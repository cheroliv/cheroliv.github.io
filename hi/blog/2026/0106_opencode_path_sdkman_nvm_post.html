आप अपने टर्मिनल में OpenCode लॉन्च करते हैं, सब काम कर रहा है। एजेंट एक प्रयास कर रहा है`gh`— अप्राप्य. एक`java -version`— अनुपस्थित। एक`node`— कहीं नहीं. हालांकि, ये उपकरण सही जगह पर हैं आपके votre shell में। समस्या? OpenCode शेल्स लॉन्च करता है।गैर-इंटरैक्टिवजो कभी आपके नहीं पढ़ते`.zshrc`. यहाँ बताया गया है कि इसे सही तरीके से कैसे निदान और सुधार करें।

दृश्य: उपकरणों की दुनिया में एक अंधा एजेंट

यह मंगलवार की शाम थी। मैंneas स्थापित कर चुका थाhttps://opencode.ai[OpenCode], वह AI एजेंट जो मेरे कोडिंग के तरीके को बदलने का वादा करता था। पहला परीक्षण: उसे मेरे GitHub रिपॉज़िटरीज़ की सूची देने के लिए कहना।

$ opencode
> Utilise gh pour lister mes repos
❌ bash: gh: command not found

अजीब.`gh`मेरे टर्मिनल में यह पूरी तरह से काम कर रहा था। मैं कुछ अलग प्रयास कर रहा हूँ:

> Vérifie la version de Java
❌ bash: java: command not found

फिर :

> Lance le build Gradle
❌ bash: gradle: command not found

Java, Gradle, Node,`gh`सब कुछ एजेंट के लिए अदृश्य था। मेरा टर्मिनल, हालांकि, सब कुछ देखता था। जैसे कि एजेंट और मैं दो समानांतर दुनिया में रह रहे होते।

मुझे समझने में घंटे लग गए। घंटों`echo $PATH`, de which java, बढ़ती निराशा के कारण। मैं अंततः समझ गया कि समस्या उपकरण नहीं थी — यह थाशेल. OpenCode, किसी भी एजेंट की तरह जो सबप्रोसेस लॉन्च करता है, शेल्स में काम करता हैगैर-इंटरेक्टिव. Zsh, इन शेल्स में, आपके को पूरी तरह से अनदेखा करता है`.zshrc`.

जो आगे आता है, इस निदान, समाधान, और मेरे द्वारा सीखा गया सबक का पूरा विवरण है। यदि आप एक AI एजेंट — OpenCode, Aider, Cursor, या यहां तक कि cron स्क्रिप्ट — का उपयोग करते हैं, तो यह समस्या एक दिन आपको प्रभावित करेगी।

बग की अनाटॉमी : दो शेल, दो दुनिया

जब आप टर्मिनल खोलते हैं, Zsh इसे एक शेल के रूप में व्यवहार करता हैइंटरैक्टिव. वह चार्ज करता है`.zshrc`, सब कुछ शुरू करता है : SDKMAN, NVM, pnpm, उपनाम, आपका सुंदर प्रॉम्प्ट. आपका वातावरण पूरा है।

लेकिन जब OpenCode एक कमांड चलाता है, तो यह एक इंटरैक्टिव टर्मिनल नहीं लॉन्च करता। यह एक शेल लॉन्च करता है।गैर-इंटरैक्टिव— एक कार्य शेल, स्क्रीन के पीछे कोई मानव नहीं। और इस संदर्भ में Zsh, कूदता है।.zshrc. वह केवल पढ़ता है`.zshenv`.

इस अंतर क्यों मौजूद है? क्योंकि एक गैर-इंटरैक्टिव शेल स्क्रिप्ट निष्पादित करने के लिए डिज़ाइन किया गया है, मानव उपयोगकर्ता की सेवा करने के लिए नहीं। बैकग्राउंड में चलने वाले स्क्रिप्ट में एलियास, प्रॉम्प्ट और पूर्णता को लोड करना बर्बादी होगी। समस्या यह है कि आपका PATH — निष्पादन योग्य खोजने के लिए सबसे महत्वपूर्ण जानकारी — अक्सर इस प्रकार इनिशियलाइज़ किया जाता है`.zshrc`, नहीं में`.zshenv`.

समस्या की जड़:Zsh .zshrc को केवल इंटरैक्टिव shells के लिए source करता है. OpenCode, किसी भी IA एजेंट की तरह जो सबप्रोसेस लॉन्च करता है, गैर-इंटरैक्टिव शैल का उपयोग करता है। ये शैल केवल पढ़ते हैं`.zshenv`.

दोषी: .zshrc vs .zshenv

Zsh के पास हैचार प्रारंभ फ़ाइलें, प्रत्येक में एक विशिष्ट भूमिका है। यह एक शालीन डिज़ाइन है—लेकिन यह समस्या का नोड भी है :

आवश्यक पर्यावरण चर, PATH

✅ हाँ — यह उसकी जगह है

तालिका एक संकेत देती है, लेकिन इसे गहराई से समझना आवश्यक है। इसे घर के कमरों की तरह सोचें:

  • `.zshenv`है

(Note: The output includes a leading space before "है" and a trailing space after it, matching the spacing in the source fragment " est le".)प्रवेश हॉल— हर कोई यहाँ से गुज़रता है, चाहे वह आगंतुक हो या स्थायी निवासी। यदि आप यहाँ कुछ रखते हैं, तो सभी शेल इसे देख सकते हैं।

  • `.zshrc`हैड्राइंग रूम— केवल निवासी (shells interactifs) इसमें प्रवेश करते हैं। आगंतुक (shells non-interactifs) हॉल में रहते हैं।

  • .zprofile et `.zlogin`ये लॉगिन शेल के लिए विशेषीकृत टुकड़े हैं (जैसे जब आप SSH से जुड़ते हैं).

दुखद बात यह है कि हममें से अधिकांश PATH को ड्रॉइंग रूम में रखते हैं। और एआई एजेंट को कभी भी वहां जाने की अनुमति नहीं है।

जब आप एक टर्मिनल खोलते हैं, Zsh इंटरैक्टिव है: यह पढ़ता है`.zshrc`, सब कुछ काम करता है। जब OpenCode एक शेल लॉन्च करके एक कमांड चलाता है, Zsh इंटरैक्टिव नहीं होता: वह कूदता है`.zshrc`, केवल पढ़ता है`.zshenv`. Et si `.zshenv`मौजूद नहीं है या इसमें PATH नहीं है — यह एक रेगिस्तान है।

Zsh ऐसा क्यों करता है?यह यूनिक्स से विरासत में मिला एक डिज़ाइन विकल्प है। एक गैर-इंटरेक्टिव शेल होना चाहिएतेज et पुनरावृत्तीय. SDKMAN के एलीयास, रंगीन प्रॉम्प्ट और भारी प्रारम्भीकरण को cron स्क्रिप्ट या AI एजेंट में लोड करने से धीमा और भंगुर हो जाएगा। इसलिए अलगाव तार्किक है :`.zshenv`मुख्य रूप से (variables, PATH)`.zshrc`सुविधा के लिए (aliases, prompt, complétons)। समस्या तब होती है जब हम सार को सुविधा में रखते हैं।

चरणबद्ध निदान

सुधारने से पहले, यह समझना आवश्यक है कि ठीक क्या कमी है। यहाँ एक पुनरावृत्ति योग्य निदान विधि है — यदि आप IA एजेंटों के साथ काम करते हैं, तो इसे बुकमार्क में रखें।

1. एजेंट का PATH जाँचें

इंटरैक्टिव टर्मिनल द्वारा देखे गए की तुलना गैर-इंटरैक्टिव शेल द्वारा देखे गए से की जाती है — यानी OpenCode द्वारा देखे गए से।

# Dans votre terminal interactif (tout fonctionne)
echo $PATH | tr ':' '\n' | grep -v '^/usr' | sort

सामान्य परिणाम :

/home/cheroliv/apps
/home/cheroliv/.nvm/versions/node/v22.19.0/bin
/home/cheroliv/.sdkman/candidates/java/current/bin
/home/cheroliv/.sdkman/candidates/gradle/current/bin
/home/cheroliv/.local/share/pnpm
/home/cheroliv/.local/bin

अब, एजेंट द्वारा देखे गए को सिमुलेट करते हैं — एक इंटरैक्टिव शेल नहीं:

# Shell non-interactif : pas de .zshrc
zsh -c 'echo $PATH' | tr ':' '\n' | grep -v '^/usr' | sort

परिणाम :

/home/cheroliv/.local/bin

छह में से पाँच मार्ग लुप्त हो गए हैं।एजेंट अपने पर्यावरण का 83% खो चुका है। यह ऐसा है जैसे आपको अपने बर्तनों की आधी संख्या के बिना खाना बनाना पड़े — आप पानी उबाल सकते हैं, लेकिन कुछ और नहीं।

आदेश`zsh -c 'echo $PATH'`आपका हैनिदान उपकरण नंबर 1. यदि कोई उपकरण जिसे आप रोज़ाना उपयोग करते हैं परिणाम में अनुपस्थित है, आपका AI एजेंट इसे भी नहीं देख सकेगा। इसका परीक्षण करें प्रत्येक संशोधन से पहले और बाद`.zshenv`.

2. पहचानें कि .zshrc में क्या है लेकिन .zshenv में नहीं

अब, हम दोषी की तलाश में हैं`.zshrc`हम उन पंक्तियों को फ़िल्टर करते हैं जो हमारे टूल्स का उल्लेख करते हैं :

grep -n 'apps\|SDKMAN\|NVM\|PNPM\|PATH' ~/.zshrc

आम तौर पर पाया जाता है :

119: PATH="/usr/bin/python3:$HOME/apps:$PATH"           # ← pas exporté !
171: export NVM_DIR="$HOME/.nvm"
172: [ -s "$NVM_DIR/nvm.sh" ] && \. "$NVM_DIR/nvm.sh"   # ← NVM init
176: nvm use --lts --silent                              # ← active une version
179: export PNPM_HOME="/home/cheroliv/.local/share/pnpm"
187: export SDKMAN_DIR="$HOME/.sdkman"
188: [[ -s "$HOME/.sdkman/bin/sdkman-init.sh" ]] && source "$HOME/.sdkman/bin/sdkman-init.sh"

यह सब हैअदृश्यOpenCode के लिए और का`PATH`पंक्ति 119 की भी नहीं है`export`é — वह वर्तमान शेल कभी नहीं छोड़ता। यह एक महत्वपूर्ण तकनीकी विवरण है : एक चर बिना`export`यह उस शेल में स्थानीय रहता है जो इसे परिभाषित करता है। उप-शेल — जैसे कि OpenCode द्वारा लॉन्च किए गए — इसे कभी नहीं विरासत में प्राप्त करते।

3. .zshenv फ़ाइल मौजूद है या नहीं जाँचें

cat ~/.zshenv 2>/dev/null || echo "FICHIER ABSENT"

यदि उत्तर 'फ़ाइल नहीं मिली' है, तो यही वह जगह है जहाँ सब कुछ तय होता है।

समाधान: .zshenv + सही पथ

रणनीति सरल है, लेकिन इसे सटीकता की आवश्यकता है: भीतर रखना`.zshenv` केवलज़रूरी पथें, भारी आरंभीकरण स्क्रिप्ट्स को स्रोत किए बिना, हम इसे नहीं ले जाते`.zshrc`में`.zshenv`— सार निकाला जाता है।

सभी आवश्यक पथों वाला .zshenv बनाएँ

`.zshenv`हैकेवल फ़ाइलकि Zsh स्रोत करने की गारंटी देता हैसभीles contextes. यहाँ PATH जाना चाहिए।

export SDKMAN_DIR="$HOME/.sdkman"
export NVM_DIR="$HOME/.nvm"
export PNPM_HOME="$HOME/.local/share/pnpm"
export PATH="$HOME/apps:$HOME/.sdkman/candidates/java/current/bin:$HOME/.sdkman/candidates/gradle/current/bin:$HOME/.nvm/current/bin:$PNPM_HOME:$HOME/.local/bin:$HOME/.local/share/JetBrains/Toolbox/scripts:/usr/bin/python3:$PATH"

हम उपयोग करते हैं`$HOME/.nvm/current/bin`और नहीं`$HOME/.nvm/versions/node/v22.19.0/bin`. कारण : Node के संस्करण बदल रहे हैं। एक हार्डकोडेड पथ अगले में गलत हो जाता है`nvm install`. अधिक विवरण निम्नलिखित अनुभाग में।

क्यों नहीं source sdkman-init.sh .zshenv में ?

यह सबसे आकर्षक दृष्टिकोण बस दोहराने में होगा`.zshenv`हम क्या करते हैं`.zshrc`— इनिशियलाइज़ेशन स्क्रिप्ट्स को स्रोत से लाएँ. हमसकताकरने के लिए प्रलोभित होना

# ❌ MAUVAISE IDÉE
[[ -s "$HOME/.sdkman/bin/sdkman-init.sh" ]] && source "$HOME/.sdkman/bin/sdkman-init.sh"

समस्याएँ :

  • धीमा : `sdkman-init.sh`यह प्रत्येक शेल पर नेटवर्क संकल्पन और जाँच करता है। एक गैर-इंटरेक्टिव शेल में, यह अनावश्यक लागत है।

  • नाजुकSDKMAN को एक इंटरेक्टिव संदर्भ की अपेक्षा होती है। इसकी प्रारंभिक सेटअप पाइप या सबशेल में चुपचाप विफल हो सकती है।

  • बेमानी: SDKMAN अपने उम्मीदवारों को रखता है`~/.sdkman/candidates/<tool>/current/bin`— स्थिर सिमलिंक सक्रिय संस्करण की ओर इशारा करते हैं। इनका उपयोग किया जा सकता हैसीधे.

सही तरीका: SDKMAN की इनिशियलाइज़ेशन को बायपास करना और सीधे सिंबोलिक लिंक्स को इंगित करना`current`. यह समाधान की पूरी कुंजी है :फ़ाइल संरचना को अनुबंध के रूप में उपयोग करें, प्रारम्भिक कोड के बजाय.

NVM का मामला: जब वर्ज़न मैनेजर एक ट्रेस छोड़ना भूल जाता है

समस्या NVM

यहाँ पर जाँच ने мне सबसे दूर ले गया। SDKMAN का एक शानदार डिज़ाइन है: जब कोई करता है`sdk install java 25.0.2-tem`, यह सिमलिंक बनाता है :

~/.sdkman/candidates/java/current -> ~/.sdkman/candidates/java/25.0.2-tem

यह सिंबलिक लिंक हैहमेशा अपडेटेड. इशारा करें ऊपर में`.zshenv`और आप कवर किए गए हैं, शेल जो भी हो। Beautiful.

NVM, उसे, नहीं बनाताकुछ नहींऐसा का। सिमलिंक नहीं`current`. कोई स्थायी एंकर बिंदु नहीं। हमें एक हार्डकोडेड संस्करणित पथ पर इशारा करना चाहिए, जो इस तरह दिखता है:

~/.nvm/versions/node/v22.19.0/bin/node

अगला`nvm install 24`, यह रास्ता मृत है. आपका`.zshenv`यह एक ऐसी संस्करण की ओर इशारा करेगा जो अब सक्रिय संस्करण नहीं है। यह एक टाइम बम है।

NVM ऐसा क्यों करता है ?NVM कार्य करता है डायनामिकली PATH को संशोधित करके हर`nvm use`. यह डिज़ाइन किया गया है डेवलपर्स के लिए जो अक्सर संस्करण बदलते हैं, एक इंटरैक्टिव शेल में। सिमलिंक`current`यह शुरूआती विशिष्टताओं में नहीं था — यह डिज़ाइन की एक चूक है जिसे हम खुद सुधारेंगे।

हल : NVM के लिए सिमलिंक current बनाएँ

क्योंकि NVM ऐसा नहीं करता, हम इसे खुद करते हैं। सिद्धांत SDKMAN के समान है — एक सिम्लिंक`current`जो हमेशा सक्रिय संस्करण की ओर इशारा करता है। हम इसे एक बार बनाते हैं, फिर हम इसे स्वचालित करते हैं ताकि यह स्वयं अपडेट हो।

# Créer le symlink initial
ln -sfn "$HOME/.nvm/versions/node/v22.19.0" "$HOME/.nvm/current"

अब, में`.zshenv`, एक उपयोग करते हैं :

$HOME/.nvm/current/bin

इसके बजाय :

# ❌ Chemin en dur — cassé au prochain changement de version
$HOME/.nvm/versions/node/v22.19.0/bin

सिमलिंक के अपडेट को स्वचालित करें

एक सिमलिंक कुछ भी मूल्यवान नहीं है यदि यह अपडेट नहीं होता। सिमलिंक`current`इसे अपडेट करना चाहिए जब हम करते हैं`nvm use` ou nvm install. समाधान: एकरैपर— एक फ़ंक्शन जो असली कमांड को लपेटता है`nvm`और हर कॉल के बाद सिमलिंक को अपडेट करता है।

# À la fin de .zshrc, APRÈS le chargement de NVM
nvm use --lts --silent
ln -sfn "$(nvm_version_path "$(nvm current)")" "$NVM_DIR/current"

_nvm() {
  command nvm "$@"
  local rc=$?
  ln -sfn "$(nvm_version_path "$(nvm current)")" "$NVM_DIR/current"
  return $rc
}
alias nvm='_nvm'

यह कैसे काम करता है, विस्तार से :

अंतिम सत्यापन

बनाने के बाद`.zshenv`और सिमलिंक NVM, सुनिश्चित करें कि सब कुछ सही काम कर रहा है — दोनों संदर्भों में:

# Shell interactif (votre terminal)
gh --version && java -version && node --version
# Shell non-interactif (simulation OpenCode)
zsh -c 'gh --version && java -version && node --version'

दोनों को सफल होना चाहिए। यदि हाँ, तो आपका AI एजेंट वही उपकरण देखेगा जो आप देखते हैं। यदि नहीं, तो कृपया चरण-दर-चरण निदान पर वापस आएँ — आप शायद एक पथ भूल गए हैं या NVM सिमलिंक अपडेट नहीं है।

इस परीक्षण को स्वचालित करेंइस जाँच को अपने टूल्स के हर अपडेट के बाद चलाए जाने वाले healthcheck स्क्रिप्ट में जोड़ें। एक`zsh -c 'which java && which node && which gh'`CI, यह आश्चर्य के खिलाफ एक बीमा है।

_ गैर-इंटरैक्टिव शेल एक चुपचाप बैठे मेहमान की तरह होता है: वह केवल वही पढ़ता है जो प्रवेश द्वार पर प्रदर्शित होता है। यदि PATH ड्राइंग रूम में है, तो वह इसे कभी नहीं देख पाएगा। _

  • SDKMAN : इंस्टॉलेशन— SDKMAN स्थापना मार्गदर्शक.

  • gh` — GitHub CLI— GitHub का कमांड-लाइन टूल, हर डेवलपर के लिए आवश्यक।

  • Gradle — आधिकारिक साइट— SDKMAN के माध्यम से हम जो बिल्ड सिस्टम स्थापित करते हैं।

  • pnpm — आधिकारिक साइट— Node.js का तेज़ और जगह बचाने वाला पैकेज मैनेजर।

  • JetBrains Toolbox— जेटब्रेन्स IDE प्रबंधक, जो अपने स्क्रिप्ट को PATH में जोड़ता है।
