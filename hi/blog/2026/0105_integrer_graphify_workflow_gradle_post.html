समस्या: आरेख हमेशा कोड के पीछे रहते हैं

कुछ हज़ार पंक्तियों से अधिक वाली प्रत्येक परियोजना इस सिंड्रोम का अनुभव करती है :

  1. हम प्रोजेक्ट के शुरुआत में आर्किटेक्चर डायग्राम बनाते हैं।

  2. कोड विकसित हो रहा है, निर्भरताएँ बदल रही हैं

  3. आरेख सजावटी झूठ बन जाता है

  4. कोई इसे अपडेट नहीं करता क्योंकि यह थकाऊ है।

  5. नए आगंतुक इस पर आधारित होते हैं और गलतियाँ करते हैं

प्रश्न यह नहीं है कि क्या हमें आरेख चाहिए — सभी जानते हैं कि हाँ। प्रश्न यह है:कौन उन्हें अद्यतन रखता है ?

जवाब: कोई नहीं। सिवाय इसके कि यह स्वचालित हो।

समाधान: एक निर्धारित Knowledge Graph → PlantUML पाइपलाइन

सिद्धांत सरल है: हाथ से आरेख बनाने के बजाय, हम उन्हेंवास्तविक कोड संरचना से उत्पन्न होता है.

दो कमांडें. बस यही है।

# Étape 1 : extraire le Knowledge Graph
graphify . --no-viz

# Étape 2 : générer les diagrammes PlantUML
./gradlew generateKnowledgeGraphDiagram

चरण 1 : Graphify इंस्टॉल करें और Knowledge Graph एक्सट्रैक्ट करें

स्थापना

Graphify एक पायथन टूल है जो आपका कोडबेस विश्लेषण करता है और एक संरचित ज्ञान ग्राफ़ बनाता है:

# Méthode recommandée
uv tool install graphifyy && graphify install --platform opencode

# Alternative avec pip
pip install graphifyy && graphify install --platform opencode

अपवादों को कॉन्फ़िगर करें

एक फ़ाइल बनाएँ`.graphifyignore`प्रोजेक्ट के मूल में व्यवसायिक तर्क से संबंधित नहीं होने वाली फ़ाइलों को बाहर रखने के लिए:

# Secrets — JAMAIS dans le graphe
*-context.yml
*.env

# Fichiers générés
build/
.gradle/

# Tests fonctionnels
src/functionalTest/

ज्ञान ग्राफ़ निकालें

graphify . --no-viz

फ़्लैग`--no-viz`HTML जनरेशन को छोड़ देता है (Gradle पाइपलाइन में अनावश्यक)। परिणाम एक फ़ाइल है।`graphify-out/graph.json`सामग्री :

  • गाँठें: क्लास, फ़ंक्शन, फ़ाइलें — उनके प्रकार और समुदाय के साथ

  • किनारेनोड्स के बीच संबंध (EXTRACTED कोड से, INFERRED LLM द्वारा)

  • समुदायसंबद्ध नोड्स के स्वचालित समूह

उदाहरण संरचना`graph.json`
{
  "nodes": [
    {"id": "0", "label": "LlmService", "file_type": "code", "community": 0},
    {"id": "1", "label": "ApiKeyPool", "file_type": "code", "community": 0},
    {"id": "2", "label": "PlantumlService", "file_type": "code", "community": 1}
  ],
  "links": [
    {"source": "1", "target": "0", "relation": "uses", "confidence": "EXTRACTED", "weight": 0.9},
    {"source": "0", "target": "2", "relation": "calls", "confidence": "INFERRED", "weight": 0.7}
  ]
}

स्रोत कोड (.kt, .java) tree-sitter द्वारा स्थानीय रूप से विश्लेषित किया जाता है,अपील रहित. केवल दस्तावेज़ फ़ाइलें (.adoc, .md) आवश्यक हैं एक LLM कॉल सेमेंटिक निष्कर्षण के लिए। इसलिए`--update`कोटलिन कोड पर लगभग तात्कालिक है।

चरण 2 : Gradle प्लगइन Knowledge Graph को PlantUML में बदलता है

पाइपलाइन की आर्किटेक्चर

प्लग इन`com.cheroliv.plantuml`एक कार्य को एकीकृत करता है`generateKnowledgeGraphDiagram`जो बदलता है`graph.json`PlantUML डायग्रामों में तरीके सेपूरी तरह निर्धारक :

आंतरिक घटक

घटक भूमिका

KnowledgeGraphParser

पार्स`graph.json`— समर्थन करता है 3 प्रारूप: graphify natif (nodes+links), विरासत (communities), flat. समाधान करता है इन IDs संख्यात्मक में लेबल.

KnowledgeGraphRenderer

एक को निर्धारित रूप से बदलता`KnowledgeGraph`PlantUML कोड में. प्रकार द्वारा समूह, पैकेज में समुदाय, स्वचालित लीजेंड।

GenerateKnowledgeGraphDiagramTask

ग्रेडल कार्य जो parse → render → validate → PNG को ऑर्केस्ट्रेट करता है। Gradle गुणों के माध्यम से कॉन्फ़िगर करने योग्य।

kgmodels.kt

डेटा मॉडल:`KnowledgeGraph`, KnowledgeGraphNode, KnowledgeGraphEdge, KnowledgeGraphCommunity, EdgeType।

PlantumlService

सिंटैक्स मान्यता + PNG रेंडरिंग (प्लगइन के सभी कार्यों द्वारा पुनः उपयोग किया जाता)

रेंडरिंग के नियम

रेन्डरर निर्दिष्ट दृश्य सम्मेलन लागू करता है:

किनारे का प्रकार PlantUML नोटेशन अर्थ

EXTRACTED

-→(रेखा भरा, काला)

स्रोत कोड से निकाली गई संबंध (निश्चितता)

INFERRED

..>(बिंदुदार रेखा)

LLM द्वारा अनुमानित संबंध (विश्वास स्कोर)

Please provide the French text you would like translated into Hindi.

--x(लाल बिंदुदार रेखा)

अस्पष्ट संबंध (जाँचने की आवश्यकता)

समुदायों को स्वचालित रंग पैलेट वाले PlantUML पैकेज के रूप में प्रस्तुत किया जाता है।

चरण 3: दैनिक उपयोग

पूर्ण आरेख

# Générer le diagramme du Knowledge Graph complet
./gradlew generateKnowledgeGraphDiagram

आउटपुट:`diagrams/knowledge-graph/knowledge-graph-full.puml`(No response).png

समुदाय द्वारा फ़िल्टर

# Une seule communauté
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.community=community_0

# Limiter le nombre de noeuds (lisibilité)
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.community=community_0 \
  -Pplantuml.kg.maxNodes=15

एज प्रकार के अनुसार फ़िल्टर करें

# Uniquement les relations certaines (EXTRACTED)
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.edgeTypes=EXTRACTED

# Relations certaines + inférées
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.edgeTypes=EXTRACTED,INFERRED

नोड के प्रकार और विश्वास द्वारा फ़िल्टर करें

# Uniquement les classes de code
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.nodeTypes=code

# Seuil de confiance minimum (pour les INFERRED)
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.minConfidence=0.7

कस्टम आउटपुट निर्देशिका

./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.outputDir=docs/architecture

पाइपलाइन विकास के प्रमुख चरणों में स्वाभाविक रूप से एकीकृत होती है:

इंक्रीमेंटल अपडेट

जब कोड बदलता है, तो हम शून्य से पूरा ग्राफ़ फिर से नहीं बनाते:

# Mise à jour incrémentale (fichiers modifiés uniquement)
graphify . --update

# Puis régénérer les diagrammes
./gradlew generateKnowledgeGraphDiagram

--update`केवल संशोधित फ़ाइलों को फिर से निकालता है (SHA256 द्वारा पता लगाए गए में`graphify-out/cache/) Kotlin कोड पर, यह लगभग तुरंत हो जाता है क्योंकि tree-sitter स्थानीय रूप से काम करता है और LLM के किसी कॉल के बिना।

डॉगफ़ूडिंग : प्लगइन खुद को दस्तावेज़ीकृत करता है

PlantUML प्लगिन प्रॉम्प्ट को आरेखों में परिवर्तित करने के लिए उपलब्ध है। यह Knowledge Graph को अपनी propre codebase से दस्तावेज़ीकरण आरेखों में भी परिवर्तित कर सकता है। यह dogfooding है: प्लगिन अपनी सेवा की खपत करता है।

Gradle से संबंधित कार्य :

कार्य LLM ? विवरण

generateKnowledgeGraphDiagram

नहीं

परिवर्तित करो`graph.json`में PlantUML (निर्धारित)

generateDiagramDocs

हाँ

कुछ जनरेट करता है`.prompt`ग्राफ़ से, उन्हें LLM (डॉगफ़ूडिंग) के माध्यम से संसाधित किया जाता है

 
# Documentation déterministe (rapide, pas de LLM)
./gradlew generateKnowledgeGraphDiagram

# Documentation LLM (plus riche, consomme des tokens)
./gradlew generateDiagramDocs

क्योंकि यह निर्धारक है (और यह क्यों मायने रखता है)

पाइपलाइन का मुख्य बिंदु`generateKnowledgeGraphDiagram`:वह किसी भी LLM को नहीं बुलाता है. परिवर्तन`graph.json`PlantUML एक शुद्ध फ़ंक्शन है।

लाभ प्रभाव

पुनरुत्पादनीयता

वही`graph.json`→ एक ही आरेख. सटीक। हर बार।

शून्य लागत

कोई LLM कॉल नहीं = कोई टोकन नहीं = कोई API बिल नहीं।

शून्य विलंब

पार्स + रेंडर को लगभग 100ms लगता है, 1-5 सेकंड नहीं।

संगत CI

कोई एपीआई कुंजी आवश्यक नहीं है। चर LLM प्रतिक्रिया के कारण कोई अस्थिर परीक्षण नहीं है।

संस्करणयोग्य

Le .puml`निर्मित पाठ है। हम इसे`diff, PR में समीक्षक, Git में वर्जन।

पाइपलाइन के स्वयं के आरेख

परियोजना शासन में एकीकरण
