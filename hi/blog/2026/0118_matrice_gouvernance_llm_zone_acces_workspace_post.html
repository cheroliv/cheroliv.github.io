पढ़ने का समय : 14 minutes

महीनों तक, मैंने एजेंट शासन के नियमों को ढेर लगाया। फ़ाइलें EAGER, चेकलिस्टों LAZY, सत्र समाप्ति के छह-चरणीय प्रोटोकॉल। फिर भी, एक प्रश्न लंबित रहा: LLM यह कैसे जानता है कि यह उसके पास एक फ़ाइल के साथ काम करने का अधिकार है ?

उत्तर प्रॉम्प्ट में नहीं है। यह फ़ाइल सिस्टम में है।

यह वास्तुशिल्प विनिर्देश है जो प्रतिक्रिया को उपयोगी बनाता है — la LLM शासन मैट्रिक्स.

समस्या : प्रॉम्प्ट इंजीनियरिंग एक रेत का महल है

जब हम किसी LLM को एक फ़ाइल देते हैं, तो हम उसे सब कुछ देते हैं। सामग्री, हाँ — लेकिन साथ ही सुरक्षा उपायों की अनुपस्थिति भी। LLM को नहीं पता कि यह फ़ाइल में क्या है। एक गुप्त बात, एक अनुमानात्मक राय, या बंद स्रोत कोड। वह इसे अनुक्रमित करेगा, इसको सारांशित करना, इसको उद्धृत करना, इसको अन्य डेटा के साथ मिलाना — और संभावित रूप से इसे एक सार्वजनिक एम्बेडिंग या उपयोगकर्ता उत्तर में प्रकाशित करें।

पारंपरिक परेड, यह प्रॉम्प्ट है:

"Tu es un assistant sécurisé. Ne divulgue jamais d'informations confidentielles.
Si tu détectes un secret, ignore-le. Si tu détectes une opinion, ne la répète pas."

इस प्रॉम्प्ट में तीन समस्याएँ हैं:

  1. यह LLM की अच्छी इच्छा पर आधारित है。 एक पर्याप्त बड़ा मॉडल के लिए

जटिल बग्स को हल करना एक निर्देश को चकमा देने के लिए पर्याप्त बड़ा है 200k टोकन के संदर्भ में डूबा हुआ सुरक्षा

  1. यह संदर्भ में है, संरचनात्मक नहीं। प्रॉम्प्ट बदलें, LLM बदलें

सत्र बदलें — और नियम गायब हो जाता है।

  1. यह स्केल नहीं करता। प्रत्येक नया फ़ाइल प्रकार, प्रत्येक नया स्तर

गोपनीयता के लिए एक नया क्लॉज़ आवश्यक है। आपका प्रॉम्प्ट एक बन जाता है नियामक पाठ जो कोई भी पूरी नहीं पढ़ता।

एक प्रणाली की सुरक्षा कभी भी किसी निर्देश पर निर्भर नहीं होनी चाहिए कि हम भूल सकता है, बायपास कर सकता है, या लोड नहीं कर सकता। इसे एक पर निर्भर होना चाहिए। वह बाधा जिसे स्पष्ट रूप से चाहने के बिना नहीं लांघा जा सकता।

मेरा उत्तर: 4×4 मैट्रिक्स

समाधान जिसे मैंने अपने वर्कस्पेस में लागू किया एक ज़ोन मैट्रिक्स × पहुँच का अधिकार LLM। वह LLM से सावधान होने की मांग नहीं करती। वह देती है लापरवाही संरचनात्मक रूप से असंभव।

नियम सरल है: फ़ाइल का पथ निर्धारित करता है कि LLM इसके साथ क्या कर सकता है。 कोई मेटाडेटा बनाए रखने की आवश्यकता नहीं, फ़्रंटमैटर में कोई टैग जोड़ने की आवश्यकता नहीं, हर कमिट पर कोई मैनुअल वर्गीकरण नहीं। फ़ाइल में है`OSS/? यह सार्वजनिक है। यह है में`configuration/? वह अस्पर्शीय है।

एपिस्टेमिक वर्गीकरण (दूसरा आयाम)

स्थानिक आयाम कहता है where रूट करने के लिए। लेकिन एक दूसरा अक्ष, लंबवत : quoi राउटर. कुछ फ़ाइलें एक अधिकृत क्षेत्र में जानकारी रखती हैं जिन्हें इस तरह से पतला नहीं किया जाना चाहिए:

@startuml
skinparam backgroundColor #FEFEFE
skinparam defaultTextAlignment center
skinparam wrapWidth 240

title दबल कैस्केड — स्पेशियल फिल्टर + एपिस्टेमिक फिल्टर
start

:Le LLM rencontre un fichier;

if (Zone physique ?) then (Cercle 0-1)
  :ACCÈS BLOQUÉ\n(secret, brain dump);
  stop
elseif (Zone CSS/)
  :DROIT D'ACCÈS PRIVÉ\n→ dataset fine-tuning;
  :Filtre épistémique\nVision/Opinion;
  if (Classification ?) then (VISION)
    :Dataset privé\n→ entraînement autorisé;
  else (OPINION)
    :CONFINÉ\n→ pas d'entraînement;
  endif
elseif (Zone office/)
  :DROIT D'ACCÈS FILTRÉ\n→ accès conditionnel;
  :Filtre épistémique\nVision/Opinion/Stratégie;
  if (Classification ?) then (VISION)
    :DILUTION COMPLÈTE\n→ docs racine + blog;
  elseif (STRATÉGIE)
    :DILUTION RESTREINTE\n→ docs racine seulement;
  else (OPINION)
    :CONFINEMENT\n→ office/ uniquement;
  endif
else (Zone OSS/)
  :ACCÈS LIBRE\n→ indexation complète;
endif

stop

@enduml

एपिस्टेमिक वर्गीकरण ग्रिड, मेरे शासन के नियम 2बी में अंकित एजेंट :

| स्थिति | परिभाषा | LLM संकेत | गंतव्य | | दृष्टि | स्थिर वास्तुशास्त्र, पैटर्न परीक्षण | घोषणात्मक भाषा, सत्र/टेस्ट संदर्भ | पूर्ण तनुकरण + ब्लॉग | | रणनीति | व्यवसाय स्थिति, मूल्य निर्धारण | बाजार शब्दावली, प्रतिस्पर्धा | मूल दस्तावेज़ केवल | | OPINION | अनुमान, सत्यापित नहीं की गई परिकल्पना | परिकल्पित भाषा, अनुभूति | बंदी वृत्त 0 |

LLM इस मैट्रिक्स को कैसे उपभोग करता है

मैट्रिक्स एक ऐसा दस्तावेज़ नहीं है जिसे LLM पढ़ता है। यह एक बाध्यता अनपेक्षित एन्कोडेड संयुक्त संदर्भ वेक्टर में (EPIC 9 — चल रहा है कार्यान्वयन का).

यहाँ वह है जो LLM को प्रत्येक सत्र में मिलता है :

VECTEUR COMPOSITE DE CONTEXTE
├── RAG pgvector → OSS/ + office/Vision
│   (similarité sémantique sur contenu publiable)
├── Knowledge Graph graphify → OSS/
│   (relations exactes entre artéfacts publics)
├── Knowledge Graph privé → CSS/
│   (relations entre code closed source — jamais exporté)
├── Métadonnées de zone → chaque fichier taggé par zone physique
│   (le LLM sait s'il est dans office/ ou OSS/)
└── Historique des décisions → WORKSPACE_VISION.adoc
    (contexte temporel des arbitrages)

वास्तव में, जब LLM मुझे कहता है :

Je vais indexer le contenu de edster/ pour enrichir le knowledge graph...

ज़ोन मेटाडेटा LLM के अपने वाक्य को पूरा करने से भी पहले उत्तर देता है : edster/`है में`CSS/, स्तर 3 →सार्वजनिक ज्ञान ग्राफ़ में प्रवेश निषिद्ध है। RAG इसे नहीं देखता। ग्राफ़ इसे नहीं छูता। उपयोगकर्ता की प्रतिक्रिया नहीं वह उद्धृत नहीं करता।

स्थानिक अन्टोलॉジー जैसे एक कार्य करता हैअनुमति UnixLLM के लिए. आप एक प्रक्रिया से सावधानी बरतने के लिए नहीं कहते हैं`/etc/shadow`— आप उसे पढ़ने की अनुमति नहीं देते। वही सिद्धांत।

कार्यान्वयन : टाइप्ड ग्रैडल कार्य

मैट्रिक्स एक दर्शन नहीं है। यह कोड है। यहाँ कार्य का अनुबंध है। Gradle जो इसे लागू करता है:

abstract class ZoneAwareIndexer @Inject constructor(
    private val rootDir: DirectoryProperty,
    private val configServer: ConfigServerProperty  // → configuration/
) : DefaultTask() {

    @Input
    val zoneFilter: SetProperty<Zone> = project.objects.setProperty(Zone::class.java)

    @OutputFile
    val ragIndex: RegularFileProperty = project.objects.fileProperty()

    @TaskAction
    fun index() {
        val allowedPaths = zoneFilter.get().flatMap { it.resolve(rootDir.get()) }
        val forbiddenPaths = Zone.RESTRICTED.resolve(rootDir.get())
                            + Zone.INTIMATE.resolve(rootDir.get())
        // Le RAG ne voit jamais configuration/ ni la racine
        // CSS/ alimente un index privé, pas celui-ci
        // office/ est filtré par le classifieur Vision/Opinion
    }
}

enum class Zone {
    INTIMATE,      // Cercle 0 — racine
    RESTRICTED,    // Cercle 1 — configuration/
    EDITORIAL,     // Cercle 2 — office/
    CLOSED_SOURCE, // Cercle 3 — foundry/private/
    OPEN_SOURCE    // Cercle 3 — foundry/public/
}

परीक्षणयोग्य. आप एक परीक्षण लिख सकते हैं जो जाँचता है:

@Test
fun `le RAG n'indexe jamais configuration`() {
    val index = ZoneAwareIndexer(rootDir, configServer)
    index.zoneFilter.set(setOf(Zone.OPEN_SOURCE, Zone.EDITORIAL))
    index.index()

    assertThat(index.ragIndex).doesNotContain("configuration/")
}

@Test
fun `le code closed source est exclu du RAG public`() {
    val index = ZoneAwareIndexer(rootDir, configServer)
    index.zoneFilter.set(setOf(Zone.OPEN_SOURCE))  // OSS only

    assertThat(index.ragIndex).doesNotContain("edster")
}

380 tests, 380 PASS. प्लांटुमल-gradle के लिए — सुरक्षा का परीक्षण किया गया, अपेक्षित नहीं

क्योंकि यह एक घोषणापत्र है, सिर्फ एक विनिर्देश नहीं

यह दस्तावेज़ एक आर्किटेक्चर स्पेसिफिकेशन है क्योंकि यह परिभाषित करता है :

  • कुछआयाम(स्थानिक, ज्ञानात्मक)

  • कुछनिर्धारित नियम(ज़ोन → पहुँच का अधिकार)

  • Un कार्य अनुबंध(ग्रैडल टाइप्ड, टेस्टेबल)

  • एकसंदर्भ कार्यान्वयन(मेरा कार्यक्षेत्र)

लेकिन यह भी एकस्पष्टक्योंकि वह एक बहस पर अपना पक्ष लेता है बड़ा : LLM के डेटा तक पहुँच को कैसे नियंत्रित करें ?

उद्योग का जवाब, प्रॉम्प्ट इंजीनियरिंग + गार्ड रेल्स है
पोस्ट-हॉक वर्गीकरणकर्ता। मेरा उत्तर है: अपने फाइलों को रखें अच्छे फ़ाइलें. बाकी स्वचालित है।

Ce manifeste ne dit pas "les LLM doivent être alignés". Il dit : "l’alignement आपके सुरक्षा नियमों पर एक LLM का प्रभाव आपके सिस्टम का परिणाम है फाइलें, आपके प्रॉम्प्ट नहीं.

पक्ष/विपक्ष

यह पद्धति (स्थानिक ओन्टोलॉजी + मैट्रिक्स) क्लासिक पद्धति (प्रॉम्प्ट + गार्ड्रेल्स)

yांत्रिक — फ़ाइल सिस्टम एक्सेस को ब्लॉक करता है, LLM नहीं

घोषणात्मक — प्रॉम्प्ट LLM को सावधान रहने के लिए कहता है

Testable — Gradle टास्क अनुबंध 380+ परीक्षणों द्वारा सत्यापित है

अनपरीक्षणीय — "क्या LLM ने नियम का पालन किया?" एक खुला प्रश्न है

LLM से स्वतंत्र — मॉडल बदलें, फ़ोल्डर बरकरार रहते हैं

LLM पर निर्भर — हर मॉडल प्रॉम्प्ट को अलग-अलग तरीके से व्याख्या करता है

Scalable — नया डेटा प्रकार = नया फ़ोल्डर, कोड में कोई परिवर्तन नहीं

स्केलेबल नहीं — नया डेटा प्रकार = नया प्रॉम्प्ट खंड, नया प्रतिगमन जोखिम

Auditable — फ़ाइल सिस्टम ऑडिट ट्रेल है

ऑडिट योग्य नहीं — प्रॉम्प्ट का कोई इतिहास नहीं, कोई diff नहीं, कोई blame नहीं

बाध्यता : प्रारम्भिक संगठन अनुशासन की मांग करता है

बाधा : प्रत्येक सत्र में प्रॉम्प्ट लेखन की अनुशासन की आवश्यकता होती है

निष्कर्ष: अपने फाइलों को व्यवस्थित करें, अपने प्रॉम्प्ट्स नहीं

मैंने अभी जो LLM शासन मैट्रिक्स का वर्णन किया है, वह एक उत्पाद नहीं है। यह एकआर्किटेक्चर विनिर्देश— और इसलिए वह प्रकाशन योग्य.

जो इसे मजबूत बनाता है, वह यह है कि यह LLM से कुछ भी नहीं मांगती। वह उसे नहीं वह भरोसा नहीं करती। वह अपने संरेखण या अपनी समझ पर भरोसा नहीं करती। फ़्रेंच की, या उसकी सद्भावना। यह फ़ाइल सिस्टम पर आधारित है — सभी स्टैक में सबसे नीचे की, सबसे स्थिर, सबसे अधिक परीक्षण की गई परत।

जब मैं अपने LLM से कहता/कहती हूँ 'आप यहाँ सब कुछ इंडेक्स कर सकते हैं'`OSS/, कुछ भी नहीं `configuration/, et `office/`केवल यदि इसे विज़न के रूप में वर्गीकृत किया गया हो यह एक निर्देश नहीं है। यह एक फ़िल्टर है — कोटलिन में लागू किया गया, 380 टेस्टों द्वारा सत्यापित, LLM के डेटा को देखने से पहले निष्पादित

यह अंतर किसी से कहने में है 'इस दराज में मत देखो'। और चाबी के ड्रॉअर को बंद करें। शासन एजेंट जिसे मैं बना रहा हूँ महीने ही कुंजी हैं। मैट्रिक्स फर्नीचर की योजना है।
