दृश्य: मंगलवार 12 मई, 17:30

मैं अपने लेखों में से एक को फिर से पढ़ रहा हूँ — celui sur le Knowledge Graph comme outil de compréhension de codebase. सामग्री घनिष्ट है : नोड्स, किनारे, समुदाय, PlantUML, ऑनबोर्डिंग. एक लेख 15 मिनट की पढ़ने की तकनीक जो लगाती है`graphify-gradle`, plantuml-gradle, और ग्राफ़ टोपोलॉजी की अवधारणाएँ।

पृष्ठ के नीचे, सम्बंधित लेख मुझे सुझाव देते हैं :

  1. फ़ायरबेस कॉन्टैक्ट फ़ॉर्म (0113) पर एक लेख

  2. एक लेख ईगर/लेसी मकेनिज़्म पर (0108)

  3. एक लेख Gradle स्क्रिप्ट → प्लगिन माइग्रेशन पर (0102)

  4. Ollama Pro सब्सक्रिप्शनों के संचय पर एक लेख (0120)

इन चारों लेखों में से तीन का Knowledge Graph से कोई नहीं संबंध है। वे इसलिए वहां हैं क्योंकि वे सबसे हाल में प्रकाशित किए गए हैं — समयिक निकटता, नहीं सैमेंटिक पड़ोस

मैं टेम्पलेट देख रहा हूँ`post.thyme`</think>

यह JBake का बग नहीं है। यह सबका डिफ़ॉल्ट व्यवहार है। स्थिर साइट जनरेटर: पोस्ट की साधारण सूची तारीख के अनुसार क्रमबद्ध है। टेम्प्लेट अपने पास जो भी है, उसी से जो कर सकता है, करता है।

लेकिन यह इसे स्वीकार करने का कारण नहीं है।

निदान : तीन प्रकार के संबंध जो कोई टेम्पलेट नहीं देखता

समाधान: एक Gradle पाइपलाइन, एक गर्म LLM कॉल नहीं

पहली प्रलोभन यह होगा कि bake के समय LLM को बुलाया जाए: « के लिए इस लेख में, corpus में सबसे समान तीन लेख खोजें। इसे मत करो।

हर LLM के लिए एक कॉल`./gradlew bake`यह समय और पैसा खर्च करता है, और अपनी बिल्ड में non-determinism लाता है। LLM का उत्तर हो सकता है दो बिल्ड्स के बीच बदलें बिना सामग्री में परिवर्तन किए। आपका CI बन जाता है अपुनरावृत्त, आपके टेस्ट अस्थिर हो जाते हैं।

समाधान निर्धारित है: एक Gradle पाइपलाइन जो ग्राफ़ का पूर्व-गणना करता है समानता के और इसे में संग्रहीत करता है`graph.json`. टेम्प्लेट परिणाम पढ़ता है — वह एक गणना को कभी नहीं ट्रिगर करता है।

आर्किटेक्चर: बेकरी ग्राफ़ी आयात करती है, इंजन नहीं

यह वास्तुकला का सबसे महत्वपूर्ण बिंदु है। लुभावनी होगी। सहयोग में तार करना`engine/build.gradle.kts`: engine लागू graphify के लिए scan, bakery के लिए bake, और engine के बीच पुल बनाता है दोनों

यह एक एंटी‑पैटर्न है। Engine एक उपभोग करने वाला टर्मिनल — यह लागू करता है प्लगइन, यह व्यावसायिक तर्क लागू नहीं करता है। नियम यह है: स्वामित्व वाले प्लगइन पर प्रमाण का भार है।

  1. स्कैन (ग्राफ़ाइ) :`graphify-plugin` स्कैन करता है वर्कस्पेस. इसके

वर्तमान रूप में, यह उन्हें पहले से ही पहचानता है`xref:`बीच`.adoc`और में प्रदर्शित`graph.json`जैसे quelques edges de type`reference`.
हम इसे संपादकीय सामग्री के लिए समृद्ध करते हैं: * JBake मेटाडेटा को पार्स (:jbake-tags:, :jbake-description:) प्रत्येक का`.adoc`ब्लॉग का * गणना करता है टैग्स के सह-उपस्थितियों → किनारे`tag_cooccurrence`वजन के साथ * नामित इकाइयों को विवरणों से TF-IDF के माध्यम से निकालें → edges`entity_overlap` * सेक्शन इंजेक्ट करता है`blog_articles`में`graph.json`अस्तित्व में

// Extrait de l'enrichissement graphify pour le blog
fun enrichBlogSection(graphJson: File, blogDir: File): GraphJson {
    val articles = blogDir.listFiles { f -> f.extension == "adoc" }
        .map { parseJbakeMetadata(it) }

    val nodes = articles.map { ArticleNode(it.slug, it.title, it.tags) }
    val edges = mutableListOf<GraphEdge>()

    // Couche 1 : xref (déjà fait par scanWorkspace)

    // Couche 2 : co-occurrences de tags
    for (a in articles) {
        for (b in articles) {
            if (a.slug == b.slug) continue
            val common = a.tags.intersect(b.tags)
            if (common.isNotEmpty()) {
                edges.add(GraphEdge(
                    source = a.slug,
                    target = b.slug,
                    type = "tag_cooccurrence",
                    weight = common.size.toDouble() / (a.tags.size + b.tags.size)
                ))
            }
        }
    }

    return graphJson.copy(
        blogArticles = BlogSection(nodes, edges)
    )
}

  1. Bake (बेकरी) : के क्षण में`./gradlew bake`, `BakeryPlugin`बिस्तर

`graph.json`और यह प्रत्येक पोस्ट के लिए संबंधित लेखों को हल करता है।

// BakeryPlugin — résolution des articles connexes
fun resolveRelatedPosts(
    currentSlug: String,
    graph: GraphJson,
    maxResults: Int = 4
): List<RelatedPost> {
    val edges = graph.blogArticles.edges
        .filter { it.source == currentSlug || it.target == currentSlug }

    return edges
        .sortedByDescending { it.weight }
        .take(maxResults)
        .map { edge ->
            val relatedSlug = if (edge.source == currentSlug) edge.target else edge.source
            graph.blogArticles.nodes.first { it.slug == relatedSlug }
        }
}

NLP की शक्ति एल्गोरिदम की परिष्कार से नहीं आती, लेकिन corpus का आकार और विवरणों की गुणवत्ता। एक `:jbake-description:`अच्छी तरह लिखी गई 150 अक्षर की सामग्री में अधिक TF-IDF के लिए संकेत कि एक पूरा लेख 3000 शब्दों का।

इस सुविधा एक अधिक व्यापक परिप्रेक्ष्य: और यदि`cheroliv.com` खुद बन रहा था एक knowledge graph navigable?

लेख नोड्स हैं। टैग समुदाय हैं। xref हैं किनारों। पाठक अब एक अलग लेख नहीं पढ़ता — वह एक में नेविगेट करता है graphe de connaissance जिसका वर्तमान लेख प्रवेश बिंदु है।

होमपेज की कल्पना करें जो क्रोनोलॉजिकल सूची नहीं दिखाता अंतिम पोस्टों के, लेकिन एक कार्पस मानचित्र : ऑन्टोलॉजिकल क्लस्टर पिवोट लेख (जिनके पास सबसे अधिक किनारे हैं), पढ़ने के रास्ते सुझाए गए (« यदि आपको Graphify पर लेख पसंद आया, तो आगे पढ़ें वह Knowledge Graph को समझने के उपकरण के रूप में )

यह अब एक ब्लॉग नहीं है। यह एक अर्थसंबंधी एटलस है।

और यह विज्ञान कथा नहीं है। वह`graph.json`पहले से मौजूद है। उसके पास केवल नेविगेशन इंटरफ़ेस नहीं है।

निष्कर्ष: फ़ाइल सिस्टम जानता है कि टेम्प्लेट नहीं जानता

मंगलवार की शाम मैंने जो डिज़ाइन किया वह एक हीुरिस्टिक का प्रतिस्थापन है। आलसी (क्रमानुक्रमिक क्रम) एक वफादार प्रतिनिधित्व द्वारा मेरे कॉर्पस की संरचना (Knowledge Graph).

टेम्पलेट`post.thyme`बदलता नहीं है। जो बदलता है, वह है जो हम पहले : एक जावा सूची, जो …​ से क्रमबद्ध`date`. बाद : तीन विश्लेषण परतों से प्राप्त भारित ग्राफ़ — xrefs, co-occurrences tags के, और NLP द्वारा उभरती हुई आन्तोलजी।

लूप बंद हो गया। graphify कार्यक्षेत्र को स्कैन करता है। Bakery पढ़ता है ग्राफ़ टेम्पलेट को पोषण देता है। पाठक को सुझाव दिखाई देते हैं। प्रासंगिक। और engine — संगीत निर्देशक — वह यह भी नहीं जानता कि सभी चीज़ें मौजूद हैं।

यह वही सही वास्तुकला है। हर प्लगइन एक काम करता है। और उपभोक्ता टर्मिनल को जानने की ज़रूरत नहीं है कि कैसे।
