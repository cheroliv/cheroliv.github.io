हमारा पहला नियुक्त: डेटासेट एनोनिमाइज़र — MVP0 परीक्षण अवधि में

प्रकाशित: 01 May 2026

Table des matières
  • वह समस्या जो सभी को भागने पर मजबूर करती है
पढ़ने का समय: 12 minutes

मैं LLM को नियुक्त नहीं कर रहा हूँ। मैं एक अनामियाइज़र को नियुक्त कर रहा हूँ। RAG pgvector करने से पहले, CDA/FPA के विशेषज्ञों को फाइन-ट्यून करने से पहले, क्लाइंट वर्कस्पेस प्रोविज़न करने से पहले — किसी को डेटा के टॉयलेट साफ़ करने की ज़रूरत है। यह कर्मचारी, अनामियाइज़ेशन विशेषज्ञ है (MVP0, EPIC 2 कोडबेस-ग्रेडल)। और यह वही है जो उत्पाद को बाजार योग्य बनाता है।

ओसीडी

[]

वह समस्या जो सभी को भागने पर मजबूर करती है

हर AI स्टार्टअप जो प्रशिक्षण डेटा को संभालता है, एक ही दीवार से टकराता है :

----
----
Données brutes client (SPG, cours, évaluations)
  ├→ Noms de stagiaires en clair dans les PDF
  ├→ Emails dans les métadonnées JSON
  ├→ IP de connexion dans les logs pgvector
  ├→ Identifiants dans les nœuds Graphify
  └→ Références OF pilote dans les schémas SQL
----

परिणाम: या तो आप गंदे डेटा (PII हलूसिनेशन, GDPR अनुपालन नहीं, कानूनी जोखिम) पर RAG करते हैं, या आप कुछ नहीं करते हैं (कोई उत्पाद नहीं)। तीसरा रास्ता — हाथ से साफ़ करना — स्केलेबल नहीं है।

मेरा उत्तर: समस्या को दरकिनार न करें। L'**स्वचालित करना**.

== MVP0 : अनामनीकरणकर्ता, ट्रायल अवधि में पहला नियुक्त

MVP0 कोई फ़ीचर नहीं है। यह एक**सुविधा विशेषज्ञ**— एक कर्मचारी जो नीचा, बेवकूफ़ और क्रूर काम करता है, और जिसके बारे में कोई भी पिच डेक में बात करना नहीं चाहता।

वह क्या करता है :

[source]
----
ENTRÉE : Données brutes multi-sources
  ├→ AsciiDoc (SPG_A2SP.adoc) → noms, dates, OF pilote
  ├→ JSON (catalogue formations) → emails, téléphones
  ├→ YAML (config workspace) → tokens OAuth2
  ├→ SQL (schémas DDL) → IP, adresses
  ├→ pgvector (métadonnées embeddings) → identifiants
  ├→ ONNX (outputs classification) → noms propres
  └→ Graphify (graph.json) → nœuds avec PII

SORTIE : Datasets propres, format standardisé
  ├→ [ANONYMIZED] remplace les PII détectées
  ├→ Classification RGPD (niveau 0→4)
  ├→ Rapport d'audit (quoi a été nettoyé)
  └→ Dataset prêt pour RAG ET fine-tuning
----

यह सबसे स्पष्ट पैटर्न पहले पहचानता है (इमेल`.*@.*`, टोकन`sk-*`, `ghp_*`, IPs), फिर वह सीखता है। परीक्षण अवधि, यही है : हम यह सत्यापित करते हैं कि वह झूठे नकारात्मक को पास नहीं होने देता इससे पहले कि उसे स्थायी बनाया जाए।

== यह इस MVP को क्या अनलॉक करता है (और यह केवल अनुपालन नहीं है)

एमवीपी0 जैसे अनामीकरण RGPD टोल हाईवे से पहले नहीं है। यह खुद हाईवे है। यह क्या खोलता है:

=== वर्तमान: प्रॉम्प्ट में संवर्धित वास्तविकता

[source]
----
DONNÉES BRUTES CLIENT
    ↓
Anonymiseur MVP0 → datasets propres
    ↓
RAG pgvector (MVP1) → top-K documents similaires (filtrés, anonymisés)
    ↓
LLM (deepseek-v4-pro) → réponse augmentée, zéro PII
----

RAG गंदे डेटा में नहीं खोजता — यह एक स्थान में खोजता है**निर्माण द्वारा स्वच्छ**. यह प्रतिक्रियाओं की गुणवत्ता के लिए सब कुछ बदल देता है : LLM अपने समय को उन PII को बायपास करने में नहीं लगाता जिन्हें वह पहचानता है लेकिन जिनका उल्लेख नहीं करना चाहिए।

=== भविष्य: फ़ाइन-ट्यूनिंग स्वस्थ डेटा पर

[source]
----
MVP0 → datasets propres accumulés (session après session)
    ↓
Fine-tuning expert métier (CDA, FPA) sur données zéro PII
    ↓
Modèle fine-tuné exposé via Ollama (sans fuite de données)
----

फ़ाइन-ट्यूनिंग कच्चे डेटा पर एक संभावित कानूनी आपदा है। स्वच्छ डेटा पर, यह एक**पुनरुत्पादन योग्य विधि**. प्रत्येक ग्राहक अपने साफ़ किए गए डेटासेट्स इकट्ठा करता है, प्रत्येक ग्राहक अपने व्यावसायिक विशेषज्ञों को अपने डेटा पर फाइन-ट्यून कर सकता है — कभी भी व्यक्तिगत डेटा को उजागर नहीं किया जाता।

== क्यों यह मार्केटेबल है

यह « GDPR अनुपालन टूल » नहीं है। यह एक**पुनरावृत्तिमयी विधि जो एक सार्वभौमिक समस्या को एक संपत्ति में बदल देती है**:

1. *हर प्रशिक्षण कंपनी में गंदा डेटा होता है* — यह समस्या है
2. *कोई नहीं के पास मल्टी‑स्रोत सफ़ाई का स्वचालित पाइपलाइन है* — यह बाजार है
3. *लूप: गोपनीयकरण → RAG → फ़ाइन-ट्यूनिंग स्वामित्व वाला है* — यह बाधा है

SaaS Edster (MVP3) « एक Gradle वर्कस्पेस » नहीं बेचेगा। यह इस बंद लूप को बेचेगा। और MVP0 प्रवेश द्वार है।

== SQL प्रारूप को तृतीय मार्ग के रूप में संदर्भ

संरचित डेटा का आयात केवल एक्सचेंज फॉर्मेट नहीं है। SQL स्कीमा (DDL) ले जाता है**डोमेन इंटिटी-रिलेशन मॉडल**:

[source]
----
CREATE TABLE formation (
  id UUID PRIMARY KEY,
  titre VARCHAR NOT NULL,
  referentiel RNCP REFERENCES rncp(id),
  organisme OF REFERENCES of_pilote(id)  -- ← va être anonymisé
);
----

यह DDL, एक बार अनामिकृत (लाइन 4) के बाद, LLM के लिए संदर्भ का स्रोत बन जाता है। पाठ नहीं —**व्यवसाय मॉडल**. RAG सामग्री देता है (वेक्टर समानता), Graphify संबंध देता है (सटीक संरचना), और SQL स्कीमा देता है**डोमेन-आधारित डिज़ाइन अंतर्निहित**: सीमाबद्ध संदर्भ, समूह, मूल्य वस्तुएं। LLM व्यवसाय को समझता है क्योंकि वह अपना स्कीमा पढ़ता है।

== रोडमैप: MVP0 से SaaS तक

[source]
----
MVP0 — Anonymiseur (ce que cet article décrit)
  Sortie : datasets propres, reproductible

MVP1 — RAG pgvector (dépend de MVP0)
  Realité augmentée en prompt sur données nettoyées

MVP2 — Graphify + ONNX + SQL DDD (dépend de MVP1)
  Vecteur composite de contexte (règles + similarité + relations exactes)

MVP3 — SaaS Edster (dépend de MVP0-2)
  Provisionnement workspace client complet
----

हर MVP पिछले पर निर्भर करता है। कोई भी MVP0 के बिना जारी नहीं किया जा सकता। यही कारण है कि अनोनिमाइज़र बैकलॉग में « P0 » नहीं है — यह**MVP0**. यह पहला वाणिज्यिक वितरणीय है, और सब कुछ इसके सफल होने पर निर्भर है।

== निष्कर्ष : अदृश्य कार्य जो सब कुछ संभव बनाता है

एक सामान्य स्टार्टअप में, डेटा सफ़ाई को बाह्य रूप से बाहर कर दिया जाता है, मैन्युअल होता है, या अनदेखा किया जाता है। इस आर्किटेक्चर में, यह है**उत्पाद का कोर**. वह पहला कर्मचारी है क्योंकि उसके बिना कुछ भी काम नहीं करता :

* MVP0 के बिना → कोई कानूनी RAG नहीं (MVP1)
* MVP0 के बिना → डेटा लीक के बिना कोई फ़ाइन-ट्यूनिंग नहीं (EPIC 5)
* MVP0 के बिना → विश्वसनीय SaaS नहीं (MVP3)
* MVP0 के बिना → प्रॉम्प्ट में कोई बढ़ाई गई वास्तविकता नहीं
* MVP0 के बिना → संदर्भ का कोई तीसरा मार्ग नहीं (SQL DDD)

वह गंदा काम करता है। वह कभी भी पिच में उद्धृत नहीं किया जाएगा। लेकिन वही है जो कारखाने को चलाता है।

और यही वजह है कि हम उसे पहले नौकरी पर रखते हैं।
