हमारा पहला भर्ती: डेटासेट एनामाइज़र — MVP0 परीक्षण अवधि में

प्रकाशित: 01 May 2026

Table des matières
  • जो समस्या सबको भागने पर मजबूर करती है
पढ़ने का समय : 12 minutes

मैं एक LLM को नियुक्त नहीं करता। मैं एक अनामीकरण विशेषज्ञ को नियुक्त करता हूँ। RAG pgvector करने से पहले, fine-tuner des experts CDA/FPA करने से पहले, provisionner des workspaces clients करने से पहले — किसी को डेटा के शौचालयों को साफ़ करना होगा। यह कर्मचारी expert anonymisation (MVP0, EPIC 2 de codebase-gradle)। और यही वह है जो उत्पाद को बाजार योग्य बनाता है।

टिक

[]

जो समस्या सबको भागने पर मजबूर करती है

हर AI स्टार्टअप जो प्रशिक्षण डेटा को संभालती है, उसी दीवार से टकराती है:

----
----
Données brutes client (SPG, cours, évaluations)
  ├→ Noms de stagiaires en clair dans les PDF
  ├→ Emails dans les métadonnées JSON
  ├→ IP de connexion dans les logs pgvector
  ├→ Identifiants dans les nœuds Graphify
  └→ Références OF pilote dans les schémas SQL
----

परिणाम : या तो आप गंदे डेटा पर RAG करते हैं (PII hallucinations, GDPR गैर‑अनुपालन, कानूनी जोखिम), या आप कुछ नहीं करते हैं (कोई उत्पाद नहीं)। तीसरा मार्ग — मैन्युअल सफ़ाई — स्केलेबल नहीं है।

मेरा उत्तर : समस्या से न बचें। L'**स्वचालित करना**.

== MVP0 : अनोनिमाइज़र, ट्रायल अवधि में पहला भर्ती

MVP0 एक फ़ीचर नहीं है। यह एक**सुविधा का विशेषज्ञ**— एक कर्मचारी जो गंदा, बेवकूफ़ और बुरा काम करता है, और जिसके बारे में कोई भी पिच डेक्स में बात करना नहीं चाहता।

वह क्या करता है :

[source]
----
ENTRÉE : Données brutes multi-sources
  ├→ AsciiDoc (SPG_A2SP.adoc) → noms, dates, OF pilote
  ├→ JSON (catalogue formations) → emails, téléphones
  ├→ YAML (config workspace) → tokens OAuth2
  ├→ SQL (schémas DDL) → IP, adresses
  ├→ pgvector (métadonnées embeddings) → identifiants
  ├→ ONNX (outputs classification) → noms propres
  └→ Graphify (graph.json) → nœuds avec PII

SORTIE : Datasets propres, format standardisé
  ├→ [ANONYMIZED] remplace les PII détectées
  ├→ Classification RGPD (niveau 0→4)
  ├→ Rapport d'audit (quoi a été nettoyé)
  └→ Dataset prêt pour RAG ET fine-tuning
----

यह सबसे स्पष्ट पैटर्न पहले पहचानता है (emails`.*@.*`, टोकन`sk-*`, `ghp_*`, IPs), फिर यह सीखता है। परिक्षण अवधि, यही है: हम यह पुष्टि करते हैं कि यह झूठे नकारात्मक को पास नहीं होने देता, इससे पहले कि हम इसे स्थायी बना दें।

== यह MVP क्या अनलॉक करता है (और यह केवल अनुपालन नहीं है)

MVP0 के रूप में अनामनीकरण, GDPR टोल से पहले हाईवे नहीं है; यह हाईवे ही है। यहाँ यह खोलता है:

=== वर्तमान: प्रॉम्प्ट में संवर्धित वास्तविकता

[source]
----
DONNÉES BRUTES CLIENT
    ↓
Anonymiseur MVP0 → datasets propres
    ↓
RAG pgvector (MVP1) → top-K documents similaires (filtrés, anonymisés)
    ↓
LLM (deepseek-v4-pro) → réponse augmentée, zéro PII
----

RAG गंदे डेटा में नहीं खोजता — यह एक स्थान में खोजता है**निर्माण द्वारा**. यह सब बदल जाता है प्रतिक्रिया की गुणवत्ता के लिए: LLM वह समय बर्बाद नहीं करता है जो वह पहचानता है PII को बचने में लेकिन उल्लेख नहीं करना चाहिए।

=== भविष्य : स्वस्थ डेटा पर फाइन-ट्यूनिंग

[source]
----
MVP0 → datasets propres accumulés (session après session)
    ↓
Fine-tuning expert métier (CDA, FPA) sur données zéro PII
    ↓
Modèle fine-tuné exposé via Ollama (sans fuite de données)
----

कच्चे डेटा पर फ़ाइन-ट्यूनिंग एक संभावित कानूनी आपदा है। साफ़ डेटा पर, यह एक**पुनरावृत्ति योग्य विधि**. प्रत्येक क्लाइंट अपने साफ़ किए गए डेटासेट जमा करता है, प्रत्येक क्लाइंट अपने डेटा पर अपने व्यवसाय विशेषज्ञों को फ़ाइन-ट्यून कर सकता है — कभी भी व्यक्तिगत डेटा नहीं उजागर किए बिना.

== क्यों यह मार्केटेबल है

यह « GDPR अनुपालन उपकरण » नहीं है। यह एक**एक पुनरावृत्ति योग्य विधि जो एक सार्वभौमिक समस्या को संपत्ति में बदल देती है**:

1. *हर प्रशिक्षण कंपनी के पास गंदा डेटा होता है* — यही समस्या है
2. *कोई भी मल्टी-सोर्स क्लीनिंग का स्वचालित पाइपलाइन नहीं है* — यह बाजार है
3. *लूप : अनामिकरण → RAG → फाइन-ट्यूनिंग स्वामित्व वाला है* — यह बाधा है

एडस्टर SaaS (MVP3) « एक workspace Gradle » नहीं बेचेगा। यह बंद लूप बेचेगा। और MVP0 प्रवेश द्वार है।

== SQL फ़ॉर्मेट को संदर्भ के तीसरे मार्ग के रूप में

स्ट्रक्चर्ड डेटा इम्पोर्ट केवल एक आदान-प्रदान प्रारूप नहीं है। SQL स्कीमा (DDL) ले जाता है**डोमेन एंटिटी-रिलेशनशिप मॉडल**(Empty output)

[source]
----
CREATE TABLE formation (
  id UUID PRIMARY KEY,
  titre VARCHAR NOT NULL,
  referentiel RNCP REFERENCES rncp(id),
  organisme OF REFERENCES of_pilote(id)  -- ← va être anonymisé
);
----

DDL, एक बार अनामिकृत (पंक्ति 4) होने पर, LLM के लिए संदर्भ का स्रोत बन जाता है। न पाठ —**व्यवसाय मॉडल**. RAG सामग्री (वेक्टर समानता) प्रदान करता है, Graphify संबंध (सटीक संरचना) प्रदान करता है, और SQL स्कीमा देता है**डोमेन-ड्रिवन डिज़ाइन अंतर्निहित**: bounded contexts, aggregates, value objects. LLM व्यवसाय को समझता है क्योंकि यह अपनी स्कीमा पढ़ता है।

== रोडमैप : MVP0 से SaaS तक

[source]
----
MVP0 — Anonymiseur (ce que cet article décrit)
  Sortie : datasets propres, reproductible

MVP1 — RAG pgvector (dépend de MVP0)
  Realité augmentée en prompt sur données nettoyées

MVP2 — Graphify + ONNX + SQL DDD (dépend de MVP1)
  Vecteur composite de contexte (règles + similarité + relations exactes)

MVP3 — SaaS Edster (dépend de MVP0-2)
  Provisionnement workspace client complet
----

हर MVP पिछले MVP पर निर्भर करता है। कोई भी MVP0 के बिना डिलीवर नहीं किया जा सकता। यह वह कारण है कि अनामाइज़र बैकलॉग में « P0 » नहीं है — यह**MVP0**. यह पहला वाणिज्यिक डिलिवरेबल है, और सब कुछ उसकी सफलता पर निर्भर करता है।

== निष्कर्ष : अदृश्य कार्य जो सब कुछ संभव बनाता है

एक पारंपरिक स्टार्टअप में, डेटा क्लीनिंग आउटसोर्स्ड, मैनुअल है, या अनदेखा की जाती है। इस आर्किटेक्चर में, यह**उत्पाद का हृदय**. वह पहला कर्मचारी है क्योंकि बिना उसके कुछ भी काम नहीं करता :

* MVP0 के बिना → कोई कानूनी RAG नहीं (MVP1)
* MVP0 के बिना → डेटा लीक के बिना फाइन-ट्यूनिंग नहीं (EPIC 5)
* MVP0 के बिना → कोई विश्वसनीय SaaS नहीं (MVP3)
* MVP0 के बिना → प्रॉम्प्ट में कोई संवर्धित वास्तविकता नहीं
* MVP0 के बिना → तीसरा संदर्भ पथ नहीं (SQL DDD)

वह गंदा काम करता है। वह कभी भी पिच में उद्धृत नहीं किया जाएगा। लेकिन यही वह है जो कारखाने को चलाता है।

और यही कारण है कि हम पहले इसे काम पर रखते हैं।
