现代建筑的虚假两难

在构建具有静态前端的现代应用时，我们常常会面临一个二元选择：

  • 全力押注 Backend-as-a-Service 解决方案（Supabase、Firebase）—— 简单但受限

  • 构建一个完整的后端(Spring Boot, Node.js) - 强大但复杂

这种选择是一个伪两难。混合架构提出了第三条道路：在每种技术最擅长的地方使用它。

建筑愿景

传统架构：单体式

在这种方法中，即使是最简单的操作（阅读文章、创建评论）也必须经过你的后端。你从第一天起就要承担复杂性的成本。

BaaS 架构：全部委托

相反，把所有工作都交给 BaaS 起初很吸引人，但一旦业务逻辑变得复杂，很快就会显露出局限。

混合架构：职责分离

混合架构根据操作的复杂性和性质清晰地划分了职责。

设计原则

原则1：简单起步，智能演进

如果你不需要，就不要构建 Spring Boot。从 Supabase 开始，当复杂度证明有必要时再加入 Spring Boot。

原则2：按操作性质分离

原则3：单一事实来源

通过共享同一个 PostgreSQL 实例，Supabase 和 Spring Boot 无需复杂的同步即可处理相同的数据。

流编排

流程 1：集中式身份验证

关键点：单一认证流程，单一 JWT，随处可用。

Flux 2：复杂业务流程的编排

Spring Boot 带来了什么: 可靠编排涉及多个系统并具有事务保证的复杂流程。

流程 3：计划作业与同步

Spring Boot 带来了什么: 可靠的计划任务，具备状态管理、自动重试和保证执行。

应牢记的原则

何时选择这种架构？

✅ 这种架构非常适合以下情况：

  • 您想快速启动（MVP 几天即可完成，而不是几个月）

  • 您预见到业务复杂性的增长

  • 您希望最大限度地降低初始成本

  • 您喜欢 PostgreSQL，并希望拥有单一事实来源

  • 您欣赏 Kotlin 和协程在业务代码中的应用

  • 您希望避免完全的vendor lock-in

❌ 此架构不适用于以下情况：

  • 你的项目很简单，而且会一直如此（个人博客 → 100% Supabase 就够了）

  • 您已经拥有一个成熟且您熟练掌握的后端技术栈

  • 您更喜欢传统的单体架构

  • 您需要 .NET、Python 或其他后端语言

应避免的反模式

❌ 不要做：

  • 在 Supabase 和 Spring Boot 之间复制数据

  • 创建两个独立的 PostgreSQL 数据库

  • 自行编写身份验证

  • 使用 Spring Boot 进行简单的 CRUD

  • 从一开始就过度架构

  • 忽略 Supabase 的行级安全

✅ 而应改为：

  • 共享单个 PostgreSQL 数据库

  • 让 Supabase 处理身份验证

  • 仅将 Spring Boot 用于复杂性

  • 从简单开始，逐步演进

  • 发挥每种技术的优势

  • 使用 RLS 在数据库层面保障安全

总结：现代建筑范式

Supabase + Spring Boot 的混合架构代表了一种新范式：建筑专业化.

基本原则：不要构建已经以服务形式存在的东西。专注于让你的应用与众不同的地方。

80/20法则

在大多数应用中：

  • 80% 的操作是标准 CRUD → Supabase

  • 20%的操作需要业务逻辑 → Spring Boot

这一自然法则证明了混合架构的合理性。

最终结论

混合架构并非技术上的妥协，而是一种战略决策。

它让您能够：

  • ✅ 使用可用的 MVP 快速启动

  • ✅ 无需大量投资即可验证您的市场

  • ✅ 当复杂性需要时逐步演进

  • ✅ 在每个阶段掌控您的成本

  • ✅ 发挥每种技术的最大优势

  • ✅ 避免过早的过度工程

  • ✅ 为未来保留灵活性

它代表：

  • 🎯实用主义：她所擅长的每一项技术

  • 🚀速度：最短上市时间

  • 💰经济：成本与价值保持一致

  • 🔮可扩展性：随您成长的架构
