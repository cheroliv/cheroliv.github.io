您的代码库在增长。模块之间的依赖关系在增加。架构文档在还未写完之前就已经过时。如果您的 Gradle 构建能够 automatiquement 根据实际代码结构生成最新的图表，那将会怎样？这正是 Graphify + PlantUML Gradle 插件 pipeline 所实现的：graphify . --no-viz`提取 Knowledge Graph，./gradlew generateKnowledgeGraphDiagram`它转换为PlantUML图。零 LLM，零手册，100% 确定性。

问题：图表总是落后于代码

任何超过几千行的项目都会遇到这种综合征：

  1. 在项目开始时绘制一个架构图

  2. 代码在演变，依赖关系在变化

  3. 图表变成了装饰性的谎言

  4. 没有人愿意更新它，因为这很麻烦。

  5. 新来的人以此为依据并犯错

@startuml
skinparam backgroundColor #FEFEFE
skinparam ActivityBackgroundColor #FDEDEC
skinparam ActivityDiamondBackgroundColor #FFF3CD

start

:Diagramme d'architecture créé\n(manuellement, à la main);

:Le code évolue\n(nouvelles classes, nouvelles dépendances);

:Diagramme obsolète\n(ne reflète plus le code);

if (Qui met à jour ?) then (Personne)
    :Documentation mensongère;
    note right: Les nouveaux développeurs\nse basent dessus... et font des erreurs
else (Quelqu'un)
    :Mise à jour manuelle\n(2-3 heures de travail);
    note right: Déjà obsolète\nà la prochaine PR
endif

stop

@enduml

问题不是 是否需要图表 ? — 毫无疑问，大家都知道答案是肯定的。问题：谁在保持它们最新？

答案：没有人。除非是自动的。

解决方案：确定性 Knowledge Graph → PlantUML 管道

原则很简单：不是手动绘制图表，而是我们生成自代码的实际结构。

@startuml
skinparam backgroundColor #FEFEFE
skinparam componentStyle rectangle

actor Développeur
component "Graphify\n(pip install graphifyy)" as Graphify
collections "graphify-out/graph.json
(知识图谱)" as KGJSON
component "PlantUML Gradle 插件
(generateKnowledgeGraphDiagram)" as Plugin
component "知识图谱解析器" as Parser
component "知识图谱渲染器" as Renderer
component "PlantumlService\n(验证 + 渲染 PNG)" as PS
collections "diagrams/knowledge-graph/\n(.puml + .png)" as Output

Développeur --> Graphify : graphify . --no-viz
Graphify --> KGJSON : extrait la structure\ndu code source
Développeur --> Plugin : ./gradlew generateKnowledgeGraphDiagram
Plugin --> Parser : parse(graph.json)
Parser --> Plugin : KnowledgeGraph\n(noeuds + arêtes + communautés)
Plugin --> Renderer : render(graph, filters)
Renderer --> Plugin : code PlantUML\ndéterministe
Plugin --> PS : validateSyntax + generateImage
PS --> Output : .puml + .png

note bottom of Plugin
  Pipeline DÉTERMINISTE
  Aucun appel LLM
  Résultat reproductible
end note

@enduml

只有两个命令。

# Étape 1 : extraire le Knowledge Graph
graphify . --no-viz

# Étape 2 : générer les diagrammes PlantUML
./gradlew generateKnowledgeGraphDiagram

结果？文件`.puml` et .png`在`diagrams/knowledge-graph/, 在 Git 中进行版本控制，始终与代码保持同步。

步骤 1：安装 Graphify 并提取 Knowledge Graph

安装

Graphify 是一个 Python 工具，它分析您的代码库并构建一个结构化的知识图谱：

# Méthode recommandée
uv tool install graphifyy && graphify install --platform opencode

# Alternative avec pip
pip install graphifyy && graphify install --platform opencode

配置排除项

创建一个文件`.graphifyignore`在项目根目录下，以排除不属于业务逻辑的文件：

# Secrets — JAMAIS dans le graphe
*-context.yml
*.env

# Fichiers générés
build/
.gradle/

# Tests fonctionnels
src/functionalTest/

提取知识图谱

graphify . --no-viz

标志`--no-viz`跳过HTML生成（在Gradle流水线中不必要）。结果是一个文件`graphify-out/graph.json`包含 :

  • 节点: 类、函数、文件 — 它们的类型和社区

  • 边缘: 节点之间的关系（从代码中提取，由LLM推断）

  • 社区: 自动分组的关联节点

结构示例`graph.json`
{
  "nodes": [
    {"id": "0", "label": "LlmService", "file_type": "code", "community": 0},
    {"id": "1", "label": "ApiKeyPool", "file_type": "code", "community": 0},
    {"id": "2", "label": "PlantumlService", "file_type": "code", "community": 1}
  ],
  "links": [
    {"source": "1", "target": "0", "relation": "uses", "confidence": "EXTRACTED", "weight": 0.9},
    {"source": "0", "target": "2", "relation": "calls", "confidence": "INFERRED", "weight": 0.7}
  ]
}

源代码 (.kt, .java) 由 tree-sitter 在本地进行分析，不可上诉的LLM. 只有文档文件 (.adoc, .md) 需要进行一次LLM调用以进行语义提取。 因此`--update`在Kotlin代码上编译几乎是即时的。

步骤 2：Gradle插件将Knowledge Graph转换为PlantUML

流水线架构

插件`com.cheroliv.plantuml`包含一个任务`generateKnowledgeGraphDiagram`谁转换`graph.json`以 PlantUML 图表的方式完全决定论的 :

@startuml
skinparam backgroundColor #FEFEFE

participant "Gradle" as G
participant "GenerateKnowledgeGraphDiagramTask" as Task
participant "KnowledgeGraphParser" as Parser
participant "知识图渲染器" as Renderer
participant "PlantUML 服务" as PS

collections "graphify-out/graph.json" as JSON

G -> Task : execute
Task -> JSON : read
Task -> Parser : parse(graph.json)
Parser --> Task : KnowledgeGraph\n(noeuds + arêtes + communautés)
Task -> Renderer : render(graph, filters)
Renderer --> Task : code PlantUML\n(déterministe)
Task -> PS : validateSyntax(plantumlCode)
alt syntaxe valide
    Task -> PS : generateImage → .png
else syntaxe invalide
    Task -> Task : save .puml avec warning
end

@enduml

内部组件

组件 角色

KnowledgeGraphParser

解析`graph.json`— 支持 3 种格式： 原生 graphify (nodes+links), 遗产 (communities), 平坦。 解析数字 ID 为标签。

KnowledgeGraphRenderer

确定性地转换一个`KnowledgeGraph`在PlantUML代码中。按类型分组，社区以包形式，自动图例。

GenerateKnowledgeGraphDiagramTask

负责编排：parse → render → validate → PNG 的 Gradle 任务。可通过 Gradle 属性进行配置。

kgmodels.kt

数据模型 :`KnowledgeGraph`, KnowledgeGraphNode, KnowledgeGraphEdge, KnowledgeGraphCommunity, EdgeType。

PlantumlService

语法验证 + PNG 渲染（由插件的所有任务重复使用）。

渲染规则

渲染器应用确定的视觉惯例：

边缘类型 PlantUML 表示法 意义

提取的

-→(实线, 黑色)

从源代码中提取的关系（确定性）

推断

..>(虚线)

由LLM推断的关系（置信度得分）

含糊的

--x(红色虚线)

模糊的关系（待验证）

社区以带有自动调色板的 PlantUML 包的形式呈现。

步骤 3：日常使用

完整图表

# Générer le diagramme du Knowledge Graph complet
./gradlew generateKnowledgeGraphDiagram

输出：diagrams/knowledge-graph/knowledge-graph-full.puml + .png

按社区筛选

# Une seule communauté
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.community=community_0

# Limiter le nombre de noeuds (lisibilité)
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.community=community_0 \
  -Pplantuml.kg.maxNodes=15

按边类型过滤

# Uniquement les relations certaines (EXTRACTED)
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.edgeTypes=EXTRACTED

# Relations certaines + inférées
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.edgeTypes=EXTRACTED,INFERRED

按节点类型和置信度过滤

# Uniquement les classes de code
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.nodeTypes=code

# Seuil de confiance minimum (pour les INFERRED)
./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.minConfidence=0.7

自定义输出目录

./gradlew generateKnowledgeGraphDiagram \
  -Pplantuml.kg.outputDir=docs/architecture

属性完整参考

属性 默认 描述

plantuml.kg.community

(所有)

按名称过滤社区 (子字符串匹配)

plantuml.kg.edgeTypes

(全部)

以逗号分隔的边类型：EXTRACTED, INFERRED, AMBIGUOUS

plantuml.kg.minConfidence

0.0

边的最小置信度阈值

plantuml.kg.maxNodes

(无限)

要显示的最大节点数

plantuml.kg.nodeTypes

(所有)

以逗号分隔的节点类型（例如`class`, code)

plantuml.kg.outputDir

diagrams/knowledge-graph

输出目录用于文件`.puml` et .png

增量更新

当代码发生变化时，我们不会从零开始重建整个图：

# Mise à jour incrémentale (fichiers modifiés uniquement)
graphify . --update

# Puis régénérer les diagrammes
./gradlew generateKnowledgeGraphDiagram

--update`仅重新提取已修改的文件（由 SHA256 检测到的`graphify-out/cache/). 对于 Kotlin 代码，几乎是即时的，因为 tree-sitter 在本地工作，没有 LLM 调用。

狗粮：插件自行记录

PlantUML 插件可以将提示转换为图表。它还可以将其 propre 代码库的 Knowledge Graph 转换为文档图表。这是 dogfooding：插件使用其自身的服务。

@startuml
skinparam backgroundColor #FEFEFE
skinparam componentStyle rectangle

package "普通管道\n(用户 → 图表)" as normal {
    [Fichier .prompt] as prompt
    [LlmService\n+ ApiKeyPool] as llm1
    [ProcessPlantumlPromptsTask] as task1
    [Diagramme PNG] as out1

    prompt --> task1
    task1 --> llm1
    llm1 --> out1
}

package "Pipeline Knowledge Graph
(确定的，没有LLM)" as kg {
    [graphify-out/graph.json] as kgjson
    [KnowledgeGraphParser] as parser
    [KnowledgeGraphRenderer] as renderer
    [PlantumlService] as ps
    [Diagramme PNG\n(documentation du plugin)] as out2

    kgjson --> parser
    parser --> renderer
    renderer --> ps
    ps --> out2
}

package "管道自用\n(LLM → 插件文档)" as dogfood {
    [GraphifyPromptAdapter] as gpa
    [Fichiers .prompt\nauto-générés] as auto_prompt
    [LlmService\n+ ApiKeyPool] as llm2
    [ProcessPlantumlPromptsTask] as task2
    [Diagramme PNG\n(documentation LLM)] as out3

    kgjson --> gpa
    gpa --> auto_prompt
    auto_prompt --> task2
    task2 --> llm2
    llm2 --> out3
}

note "相同的 LlmService，相同的 ApiKeyPool，
相同的 PlantumlService
— 零重复" as N

@enduml

关联的 Gradle 任务：

任务 LLM ? 描述

generateKnowledgeGraphDiagram

不

转换`graph.json`在 PlantUML (确定性的)

generateDiagramDocs

是

生成一些`.prompt`从图中，通过 LLM 处理它们（dogfooding）

 
# Documentation déterministe (rapide, pas de LLM)
./gradlew generateKnowledgeGraphDiagram

# Documentation LLM (plus riche, consomme des tokens)
./gradlew generateDiagramDocs

为什么它是确定的（以及为什么这很重要）

流水线的关键点`generateKnowledgeGraphDiagram`:他不调用任何LLM. 转换`graph.json`→ PlantUML 是一个纯函数。

@startuml
skinparam backgroundColor #FEFEFE
skinparam componentStyle rectangle

rectangle "确定性流水线
(generateKnowledgeGraphDiagram)" as det {
    [graph.json] as json
    [KnowledgeGraphParser] as parser
    [KnowledgeGraphRenderer] as renderer
    [PlantUML code] as puml

    json --> parser : parse
    parser --> renderer : KnowledgeGraph
    renderer --> puml : render (fonction pure)
}

rectangle "流水线LLM
(processPlantumlPrompts)" as llm {
    [.prompt] as prompt
    [LlmService] as llmSvc
    [ChatModel] as model
    [PlantUML code] as puml2

    prompt --> llmSvc
    llmSvc --> model : API call
    model --> puml2 : réponse non-déterministe
}

note bottom of det
  Même entrée → même sortie
  Pas de latence réseau
  Pas de coût en tokens
  Reproductible en CI
end note

note bottom of llm
  Même entrée → sortie variable
  Latence réseau (1-5s)
  Coût en tokens
  Nécessite une clave API
end note

@enduml

具体的好处：

优势 影响

可重复性

即使`graph.json`→ 同一张图。的确。每次。

零成本

没有 LLM 调用 = 没有 token = 没有 API 账单。

零延迟

Parse + render 需要约 100 毫秒，而不是 1-5 秒。

兼容持续集成

不需要 API 密钥。不会因 LLM 响应可变而出现不稳定的测试。

可版本化

Le .puml`生成的文本。我们可以它`diff, PR中的审阅者，在 Git 中进行版本控制。

陷阱与缓解措施

陷阱 描述 减缓

图形过于密集

一个大型项目会产生数百个不可读的节点

使用`-Pplantuml.kg.maxNodes=30`并按社区筛选

排除范围过大

文件过多在`.graphifyignore`减少图的价值

首先仅排除 credentials 和 build

箭头方向

推断的边可能具有不明确的方向

按…​过滤`-Pplantuml.kg.edgeTypes=EXTRACTED`仅限于确定的关系

过时的图形

代码发生了变化，但图未被重建

使用`graphify . --update`经常或 git 钩子`graphify hook install`

成本已更新

增量更新几乎免费 ( tree-sitter local )

只有文档 (.adoc) 消耗 LLM tokens
