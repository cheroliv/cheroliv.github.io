问题：一个繁忙的终端

每个开发者都遇到过这种情况：

$ ./gradlew build
> Building...

终端已被锁定。您无法再输入任何命令。您需要查看一个文件，启动一个`git status`, 或者检查一个被占用的端口。

@startuml
skinparam backgroundColor #FEFEFE

actor Développeur as dev
participant "终端" as term
participant "Gradle\n( 进程 )" as gradle

dev -> term : ./gradlew build
term -> gradle : Lance le build
gradle -> term : Occupe le terminal\n(pas de prompt)
dev -> term : veut taper une commande
term --> dev : ❌ Terminal bloqué

note right of dev
  Le développeur est
  paralysé pendant
  toute la durée du build
end note
@enduml

大多数开发者会打开一个新终端。但有一种更优雅、更快速且原生的解决方案：作业管理。

必不可少的三个命令

Ctrl+Z — 暂停 (SIGTSTP)

`Ctrl+Z`发送信号`SIGTSTP`到前台进程。 该进程是已暂停— 未被杀死 — 终端恢复了提示符。

$ ./gradlew build
> Building...
^Z
[1]+  Stoppé    ./gradlew build
$

括号中的数字`[1]`是工作编号. Le `+`表示默认作业。

fg — 切换到前台

`fg`将暂停的作业调到前台。进程正好在它停止的地方继续执行。

$ fg
./gradlew build
> Building... (reprend où il en était)

使用特定的作业编号：

$ fg %2

bg — 在后台恢复

`bg`恢复进程 sans 不阻塞终端。 适用于长时间的构建。

$ bg
[1]+ ./gradlew build &
$

Le `&`在最后表示进程在后台运行。

jobs — 列出 shell 作业

$ jobs
[1]-  Stoppé    vim README.md
[2]+  En cours   ./gradlew build
@startuml
skinparam backgroundColor #FEFEFE
skinparam defaultFontName sans-serif

state "前景\n(终端被阻塞)" as fg #LightCoral
state "已暂停
(Ctrl+Z)" as stopped #LightYellow
state "背景\n(bg)" as bg_ #LightGreen

[*] --> fg : Lance une commande
fg --> stopped : Ctrl+Z\n(SIGTSTP)
stopped --> fg : fg\nreprend en avant-plan
stopped --> bg_ : bg\nreprend en arrière-plan
bg_ --> fg : fg\nramène en avant-plan
fg --> [*] : Commande terminée

note right of stopped
  Le processus est figé
  mais _pas_ tué
end note

note left of bg_
  Le terminal est libre
  le build continue
end note
@enduml

高级技巧

fg 与最新的工作和交替一起

fg`无参数返回被标记的作业+(最新的). 但您也可以使用%-`用于定位上一个作业：

$ vim file1.txt
^Z
[1]+  Stoppé    vim file1.txt

$ vim file2.txt
^Z
[2]+  Stoppé    vim file2.txt

$ fg      # ramène job [2] (le plus récent)
$ fg %-   # ramène job [1] (le précédent)

妥善地结束作业

$ jobs
[1]-  Stoppé    vim config.yml
[2]+  Stoppé    ./gradlew test

$ kill %2       # envoie SIGTERM au job 2
$ kill -9 %1    # envoie SIGKILL au job 1 (force)

désown : détacher du shell

disown`从 shell 的作业表中移除一个作业。进程继续运行，但不能再被带回`fg:

$ ./gradlew build &
[1] 12345

$ disown %1
# Le processus continue mais n'est plus lié au shell
# Ça survives à la fermeture du terminal

将 nohup 与长时间运行的进程结合使用

为了让进程在终端关闭后仍然存活：

$ nohup ./gradlew build &
[1] 12345
$ disown %1
# Le build continue même si vous fermez le terminal

陷阱和常见错误

混淆 Ctrl+Z 和 `Ctrl+C

这是最常见的错误。`Ctrl+C`杀死该进程。`Ctrl+Z`暂停它。 如果你按下`Ctrl+C`作为反射，所有状态都丢失了 — 打开的文件、LLM 会话、进行中的构建。

  card "没有损失" as z3
}

  card "进程已完成" as c1
  card "永久丢失的状态" as c2
  card "无法返回" as c3
}

  Pause → Reprendre
end note

作业是 shell 本地的

jobs, fg et `bg`仅在启动这些进程的shell中起作用。 如果您打开一个新的终端，您将看不到另一个作业。

# Terminal 1
$ vim file.txt
^Z
[1]+  Stoppé    vim file.txt

# Terminal 2 (nouveau)
$ jobs
# (rien — les jobs sont locaux au shell)

要查看系统范围的进程，请使用`ps` ou htop:

ps aux | grep vim

作业不会在 shell 关闭后存活

如果您关闭终端，所有挂起的或在后台运行的作业都将被销毁。为了让进程继续运行，请使用`nohup` + disown:

$ nohup ./gradlew build &
[1] 12345
$ disown %1
# Fermer le terminal → le build continue

交互式进程和 fg

一些交互式程序在一个…之后表现不佳`Ctrl+Z`+fg. 虽然罕见，但会发生：

  • 某些使用信号的程序 (vim, htop, less 处理得很好`Ctrl+Z`)

  • 长时间运行的网络程序（ssh, opencode）通常能够正确恢复

  • 修改终端的程序（ncurses）有时可能会使终端处于意外状态。

如果终端在一个…​之后损坏`fg`, 请输入 :

reset

为什么fg被低估了

大多数现代开发者发现`fg`迟到，甚至可能永不。一些原因：

  1. IDE 隐藏了终端: VS Code 提供了内置终端，但多个选项卡会导致`fg`表面上看起来不那么必要

  2. 图形工具替代 CLI: 文件管理器，系统监视器，图形化 Git 客户端

  3. tmux 和 screen: 这些多路复用器以不同的方式解决相同的问题，但`fg`更简单且始终可用

然而,`fg`是 :

  1. 普遍: 存在于所有 POSIX shell 中（bash, zsh, fish…​）

  2. 无依赖: 不需要安装 tmux 或 screen

  3. 快照: 两次打击 (Ctrl+Z`然后`fg) 暂停并恢复

  4. 上下文保存者: 进程状态完好

3

带有核心转储退出

18

SIGTSTP

Ctrl+Z

交互式停止 — 暂停进程

19

SIGCONT

fg/bg

继续 — 恢复一个暂停的进程

@enduml

结论

`fg`这并不是一个晦涩的技巧 — — 而是 Unix shell 的一个基本机制，自 70 年代起就已存在。多数开发者对此视而不见，反映了我们这个时代的特点：IDE 和复用器让我们远离了基础。

但当你在 SSH 服务器上、在最小化终端中，或者只是在使用时`opencode`而且 LLM 正在全力工作 —Ctrl+Z, fg, bg, `jobs`是你们最好的朋友。

_ Ctrl+Z 挂起，fg 恢复。这是终端的暂停/播放。 _
