我在查看模板`post.thyme` :

这不是JBake的错误。这是一切的默认行为。 静态网站生成器：文章列表是平铺的，按日期排序。 模板尽其所能地使用它所拥有的。

但这不是接受它的理由。

我的文章语料库 — 23篇文章，4个月 — 具有丰富的结构 时间顺序模板完全覆盖：

解决方案：Gradle 流水线，而非热调用 LLM

第一个诱惑会是在 bake 时调用一个 LLM：« Pour 这篇文章，在语料库中找到三篇最相似的文章。 不要那样做。

每次一个LLM调用`./gradlew bake`花费时间、金钱，并 在你的构建中引入了非确定性。LLM 的响应可能 在两个构建之间切换而内容未改变。您的 CI 变得 不可重复，您的测试变得不稳定。

解决方案是确定的：一个预先计算图的 Gradle 管道 相似度并将其存储在`graph.json`. 模板读取结果 — 它永不触发计算。

架构：Bakery 导入 Graphify，而不是 Engine

这是最重要的建筑点。诱惑将是 在…​中布线合作`engine/build.gradle.kts`: 引擎 应用 graphify 用于扫描，bakery 用于烘焙，而 engine 在其之间搭建桥梁 两者

这是一种反模式。引擎是一个*消费终端*——它应用 对于插件，它不实现业务逻辑。规则是： 举证责任在于专有插件。

正确的架构 — Bakery 导入 Graphify

流水线：扫描 → 图谱 → 模板

这是完整的三步流程：

  1. 扫描 (图形化) :`graphify-plugin`扫描工作区。在其

当前形式，它已经检测到这些`xref:`之间`.adoc`和其 展示在`graph.json`就像某种类型的边缘`reference`。
我们对其进行丰富，用于编辑内容： * 解析 JBake 元数据 (:jbake-tags:, :jbake-description:) 每个的`.adoc`博客的 * 计算标签的共现 → edges`tag_cooccurrence`带有重量 * 通过 TF-IDF 从描述中提取命名实体 → 边`entity_overlap` * 注入一个章节`blog_articles`在`graph.json`现有的

// Extrait de l'enrichissement graphify pour le blog
fun enrichBlogSection(graphJson: File, blogDir: File): GraphJson {
    val articles = blogDir.listFiles { f -> f.extension == "adoc" }
        .map { parseJbakeMetadata(it) }

    val nodes = articles.map { ArticleNode(it.slug, it.title, it.tags) }
    val edges = mutableListOf<GraphEdge>()

    // Couche 1 : xref (déjà fait par scanWorkspace)

    // Couche 2 : co-occurrences de tags
    for (a in articles) {
        for (b in articles) {
            if (a.slug == b.slug) continue
            val common = a.tags.intersect(b.tags)
            if (common.isNotEmpty()) {
                edges.add(GraphEdge(
                    source = a.slug,
                    target = b.slug,
                    type = "tag_cooccurrence",
                    weight = common.size.toDouble() / (a.tags.size + b.tags.size)
                ))
            }
        }
    }

    return graphJson.copy(
        blogArticles = BlogSection(nodes, edges)
    )
}

  1. Bake (bakery) : 此时的`./gradlew bake`, `BakeryPlugin`床

`graph.json`并解决每个帖子的相关文章。

// BakeryPlugin — résolution des articles connexes
fun resolveRelatedPosts(
    currentSlug: String,
    graph: GraphJson,
    maxResults: Int = 4
): List<RelatedPost> {
    val edges = graph.blogArticles.edges
        .filter { it.source == currentSlug || it.target == currentSlug }

    return edges
        .sortedByDescending { it.weight }
        .take(maxResults)
        .map { edge ->
            val relatedSlug = if (edge.source == currentSlug) edge.target else edge.source
            graph.blogArticles.nodes.first { it.slug == relatedSlug }
        }
}

后备 chronological

Si `graph.json`不存在（本地构建无预扫描，第一 部署，CI 尚未集成 graphify 扫描)，模板 必须优雅降级：

fun resolveRelatedPosts(currentSlug: String, graph: GraphJson?): List<RelatedPost> {
    if (graph != null && graph.blogArticles != null) {
        return resolveFromGraph(currentSlug, graph)
    }
    // Fallback chronologique — même comportement qu'aujourd'hui
    logger.warn("[bakery] graph.json absent — fallback chronologique")
    return resolveFromChronology(currentSlug)
}

默认行为与当前行为相同。该 推荐引擎是一种*渐进式改进* —— 不是一 破坏性更改。

新兴本体论：当文章在互不认识的情况下聚集

最有趣的一层是第三层：新兴的本体论。 不被引用的文章，标签也不相同的，但 谁在不知情的情况下谈论同一件事

让我们举一个具体的例子。我的语料库中的三篇文章：

  1. 0119 — 基准测试 DGX Spark 与云订阅 LLM

  2. 0121 — Gradle插件 控制两个Ollama Pro实例

  3. 0122 — 效率比率 27倍 45倍 舰队 AI 专家

这三篇文章之间没有 aucun xref。 它们的标签没有 se 仅重叠到 20%（'ollama'、'llm' 常见）。但一个轻量级的 NLP 在描述中显现出一个明显的簇："成本"，"订阅"， 云 », « GPU », « API 密钥 », « Ollama Pro », « 效率 », « 比率

它们形成一个本体论聚类： LLM自托管经济 vs cloud. 此集群在任何地方都未被声明。 它从语料库中出现。

NLP 故意保持轻量 — TF-IDF + 余弦相似度 在 描述。不需要 BERT，也不需要语言模型。 语料库包含23篇文章，相似度矩阵可以容纳于 50KB的JSON文件。

自然语言处理的力量并不来自于算法的复杂性， 但是*语料库的大小*和*描述的质量*。一个 `:jbake-description:`写得好的150个字符包含更多的 为 TF-IDF 发出信号，表示这是一篇完整的 3000 字文章。

DAG合同：谁对谁重要

这是建筑学科见效的点。 DAG N0→N3 定义在`engine/build.gradle.kts`给出一个简单的规则： 没有任何项目对一个更高级别的项目而言是重要的

✅ 技术 OK，但 概念上错误 — 合作是在 bakery 内部的

引擎应用面包店。面包店应用图形化。这就是全部。如果有一天 我想要添加向量存储代码库 (N1) 用于研究。 跨语料语义，面包房也导入它。引擎不变。

模式是：插件 N2 是其自身依赖的中心。 Engine N3 不是一个 hub — 它是一个应用 hubs 的终端。

视角：博客作为公共知识图谱

此功能打开了一个更广阔的视角：假如`cheroliv.com` 它自己是否变成了一个*可导航的知识图谱*？

文章是节点。标签是社区。xref 是 边缘。读者不再阅读孤立的文章——他正在一个 知识图谱 其中当前条目是入口点。

想象一个主页，它显示的不是按时间顺序的列表。 最新的帖子，但是一个 语料库地图 ： 本体聚类， 枢纽文章（边最多的），阅读路径 推荐的 (« 如果你喜欢 Graphify 的文章，请接着读 它在Knowledge Graph上作为理解工具"".

这不再是一个博客。这是一个 语义图谱。

这不是科幻。 这`graph.json`已经存在。 它仅缺少导航界面。

结论：文件系统知道模板所忽略的内容

我周二晚上设计的，是一种启发式的替换。 懒惰的（按时间顺序）通过对…​的忠实再现 我的语料库结构（知识图谱）。

模板`post.thyme`不变。变化的是我们 给他喂食。前：一个按…​排序的Java列表`date`. 之后： 一个来自三层分析的加权图 — xrefs, 共现 标签的，以及通过NLP产生的新兴本体。

循环已闭合。graphify 扫描工作区。Bakery 读取 图形并填充模板。读者看到推荐。 相关。而且引擎 — 指挥家 — 甚至不知道 这一切都存在。

这就是良好的架构。每个插件只做一件事。 消费者终端不需要知道怎么做。
