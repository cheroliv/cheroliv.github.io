场景：一个 JHipster 项目，一个不再加载的构建

项目`edster`是一个在2024年生成的JHipster应用程序。 根构建脚本`build.gradle`它在几个月里保持稳定。然后决定升级版本：

组件

目标版本

Gradle

9.4.1

Java

21.0.11-tem (Eclipse Temurin)

JHipster

8.x (框架`tech.jhipster:jhipster-framework:8.11.0`)

Spring Boot

3.4.5

Kotlin

2.3.0

Docker 引擎

29.4.1 (API 1.54)

Java 版本的更改通过 SDKMAN 进行：

sdk use java 21.0.11-tem

首次发布：

$ ./gradlew build --no-daemon

FAILURE: Build failed with an exception.

* Where:
Build file '/home/.../edster/build.gradle' line: 18

* What went wrong:
An exception occurred applying plugin request [id: 'jhipster.cucumber-conventions']
> Failed to apply plugin 'jhipster.cucumber-conventions'.
   > Could not create task ':cucumberTest'.
      > Could not create task ':consoleLauncherTest'.
         > Could not set unknown property 'reportsDir' for task ':consoleLauncherTest'

甚至连构建脚本的加载都没有开始。问题出在`buildSrc/src/main/groovy/jhipster.cucumber-conventions.gradle`.

错误 1 : 幻影变量 `reportsDir

脚本`jhipster.cucumber-conventions.gradle`包含 :

tasks.register('consoleLauncherTest', JavaExec) {
    dependsOn(testClasses)
    String cucumberReportsDir = file("$buildDir/reports/tests")
    outputs.dir(reportsDir)           // <-- reportsDir n'existe PAS
    classpath = sourceSets["test"].runtimeClasspath
    main = "org.junit.platform.console.ConsoleLauncher"
    // ...
}

定义的变量是`cucumberReportsDir`. 所使用的`reportsDir`-- 哪里都没有定义。

修正:`outputs.dir(cucumberReportsDir)`

错误 2：main = \"…​\" 在 Gradle 9 中不再存在

立即跟进：

Could not set unknown property 'main' for task ':consoleLauncherTest' of type org.gradle.api.tasks.JavaExec.

Gradle 9 删除属性`main`为了…​的利益`mainClass`在任务上`JavaExec`.

更正:`mainClass = "org.junit.platform.console.ConsoleLauncher"`

错误 3 : sourceCompatibility 不再是项目的属性

新错误：

Could not set unknown property 'sourceCompatibility' for root project 'edster' of type org.gradle.api.Project.

根脚本有：

sourceCompatibility=17
targetCompatibility=17

Gradle 9 删除这些根级别的属性。它们必须位于一个块中`java`.

修正:

java {
    sourceCompatibility = JavaVersion.VERSION_21
    targetCompatibility = JavaVersion.VERSION_21
}

错误4：Groovy 三元断言

旧脚本包含：

assert System.properties["java.specification.version"] == "17" || "21" || "24"

在Groovy中,"21" et "24"`是一些真值的字符串。这个表达式解析为(…​ == "17") || true || true`, 这总是正确的 — 但语法对于所期望的严格断言是无效的。

修正:

assert System.properties["java.specification.version"] in ["17", "21", "23", "24"]

错误 5：隐式依赖 compileKotlin → `openApiGenerate

构建进展顺利。Kotlin 编译成功。然后：

Task ':compileKotlin' uses this output of task ':openApiGenerate'
without declaring an explicit or implicit dependency.

Gradle 9 拒绝任务之间的隐式依赖。既然`compileKotlin`读取由生成的数据源`openApiGenerate`, 必须声明链接。

修正在`build.gradle`:

afterEvaluate {
    tasks.named("compileKotlin").configure {
        dependsOn(tasks.named("openApiGenerate"))
    }
}

Le `afterEvaluate`是必要的因为`openApiGenerate`是一个扩展（OpenAPI Generator 插件），而不是在配置阶段直接可访问的任务。

错误 6 : generateGitProperties 在 FilterOutputStream.write() 上崩溃

Java 编译通过。资源已处理。然后：

> Task :generateGitProperties FAILED

No signature of method: java.io.FilterOutputStream.write() is applicable for argument types: (Integer) values: [103]

插件`gradle-git-properties`version 2.5.0 与 Java 21 / Gradle 9 不兼容。内部错误尝试调用`write(int)`通过 Groovy 在一个它已关闭的流上。

更正在`gradle.properties` :

gitPropertiesPluginVersion=2.5.7

到目前为止，这纯粹是 "build script debugging"。每个错误都是构建脚本中 Gradle 9 或 Java 21 的不兼容性。在以上六个修正之后，`./gradlew assemble`顺利通过。

但是`./gradlew build`也执行测试，并且 Cucumber 测试使用 Testcontainers 启动一个临时的 PostgreSQL。

阶段 1 : docker-java 路径

第一个反射：Testcontainers 使用的 Java Docker 客户端发送 API 版本`1.32`在其 HTTP 握手中，但 Docker Engine 29.4.1 需要至少`1.40`. 问题在于客户端，而不是守护进程。

Testcontainers 1.20.6 解析的 docker-java 版本验证：

$ ./gradlew dependencies --configuration testRuntimeClasspath | grep docker-java

+--- com.github.docker-java:docker-java-api:3.4.1
+--- com.github.docker-java:docker-java-transport:3.4.1

docker-java 3.4.1，源自 Testcontainers 1.20.6。docker-java 的最新公开版本是 3.5.1。让我们尝试通过强制升级版本`resolutionStrategy`在块中`configurations` de build.gradle</think>

configurations {
    all {
        resolutionStrategy.eachDependency { details ->
            if (details.requested.group == "com.github.docker-java"
                && details.requested.name.startsWith("docker-java")) {
                details.useVersion("3.5.1")
            }
        }
    }
}

重新启动构建。同样的错误：client version 1.32 is too old.

Gradle缓存验证：JARs已重新下载，但错误仍然存在。docker-java 3.5.1仍在发送`1.32`. 此版本因此不足以满足 Docker Engine 29.4.1 的需求。

净化行动: 完全清空 Gradle 缓存，只是为了确保 :

rm -rf ~/.gradle/caches
rm -rf /path/to/project/.gradle

清除后完整重启。同样的错误。

针对 testcontainers-java 和 docker-java 的议题进行有针对性的搜索：

site:github.com/testcontainers "client version 1.32 is too old"
site:github.com/docker-java "client version 1.32" Docker Engine 29

第3阶段：被重命名的工件陷阱

重命名非常残酷。在 Testcontainers 2.x 中，旧名称在该名称下均不起作用：

旧名称 (1.x)

新名称 (2.x)

org.testcontainers:postgresql

org.testcontainers:testcontainers-postgresql

org.testcontainers:jdbc

org.testcontainers:testcontainers-jdbc

org.testcontainers:junit-jupiter

org.testcontainers:testcontainers-junit-jupiter

org.testcontainers:testcontainers

未更改

第一次尝试：应用 Testcontainers 2.0.5 BOM 和新的工件名称 在`build.gradle`.

dependencies {
    testImplementation platform("org.testcontainers:testcontainers-bom:2.0.5")
    testImplementation "org.testcontainers:testcontainers-postgresql"
    testImplementation "org.testcontainers:testcontainers-jdbc"
    testImplementation "org.testcontainers:testcontainers-junit-jupiter"
    testImplementation "org.testcontainers:testcontainers"
}

./gradlew build

FAILURE: Could not find org.testcontainers:jdbc:2.0.5.
Could not find org.testcontainers:junit-jupiter:2.0.5.

testcontainers-bom的BOM不够。为什么？因为 Spring Boot 3.4.5 暴露了它自己的依赖管理 BOM（spring-boot-dependencies) 谁赢在 Testcontainers 的 BOM 中，在传递解析中。Spring Boot 修复`testcontainers` à 1.20.6, 因此所有未显式包含在Spring Boot BOM中的artifact（如新的`testcontainers-*) 解析到旧名称`1.20.6-- 在这一版本中不再存在。

在检查`dependencies --configuration testRuntimeClasspath`, 有 :

+--- org.testcontainers:testcontainers -> 1.20.6 (*)
|    \--- org.testcontainers:testcontainers:2.0.5 -> 1.20.6

Le →`表示替换：Testcontainers 2.0.5 是 需求，但 Spring Boot 强制`1.20.6.

最终校正在`build.gradle`:

configurations {
    all {
        resolutionStrategy.eachDependency { details ->
            if (details.requested.group == "com.github.docker-java"
                && details.requested.name.startsWith("docker-java")) {
                details.useVersion("3.7.1")
            }
            if (details.requested.group == "org.testcontainers"
                && details.requested.name == "testcontainers") {
                details.useVersion("2.0.5")
            }
        }
    }
}

dependencies {
    testImplementation platform("org.testcontainers:testcontainers-bom:2.0.5")
    testImplementation "org.testcontainers:testcontainers-jdbc"
    testImplementation "org.testcontainers:testcontainers-junit-jupiter"
    testImplementation "org.testcontainers:testcontainers-postgresql"
    testImplementation "org.testcontainers:testcontainers"
    // ... autres dépendances Spring Boot
}

Le `resolutionStrategy.eachDependency`这是绕过 BOM 的唯一方法`spring-boot-dependencies`由 Spring Boot 插件管理。关于相等性测试的`details.requested.name == "testcontainers"`这是有意的限制：我们只强制核心模块。模块`testcontainers-*`它们遵循我们显式声明的 Testcontainers 2.0.5 BOM。

结论

如果您的 JHipster/Gradle 构建在升级到 Gradle 9 + Docker Engine 29 后崩溃，错误将分为两类：

构建脚本错误(前6个) : Gradle 9 删除了多年有效的属性和语法`sourceCompatibility=, `main =, reportsDir).这些是机械迁移，一旦我们知道新的API。

Docker运行时错误 (les 2 dernières) : Docker Engine 29.4.1 écarte les clients API < 1.40. Testcontainers 1.20.6 (imposé par Spring Boot 3.4.5) utilise docker-java 3.4.1 qui envoie 1.32. Seul Testcontainers 2.0.5 + docker-java 3.7.1 résout le problème, avec le renommage des artifacts et le forçage de version via`resolutionStrategy.eachDependency`作为绕过 Spring Boot 隐含 BOM 的唯一方法。

项目根目录下的 Gradle 构建脚本现在很干净。`./gradlew build`基于 Java 21、Gradle 9.4.1、Spring Boot 3.4.5 和 Docker Engine 29.4.1。
