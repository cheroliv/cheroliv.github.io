Governing an AI Agent with AsciiDoc: My Eager/Lazy Strategy for Opencode Sessions Without Context Leak

Published on 24 April 2026

Summary

When working with an AI agent like Opencode on complex projects across multiple sessions, you face a fundamental problem:the context leak. The agent does not remember the previous session. Everything that was explained to them — the architecture, the conventions, the state of the backlog — is lost. Reconstructing this context each session is costly, slow, and a source of error.

This article sets out the artisanal strategy I built to solve this problem: a persistent governance system based on AsciiDoc files, with a dichotomyEager/Lazyto optimize context token consumption, and aessential end-of-session procedureto ensure continuity.

The Scene: Monday 21 April, 9:00

I reopen Opencode to resume my Gradle plugin.plantuml-plugin. Last night, I spent three hours discussing with the API key pool architecture agent — round-robin rotation, quota management, automatic fallback. This morning, the agent looks at me with goldfish eyes.

_ Hello, I am your Opencode assistant. How can I help you today? _

No — Ah yes, the API key pool, we were at the YAML structure. No — Attention,PlantumlManager`is a Kotlin singleton object, not a class. No — No, we decided yesterday that`SyntaxValidationResult`there remained a nested sealed class in`PlantumlService.

Everything has to be redone. Or rather: everything has to be re‑explained. I will spend the first twenty minutes of my session reconstructing a context that the agent already had in hand yesterday. Twenty minutes of burned tokens. Twenty minutes where I could be coding, but I am doing mandatory pedagogical work.

It’s not a bug in Opencode. It’s the very nature of conversational LLMs: between two sessions, the working memory iscompletely erased. The agent does not remember the previous mission, the decisions taken, the identified pitfalls, the code we wrote together.

I’ve experienced that dozens of times. On four simultaneous projects. With sessions that chain over weeks. I calculated: on average,30-40% of session timewas dedicated to recontextualizing the agent. At session 87 of the project`plantuml-plugin`, I cracked. I could no longer afford to explain for the tenth time that`AttemptEntry`is a top-level data class in`DiagramProcessor.kt`.

I needed a system. Not a hack. Real governance.

Genesis: From Chaos to Method

The Early Sessions: The Age of Darkness

My first project with Opencode,plantuml-plugin, started without any governance. I ask a question, the agent answers, we iterate, the session ends, and the next day we start from zero. It was session 1, then 2, then 3…​ up to session 62 where I realized I had lost cumulative hours re-explaining the same architecture.

At session 62, the numbers are there:198 unit tests pass, 42 functional tests validated, the plugin works. But the cognitive cost is unbearable. Each new session begins with a twenty-minute monologue on the project structure.

The Destroyed Episode of site.yml (Session 2, bakery-plugin)

The method also arises from a catastrophe. On the project`bakery-gradle`, at session 2, I ask the agent to modify the file`site.yml`. The agent, without checking whether the file is versioned, makes a`Write`complete that overwrites the content. Result: the real tokens (Firebase API keys, deployment secrets) are replaced with fake placeholders. The file wasn’t in git — it was in`.gitignore`to protect the secrets.

Without backup. Without`git restore`possible. I am stuck. I need to manually rebuild the configuration file, retrieve the tokens from my password managers, and put everything back together.

It is from this frustration that theAbsolute Rule 1b:

_ Never crusha config file with a`Write`complete when a`Edit`Partial suffices.Never replacesensitive values with dummy values.Check git check-ignore and `git ls-filesbefore any modification. _

This rule, now etched in stone in all my files`AGENT.adoc` et `INDEX.adoc`on four projects, was born from a real error that cost me an hour of manual work.

The Markdown → AsciiDoc Migration (Session 1, cheroliv.com)

On April 25, 2026, on`cheroliv.com`, I am making a radical decision: converting the entirety of Markdown governance to AsciiDoc. It’s not aesthetic. It’s functional. AsciiDoc offers a semantic structure that LLMs read better: hierarchical sections, typed tables, admonitions (NOTE, WARNING, CAUTION), machine-readable document attributes.

The session 1 of`cheroliv.com`formalize the structure :

  • Conversion of`AGENTS.md` en AGENT.adoc

  • Creating the specialized agents:`CODER.adoc`, SCRUM_MASTER.adoc, PLANTUML_DESIGNER.adoc

  • Creation of the Eager/Lazy structure:`INDEX.adoc`, SESSIONS_HISTORY.adoc, AGENT_SESSION_MANAGER.adoc, SESSION_CHECKLIST.adoc, PROCEDURES.adoc

Only one commit:`90975e9 refactor: migrate agent governance from Markdown to AsciiDoc`. And the site continues to operate.

The Strategy: Eager/Lazy in Depth

Philosophy : Computer Cache Applied to Cognition

My approach is directly inspired by computer cache management. Everything that iscritical and frequently usedmust be immediately accessibleEager). Everything that iscontextual or bulkymust be loaded on demandLazy).

Eager (Dashboard)

Lazy (Owner’s Manual)

Size

< 100 lines, < 10k tokens

Unlimited, detailed

Loading

Auto, at the beginning of the session

At the request of the agent

Content

Absolute rules, current mission, critical state

Session archives, complete history, detailed procedures, technical references

Role

Orient the agent immediately

Answer deep context questions

Eager Files: The Dashboard

These files live at the root of each project and are automatically loaded by the agent at the start of each session. They form thedashboard-- critical information, immediately accessible.

==== The Missing Link: `opencode.json

I must confess something I almost forgot to document. Above all these .adoc files, there is a tiny JSON file without which nothing works. It's called`opencode.json`and it is six lines. Literally six lines.

[source,json]
----
{
  "$schema": "https://opencode.ai/config.json",
  "instructions": [
    "AGENT.adoc"
  ]
}
----

This file tells Opencode: "At startup, load`AGENT.adoc`Automatically. Without him, the agent is a blank page exactly as I described at the beginning of the article. With him, the agent already has in hand the absolute rules, the project architecture, and the essential commands — even before I say hello.

I discovered the importance of this file by chance. On`bakery-plugin`, it did not exist. I was wondering why the agent was systematically more 'lost' on this project than on the others. The absolute rules were well in`AGENT.adoc`— but`AGENT.adoc`It was never loaded. The agent only read what I told him to read, manually, each session. This was session 11 of`bakery-plugin`when I realized the absence of the`opencode.json`. I created it — and session 12 started like the others.

This file is so obvious to me now that I wasn't even thinking about it anymore. A classic mistake of a developer who knows their tool too well. Nowadays, I systematically create it *before`AGENT.adoc`. This is the first stone.

==== The Duality of `INDEX.adoc

Another subtlety that deserves to be clarified:`INDEX.adoc`lives in`.agents/`— a folder that I presented as LAZY. However, I list it as EAGER in all my tables. There is an apparent tension here.

The field reality: the files`.agents/INDEX.adoc`are automatically loaded correctly at the beginning of the session, just as`AGENT.adoc` et `PROMPT_REPRISE.adoc`. They are in`.agents/`for organizational reasons — not to invade the root — but their behavior is EAGER.

on`plantuml-plugin`, `INDEX.adoc`is 200 lines long and contains the absolute *complete* rules with their history (the lessons from past sessions), the EPICs with scores, and the project portfolio. It is the document the agent consults to know 'where we stand'. Sur`bakery-plugin`, it makes 150 lines with the roadmap and recent sessions.

The deliberate redundancy between`AGENT.adoc` et `INDEX.adoc`can be surprising. The absolute rules are present in both. Why? Because they fulfill two different roles: in`AGENT.adoc`, they are *explanatory* (the storytelling of the rule, the lesson learned) ; in`INDEX.adoc`, they are *executive* (the naked rule, without justification, for a quick consultation). The agent reads`AGENT.adoc`once to *understand*; he rereads`INDEX.adoc`for each session to *apply*. Two uses, two formats.

== Specialized Agents: A Virtual Team

Governance is not limited to passive files. I have formalized**roles of specialized agents**in dedicated LAZY files, which define the expected workflow according to the task type.

|===
|Agent |File |Role |Project |**to code** |`CODER.adoc` |Implementation FTL/CSS/JS, semantic tags, accessibility criteria |cheroliv.com |**Scrum Master** |`SCRUM_MASTER.adoc` |US planning, sub-task breakdown, dependency detection |cheroliv.com |**PlantUML Designer** |`PLANTUML_DESIGNER.adoc` |Diagram creation, PUML syntax, JBake integration |cheroliv.com
|===

The file`CODER.adoc`on`cheroliv.com`contains concrete rules: _one`<h1>`per page_, _Prefix paths with`${content.rootpath}`_, _Declare language`<html lang="${content.lang!"fr"}">`_. These conventions, written once, are automatically respected by the agent since session 1.

The file`SCRUM_MASTER.adoc`imposes a deliverable structure :**Objective**, **Tasks**(coordinates with assignment),**Acceptance criteria**, **Risks**. When I ask for an action plan, the agent produces this structure without me having asked for it. The governance**program**the agent.

==== When Specialized Agents Become Indispensable

The creation of specialized agents follows a natural curve. At the beginning of a project, you don't need them —`AGENT.adoc`is more than enough. But when the project grows (let's say, beyond 20 sessions), two signals must alert you :

1. The agent mixes the conventions of two distinct fields (e.g., PlantUML syntax and CSS rules)
2. You spend more time correcting the agent on conventions that you have already explained to him 5 times.

On`cheroliv.com`, it happened during the session... 1. Yes, right from the start. Because this project is a website with three languages (FTL, CSS, JS), AsciiDoc content, and PlantUML diagrams — three domains that have nothing to do with each other. The CODER agent needs to know font sizes and media queries; the PLANTUML_DESIGNER agent needs to know the`@startuml`. Without separation, the CODER agent was proposing diagrams to me, and vice versa. The chaos.

On`jhipster-gradle-plugins`, I created two specialized agents adapted for Gradle plugin development:`PLUGIN_DEVELOPER.adoc` et `BACKLOG_MANAGER.adoc`. The first encodes all Kotlin/Gradle conventions (no`!!`python import sys

Before that, the business context was contained in`AGENT.adoc`. The rule of thumb: a specialized agent is justified when its business domain exceeds 100 lines of documentation.

==== The Session Naming Convention

A detail that seems trivial but becomes critical when you reach 100 sessions. How to name the archive files?

I learned the hard way that a convention is necessary — four projects, four different formats at the start, and I got lost. Today, the convention I have settled on is:








{N}-{type}-{sujet-kebab-case}.adoc








Concrete examples :

* `1-chore-migration-gouvernance-agent.adoc`— session 1, type chore
* `10-solidification-tests.adoc`— session 10, without explicit type (the subject suffices)
* `036-debug-graphify-symlink-epic9.adoc`— session 36 with 3-digit number for sorting

The session number is the primary sorting criterion. Projects using three‑digit numbers (001, 036, 133) avoid lexical sorting problems when exceeding 99. This is what I now use on`magic-stick`:`001-init-projet.adoc`, `036-debug-graphify-symlink-epic9.adoc`.

The type is optional and derived from the session keywords (debug, feature, refactor, docs, chore, test). The subject in kebab-case is the most important part: it must allow retrieving a session without opening the file. If you wonder « which session was it where we fixed the timeout of the integration tests? », the answer is`124-fix-timeout-integration-test.adoc`.

For reconstructed historical sessions (projects born before governance), I use negative numbers. On`cheroliv.com`, the sessions -6 to 0 cover the entire pre-governance history of the project. And for the "undocumented" or lost sessions, I create an entry in`SESSIONS_HISTORY.adoc`without a matching archive, with a score`?`. It's more honest than pretending.

== The End-of-Session Procedure: The Golden Rule


=== Why she is essential


Without this procedure, the Eager/Lazy strategy is useless. It is this that turns the session’s work into persistent information. It executesat the explicit request of the user(keywords: "end of session", "I’m leaving", etc.), and it ismandatory-- no exception, no omission.


The file`SESSION_CHECKLIST.adoc`defines ideal session metrics:


* Duration: 15-30 minutes
* Modified files: 1-3 maximum
* LLM exchanges: 5-10 messages
* Context tokens: < 50k


And signs that you need to change session: _The LLM repeats errors already corrected, More than 3 files modified in parallel, Conversation > 50 messages. The golden rule:Better to have 5 sessions of 20 minutes than one session of 2 hours with debugging chaos.

=== Step 0: Create opencode.json


This is the first file. Not`AGENT.adoc, not`INDEX.adoc`.opencode.json`First, for a simple reason: if you create`AGENT.adoc`first, you will forget to create the bridge that loads it automatically. I did it on`bakery-plugin, I know what I’m talking about.


=== Step 1: Create the Folders


[source,bash]
----

----


Two empty folders.sessions/`will receive the archives of each session`archives/`will receive the monthly COMPLETED_TASKS_ARCHIVE. These folders must exist *before the agent needs to write in them. An agent that must create the folder AND the file at the same time is an agent that can fail silently.

=== Step 3: Create PROMPT_REPRISE.adoc — The Mission Session 1


A file that explicitly says: "This is session 1, mission to define." Maximum 70 lines, with a Session 0 section (bootstrap summary) and a Session 1 section (priorities to define with the user).


=== Step 4 : Create .agents/INDEX.adoc — The Entry Point


The file that will contain the absolute rules (executive version) and the session table. For the bootstrap, it lists rules 0 to 3 in their concise format, the project portfolio (including the new project with a 🆕 emoji), and the empty roadmap ready to be filled.


=== Step 5: Create the Structuring LAZY Files


In order:


1. .agents/SESSIONS_HISTORY.adoc— a table with only session 0
2. .agents/SESSION_CHECKLIST.adoc— the template « When to change session
3. .agents/PROCEDURES.adoc— the complete procedure of the 6 steps + EAGER/LAZY
4. .agents/AGENT_SESSION_MANAGER.adoc— the archive template
5. .agents/TEST_COVERAGE_ANALYSIS.adoc— the test tracking table, empty at first


If your project has a complex business domain (like`jhipster-gradle-plugins`with its mono-repo persistence/assistant), create the specialized agents now:


1. .agents/PLUGIN_DEVELOPER.adoc— code conventions and the dependency boundary (if plugin)
2. .agents/BACKLOG_MANAGER.adoc— the planning structure and the identified risks


Do not create agents that you will not use. An agent without concrete conventions to encode is a dead file that pollutes..agents/.

1. Add a line to the new project’s portfolio (logic)
2. Add a line in the portfolio of ALL existing projects — yes, all


On my four (now five) projects, this means opening the`INDEX.adoc` de magic-stick, bakery-gradle, cheroliv.com, `plantuml-gradle`and add the line there`jhipster-gradle-plugins
