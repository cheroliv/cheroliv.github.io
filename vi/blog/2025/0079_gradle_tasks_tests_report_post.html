Tự động hóa các tác vụ build là điều tối quan trọng đối với mọi dự án phần mềm, và Gradle, với DSL Kotlin, mang lại sự linh hoạt đặc biệt. Trong suốt cuộc hội thoại của chúng ta, chúng ta đã khám phá cách tập trung hóa và tái sử dụng logic build, đặc biệt là đối với các báo cáo kiểm thử, bằng cách tận dụngtất cả dự án, buildSrc, và các tác vụ tùy chỉnh bằng Kotlin.

Tập trung hóa các Cấu hình với allprojects và `subprojects

Các khối`allprojects` et `subprojects`trong …​ của bạn`build.gradle.kts`gốc là nền tảng để áp dụng các cấu hình chung trong suốt dự án đa mô-đun của bạn.

Vui lòng cung cấp văn bản tiếng Pháp cần dịch.allprojects { …​ }: Áp dụng cấu hình chodự án gốc và tất cả các dự án con của nó. Lý tưởng để định nghĩa một`group`, một`version`, hoặc các`repositories`chung. *subprojects { …​ }: Áp dụng cấu hìnhchỉ dành cho các dự án con, ngoại trừ dự án gốc. Hoàn hảo để áp dụng các plugin cụ thể cho các module (như`java` ou kotlin-jvm) hoặc các phụ thuộc chung trong các thư viện của bạn.

Đây là một ví dụ minh họa:

// build.gradle.kts (projet racine)
plugins {
    base // Appliqué au projet racine
}

allprojects {
    group = "com.example"
    version = "1.0.0"

    repositories {
        mavenCentral()
    }

    tasks.withType<org.gradle.api.tasks.testing.Test> {
        useJUnitPlatform() // Configuration commune des tests pour tous les projets
    }
}

subprojects {
    apply(plugin = "java")
    apply(plugin = "org.jetbrains.kotlin.jvm")

    dependencies {
        implementation("org.jetbrains.kotlin:kotlin-stdlib-jdk8")
    }

}

\==buildSrc: Con dao đa năng cho Logic Build

Khi logic của các tác vụ trở nên phức tạp hoặc cần được tái sử dụng,buildSrclà giải pháp được ưu tiên. Đây là một module Gradle đặc biệt được biên dịch trước các script build chính, giúp các class của nó có sẵn trên classpath của toàn bộ bản build của bạn.

\=== Tại sao nên sử dụng`buildSrc`cho các Tâches ?

  • Khả năng tái sử dụng: Một tác vụ được định nghĩa trong`buildSrc`có thể được áp dụng cho bất kỳ dự án build nào.

  • Tổ chức: Tập trung hóa mã build, giúp mã sạch hơn và dễ bảo trì hơn.

  • An toàn kiểu dữ liệu và Tự động hoàn tất: Mã Kotlin trong`buildSrc`được biên dịch, cung cấp tính năng kiểm tra lỗi và tự động hoàn thành của IDE, giúp cải thiện trải nghiệm phát triển.

\=== Sơ đồ Luồng`buildSrc`(Mã PlantUML)

Để tạo biểu đồ này, hãy sao chép mã dưới đây và dán vào một công cụ hỗ trợ PlantUML.

RP --|\> SA : "contains RP --|\> SB : "contains

\== Tạo các Tác vụ Báo cáo Trừu tượng

Để quản lý các báo cáo thử nghiệm, chúng tôi đã thiết kế một phương pháp tiếp cận mô-đun bằng cách sử dụng một lớp tác vụ trừu tượng trong`buildSrc`. Tùy theo nhu cầu của bạn, lớp này có thể kế thừa từ`DefaultTask` ou de `Exec`Vui lòng cung cấp văn bản cần dịch.

\=== Nhiệm vụ Trừu tượng`OpenTestReportTask`(kế thừa từ`DefaultTask`)

Cách tiếp cận này được khuyến khích nếu bạn cần một logic Kotlin tùy chỉnh để tương tác với hệ thống tệp hoặc các API Gradle khác, sau đó chạy một lệnh bên ngoài.

[nguồn,kotlin]

package com.yourpackage

import org.gradle.api.DefaultTask import org.gradle.api.tasks.Input import org.gradle.api.tasks.TaskAction import java.io.File

abstract class OpenTestReportTask : DefaultTask() {

----
----
init {
    group = "verification"
    description = "Opens a test report in Firefox."
    dependsOn("check") // Assure que les rapports sont générés
}

@get:Input
abstract var reportPath: String

@TaskAction
fun openReport() {
    val separator = File.separator
    val reportFile = project.layout.projectDirectory.asFile.toPath()
        .resolve(reportPath.replace("/", separator))
        .toAbsolutePath()
        .toFile()

    if (!reportFile.exists()) {
        logger.warn("Report file does not exist: $reportFile. Ensure 'check' ran.")
        return
    }

    project.exec {
        commandLine("firefox", "--new-tab", reportFile.absolutePath)
    }
    logger.lifecycle("Opened test report: ${reportFile.absolutePath}")
}
----

## }

Các lớp này kế thừa từ tác vụ trừu tượng và định nghĩa đường dẫn báo cáo cụ thể.

\== Khả năng hiển thị Nhiệm vụ`buildSrc`

Các tác vụ và lớp mà bạn định nghĩa trong**buildSrc**là:

***Hiển thị và có thể sử dụng**bởi tất cả các dự án trong bản build chính của bạn (gốc và các dự án con). Đó là lý do tại sao bạn có thể sử dụng`com.yourpackage.ReportUnitTestsTask`trong`allprojects { ... }`Vui lòng cung cấp văn bản cần dịch. Hãy cung cấp văn bản cần dịch.**Không thể thực thi**trực tiếp dưới dạng các tác vụ buildSrc (ví dụ:`gradle :buildSrc:reportTests`sẽ không hoạt động nếu tác vụ không được lưu cụ thể trong`buildSrc/build.gradle.kts`).`buildSrc`là một mô-đun biên dịch, không phải là một mô-đun ứng dụng có thể thực thi cho các tác vụ của build chính này.

\=== Chạy báo cáo cho các bài kiểm tra của`buildSrc`chính ông ấy

Si `buildSrc`cho các bài kiểm tra của riêng mình và tạo báo cáo, bạn có thể lưu một tác vụ báo cáo trực tiếp trong`buildSrc/build.gradle.kts`Vui lòng cung cấp văn bản cần dịch.

## [nguồn,kotlin]

plugins { `kotlin-jvm` }

repositories { mavenCentral() }

tasks.withType\<Test\> { useJUnitPlatform() reports.html.outputLocation.set(layout.buildDirectory.dir("reports/tests")) }

import com.yourpackage.ReportJbakeTestsTask // Nhập lớp tác vụ của bạn

## tasks.register\<ReportJbakeTestsTask\>("reportBuildSrcTests") { // Đường dẫn đã được định nghĩa trong lớp, nó sẽ trỏ đến các báo cáo của buildSrc }

Sau đó bạn có thể thực thi:`./gradlew :buildSrc:test`theo sau là`./gradlew :buildSrc:reportBuildSrcTests`Hãy cung cấp văn bản bạn muốn dịch.

Bằng cách áp dụng những thực hành này, bạn sẽ xây dựng được các hệ thống build Gradle bằng Kotlin DSL không chỉ mạnh mẽ, mà còn cực kỳ mô-đun, dễ bảo trì và dễ hiểu.
