Twee weken geleden lanceerde ik`capsule-gradle`— een plugin die een deck transformeert reveal.js in een WebM-videocapsule met TTS. Vandaag voeg ik een nieuwe plugin toe: hyperframes-gradle. Het doet iets wat capsule-gradle niet doet : zet de AsciiDoc rechtstreeks om naar een MP4-video, zonder reveal.js te gebruiken.

Hier is waarom deze plug-in bestaat, hoe hij samenwerkt met het bestaande, en wat de HyperFrames-engine van HeyGen toevoegt aan de pijplijn voor contentproductie

Het gat in de videopijplijn

Mijn documentaire pijplijn produceert twee soorten video’s :

  1. Revisiecapsule (capsule-gradle) — een deck reveal.js opgenomen in WebM met

narration TTS. Perfect om een module te herzien.

  1. animatieslides (slider-gradle) — een interactieve reveal.js HTML-deck voor

de fysieke trainer.

Maar er ontbreekt een derde formaat: de video standalone.

Het eerste use case is cruciaal: hoe automatisch te genereren een video van 60 seconden die een project of module presenteert, met GSAP-animaties, vertelling TTS, en achtergrondmuziek — alles vanuit hetzelfde AsciiDoc-bestand wat de slides ?

Capsule-gradle kan niet reageren: het heeft al een reveal.js-deck nodig. slider-gradle produceert dit deck goed, maar het is niet ontworpen voor het renderen van video. Er was een direct pijplijn nodig: AsciiDoc → video.

HyperFrames : De Motor

Ik heb ontdekthttps://github.com/heygen-com/hyperframes[HyperFrames] il y a enkele dagen. Het is een open-source framework (Apache 2.0) gemaakt door HeyGen, de eenhoorn van de AI-video. 22 700 sterren op GitHub. De pitch houdt in een zin :

Schrijf HTML. Weergeef video. Gebouwd voor agenten.

Het principe: je schrijft HTML met`data-*`attributes, u verwijst een animatie GSAP (of CSS, Lottie, Three.js…), en de motor rendert alles als MP4 via Puppeteer (headless Chrome) + FFmpeg. Deterministisch resultaat: dezelfde input, zelfde frames, zelfde video.

Wat maakt HyperFrames anders dan Remotion? Geen React, geen bundler, geen JSX. Ruwe HTML die AI-agents van nature kunnen schrijven. Het is exact afgestemd op mijn pipeline: planner-gradle met deepseek kan deze HTML genereren vanuit een SPG/SPD-plan, en een Gradle-plugin kan het converteren naar MP4.

De architectuur van de plugin

hyperframes-gradle volgt hetzelfde patroon als al mijn plugins : de patroon „Plugin Onafhankelijk + Wortel Consument“

  1. AsciidoctorJ parst de AsciiDoc-bron en extraheert de aangepaste blokken.

[hyperframes-composition], [hyperframes-track], [hyperframes-animation].

  1. GenerateHyperframesHtmlTask genereert het HTML HyperFrames met de

`data-*`bijbehorende attributen.

  1. RenderHyperframesTask roept de HyperFrames CLI aan via`ProcessBuilder`:

npx hyperframes render --input index.html --output video.mp4.

  1. MP4 wordt geïmplementeerd in`output/`met een`metadata.json`voor de orkestratie.

De DSL AsciiDoc

De echte toegevoegde waarde van de plugin is de AsciiDoc DSL. De gebruiker Hij schrijft nooit HTML. Hij annoteert zijn bestaande AsciiDoc-document :

= Formation Docker & Kubernetes
:hyperframes-width: 1920
:hyperframes-height: 1080
:hyperframes-fps: 30

[hyperframes-composition, id="intro"]
== Introduction

Le titre apparaît avec un fondu GSAP sur fond vidéo.

[hyperframes-track, index=0, start=0, duration=6]
video::assets/background.mp4[muted, playsinline]

[hyperframes-track, index=1, start=1, duration=4]
Formation Docker & Kubernetes

[hyperframes-animation, type=gsap]

const tl = gsap.timeline({ paused: true }); tl.from("#title", { opacity: 0, y: 40, duration: 0.8 }, 1); window.timelines = window.timelines || {}; window.__timelines.intro = tl;

De docinfo-attributen`:hyperframes-width:`) configureren ze de afmetingen. De aangepaste blokken definiëren de composities en de tracks. Het blok `[hyperframes-animation]`bevat de ruwe GSAP-code — dat de AI-agent kan genereren vanuit een beschrijving in natuurlijke taal.

De Bridge Node.js

Het enige technische wrijvingspunt: HyperFrames is in Node.js/TypeScript, en mijn plugins zijn in Kotlin/JVM. De oplossing is een`ProcessBuilder` :

class RenderHyperframesTask : DefaultTask() {

    @TaskAction
    fun render() {
        val process = ProcessBuilder(
            "npx", "hyperframes", "render",
            "--input", inputHtml.absolutePath,
            "--output", outputMp4.absolutePath
        )
            .inheritIO()
            .start()

        val exitCode = process.waitFor()
        require(exitCode == 0) {
            "HyperFrames render failed with exit code $exitCode"
        }
    }
}

Geen koppeling JVM-code ↔ Node.js. Het contract is via de commandregel en bestanden op schijf. Dit is hetzelfde patroon als`plantuml-gradle` (die de PlantUML CLI aanroept) of`slider-gradle`(die AsciidoctorJ aanroept). Niets nieuws onder de zon — gewoon toegepast op een nieuwer hulpmiddel.

Waarom werkt het

Drie redenen:

  1. HyperFrames is "built for agents". Mijn pijplijn is gebaseerd op AI-agents.

(planner-gradle + deepseek) die inhoud genereren. HyperFrames accepteert Ruwe HTML — het formaat waarvan LLMs het beste bekwaam zijn. Geen React, geen geen JSX, geen leercurve voor de agent.

  1. De AsciiDoc DSL is natuurlijk. Mijn hele ecosysteem spreekt AsciiDoc.

slider-gradle, codex-gradle, training-gradle — allen verbruiken`.adoc`. Voeg aangepaste blokken toe`[hyperframes-composition]`is een extensie logisch, geen breuk.

  1. De Node.js bridge is een bewezen patroon ProcessBuilder buiten de JVM,

Dit is wat ik al doe voor PlantUML, Graphviz, Piper. HyperFrames toevoegen verandert niets aan de architectuur — het is een extra extern hulpmiddel, Gestuurd sinds Gradle.

De echte kracht van het patroon is dat er geen npm-afhankelijkheid in de Gradle-build. De plugin importeert geen Node.js-code. Het voert een shell-opdracht. Als HyperFrames evolueert of breekt, de plugin is niet gekoppeld — Het is voldoende om de opdracht bij te werken.

Conclusie: De ontbrekende schakel

Met hyperframes-gradle is mijn videopipeline compleet. Ik heb :

  • De interactieve slides (slider-gradle)

  • De herhalingscapsules (capsule-gradle)

  • De video’s standalone (hyperframes-gradle)

Drie formaten. Één bronbestand: AsciiDoc.

Het volgende doel is HF-1 : de plugin compileren en genereren een Eerste HTML HyperFrames vanaf een geannoteerd AsciiDoc-document. De sessie 001 is al gekaderd.

hyperframes-gradle bestaat. De governance is op zijn plaats. Het backlog is geschreven. De architectuur is gedocumenteerd. De plug-in is geboren.
