Tijdens maanden heb ik de agent-governance-regels gestapeld. Bestanden EAGER, luie checklists, zesstaps eind-sessieprotocollen. En toch bleef een vraag onbeantwoord: hoe weet de LLM wat het heeft het recht om iets met een bestand te doen ?

Het antwoord staat niet in een prompt. Het staat in het bestandssysteem.

Hier is de architectuurspecificatie die de response bruikbaar maakt — la LLM-governancematrix.

Het probleem: Prompt Engineering is een zandkasteel

Als je een bestand geeft aan een LLM, geef je het alles. De inhoud, ja — maar ook het ontbreken van beveiligingen. De LLM weet niet of dit bestand bevat een geheim, een speculatieve mening, of gesloten-broncode. Hij gaat het indexeren, het samenvatten, het citeren, het mengen met andere gegevens — en mogelijk publiceren in een openbare embedding of een gebruikersreactie.

De klassieke parade, dat is de prompt :

"Tu es un assistant sécurisé. Ne divulgue jamais d'informations confidentielles.
Si tu détectes un secret, ignore-le. Si tu détectes une opinion, ne la répète pas."

Deze prompt heeft drie problemen:

  1. Het berust op de goede wil van de LLM. Een model dat groot genoeg is voor

het oplossen van complexe bugs is groot genoeg om een instructie te omzeilen van verdrinkende veiligheid in 200k tokens van context

  1. Het is contextueel, niet structureel. Verander van prompt, verander van LLM

Verander van sessie — en de regel verdwijnt.

  1. Het schaalt niet. Elk nieuw bestandstype, elk nieuw niveau

de vertrouwelijkheid vereist een nieuwe clausule. Uw prompt wordt een regelgevingstekst die niemand volledig leest

De veiligheid van een systeem mag nooit afhangen van een instructie die men kan vergeten, omzeilen of niet laden. Ze moet afhankelijk zijn van een een barrière die je niet kunt overschrijden zonder het expliciet te willen

Mijn antwoord: de 4×4 matrix

De oplossing die ik in mijn werkruimte heb geïmplementeerd is een matrix zone × toegangsrecht LLM. Ze vraagt niet aan de LLM om voorzichtig te zijn. Ze geeft de structureel onmogelijke onvoorzichtigheid

De Vijf Zones (Ruimtelijke Dimensie — AVG)

Elke zone van de workspace heeft een RGPD-niveau dat bepaalt waar het bestand kan worden gerouteerd :

Zone

Niveau AVG

Inhoud

Openbaar RAG-toegangsrecht

Wortel

0 — Intiem

Brain dumps, gesprekken LLM

VERBODEN— nooit geïndexeerd

configuration/

1 — Beperkte eigenaar

Geheimen, tokens, API-sleutels

verboden— nooit geïndexeerd

office/

2 — Beperkt collaboratief

Redactionele data, kadrage, trainingen

gefilterd— Alleen visie

foundry/private/

3 — open voorwaardelijk

Code gesloten bron, SaaS niet openbaar

VERBODEN— uitsluitend privaat dataset

foundry/public/

4 — Inheems publiek

Code Apache 2.0, gepubliceerde plugins

VRIJ— volledige indexering

De regel is simpel: het pad van het bestand bepaalt wat de LLM ermee kan doen. Geen metadata om te behouden, geen tag om toe te voegen in de frontmatter geen handmatige classificatie per commit. Het bestand is in`OSS/? Het is openbaar. Het is in`configuration/? Hij is onaantastbaar.

Epistemische classificatie (tweede dimensie)

De ruimtelijke dimensie zegt waar te routeren. Maar er is een tweede as, loodrecht : wat router. Sommige bestanden in een toegestane zone bevatten informatie. die niet verdund zouden moeten worden zoals ze zijn:

  endif
elseif (Zone office/)
  :DROIT D'ACCÈS FILTRÉ\n→ accès conditionnel;
  :Filtre épistémique\nVision/Opinion/Stratégie;
  if (Classification ?) then (VISION)
    :DILUTION COMPLÈTE\n→ docs racine + blog;
  elseif (STRATÉGIE)
    :DILUTION RESTREINTE\n→ docs racine seulement;
  else (OPINION)
    :CONFINEMENT\n→ office/ uniquement;
  endif
else (Zone OSS/)
  :ACCÈS LIBRE\n→ indexation complète;

@enduml

De epistemische classificatierooster, ingegraveerd in Regel 2bis van mijn bestuur agent :

| Status | Definitie | Signaal LLM | Bestemming | | VISION | Gestabiliseerde architectuur, getest patroon | Declaratieve taal, sessie-/testverwijzingen | Volledige verdunning + Blog | | STRATEGIE | Positionering business, pricing | Vocabulaire markt, concurrentie | Docs wortel alleen | | OPINION | Speculatie, niet-gevalideerde hypothese | Hypothhetische taal, intuïtie | Confinement Cirkel 0 |

Hoe verbruikt de LLM deze matrix

De matrix is geen document dat de LLM leest. Het is een beperking impliciet gecodeerd in de composiete contextvector (EPIC 9 — gaande van de implementatie)

Hier is wat het LLM ontvangt bij elke sessie:

VECTEUR COMPOSITE DE CONTEXTE
├── RAG pgvector → OSS/ + office/Vision
│   (similarité sémantique sur contenu publiable)
├── Knowledge Graph graphify → OSS/
│   (relations exactes entre artéfacts publics)
├── Knowledge Graph privé → CSS/
│   (relations entre code closed source — jamais exporté)
├── Métadonnées de zone → chaque fichier taggé par zone physique
│   (le LLM sait s'il est dans office/ ou OSS/)
└── Historique des décisions → WORKSPACE_VISION.adoc
    (contexte temporel des arbitrages)

Concreet, wanneer de LLM mij zegt :

Je vais indexer le contenu de edster/ pour enrichir le knowledge graph...

De zone-metadata reageert voordat het LLM zijn zin zelfs afmaakt : edster/`is in`CSS/, niveau 3 →toegang verboden tot het publieke knowledge graph. RAG ziet het niet. De grafiek raakt het niet. De gebruikersreactie niet Hij citeert het niet.

De ruimtelijke ontologie werkt als eenrecht Unixvoor de LLM. Je vraagt niet aan een proces om voorzichtig te zijn met`/etc/shadow`— U weigert hem leestoegang. Hetzelfde principe.

Implementatie : Getypte Gradle-taken

De matrix is geen filosofie. Het is code. Hier is de taakcontract. Gradle die het implementeert :

abstract class ZoneAwareIndexer @Inject constructor(
    private val rootDir: DirectoryProperty,
    private val configServer: ConfigServerProperty  // → configuration/
) : DefaultTask() {

    @Input
    val zoneFilter: SetProperty<Zone> = project.objects.setProperty(Zone::class.java)

    @OutputFile
    val ragIndex: RegularFileProperty = project.objects.fileProperty()

    @TaskAction
    fun index() {
        val allowedPaths = zoneFilter.get().flatMap { it.resolve(rootDir.get()) }
        val forbiddenPaths = Zone.RESTRICTED.resolve(rootDir.get())
                            + Zone.INTIMATE.resolve(rootDir.get())
        // Le RAG ne voit jamais configuration/ ni la racine
        // CSS/ alimente un index privé, pas celui-ci
        // office/ est filtré par le classifieur Vision/Opinion
    }
}

enum class Zone {
    INTIMATE,      // Cercle 0 — racine
    RESTRICTED,    // Cercle 1 — configuration/
    EDITORIAL,     // Cercle 2 — office/
    CLOSED_SOURCE, // Cercle 3 — foundry/private/
    OPEN_SOURCE    // Cercle 3 — foundry/public/
}

De taak is testable. Je kunt een test schrijven die controleert:

@Test
fun `le RAG n'indexe jamais configuration`() {
    val index = ZoneAwareIndexer(rootDir, configServer)
    index.zoneFilter.set(setOf(Zone.OPEN_SOURCE, Zone.EDITORIAL))
    index.index()

    assertThat(index.ragIndex).doesNotContain("configuration/")
}

@Test
fun `le code closed source est exclu du RAG public`() {
    val index = ZoneAwareIndexer(rootDir, configServer)
    index.zoneFilter.set(setOf(Zone.OPEN_SOURCE))  // OSS only

    assertThat(index.ragIndex).doesNotContain("edster")
}

380 tests, 380 PASS. Zoals bij plantuml-gradle — de veiligheid wordt getest, niet verwacht.

Waarom is het een manifest, niet alleen een spec

Dit document is een architectuurspecificatie omdat het definiëert :

  • enkeleafmetingen(ruimtelijk, epistemisch)

  • python

print("", end="")deterministische regels(zone → toegangsrecht)

  • Un taakcontract(Gradle getypeerd, testbaar)

  • Eenreferentie-implementatie(mijn workspace)

Maar het is ook eenmanifestomdat hij een standpunt inneemt in een debat breder: hoe de toegang van een LLM tot data te regelen?

De reactie van de industrie is prompt engineering + guardrails
de post-hoc classifiers. Mijn antwoord is: sorteer uw bestanden in de goede dossiers. De rest is automatisch.

Dit manifest zegt niet "LLMs moeten worden uitgelijnd". Het zegt: "de uitlijning van een LLM op uw beveiligingsregels is een gevolg van uw systeem van bestanden, niet van uw prompt.

Conclusie : Berg je bestanden op, niet je prompts

De LLM-governancematrix die ik zojuist heb beschreven is geen product. Dit is eenarchitectuurspecificatie— en daarom is zij publiceerbaar

Wat het robuust maakt, is dat het niets vraagt aan de LLM. Het vraagt hem Hij/zij vertrouwt niet. Het berust niet op zijn/haar uitlijning, zijn/haar begrip. van het Frans, of zijn goede wil. Het berust op het bestandssysteem — de onderste laag, de meest stabiele laag, de meest geteste laag van de hele stack.

Wanneer ik tegen mijn LLM zeg \"Je kunt alles indexeren in`OSS/, niets in `configuration/, et `office/`alleen als het is geclassificeerd als Vision" — dit is geen instructie. Het is een filter — geïmplementeerd in Kotlin, geverifieerd door 380 tests, uitgevoerd voordat de LLM de gegevens ziet.

Dat is het verschil tussen iemand zeggen "Kijk niet in die lade en sluit de sleutelkast. De gouvernance agent die ik sinds bouw van maanden is de sleutel. De matrix is het plan van het meubel.
