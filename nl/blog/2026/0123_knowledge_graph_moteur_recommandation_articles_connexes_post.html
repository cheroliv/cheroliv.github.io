Dit is een artikel over…​ de configuratie de Kitty Terminal. Het enige gemeenschappelijke punt tussen de twee? Ze zijn gepubliceerd binnen vijftien dagen verschil. Dit is geen aanbeveling. Het is een kalender vermomd als redactioneel

De scène : dinsdag 12 mei, 17:30

Ik lees een van mijn artikelen opnieuw — dat over de Knowledge Graph als hulpmiddel voor het begrijpen van de codebase De inhoud is dicht: knooppunten, randen, gemeenschappen, PlantUML, onboarding. Een artikel 15-minuten leestechniek die mobiliseert`graphify-gradle`, plantuml-gradle, en de concepten van grafentopologie.

Onder aan de pagina stellen de « Verwante artikelen » mij voor:

  1. Een artikel over Firebase Contact Form (0113)

  2. Een artikel over het Eager/Lazy-mechanisme (0108)

  3. Een artikel over de migratie van Gradle script → plugin (0102)

  4. Een artikel over de stapeling van abonnementen Ollama Pro (0120)

Drie van deze vier artikelen hebben geen relatie met de Knowledge Graph. Ze zijn daar omdat ze de laatst gepubliceerde zijn — tijdelijke nabijheid, niet semantische omgeving

Ik bekijk de sjabloon`post.thyme`:

<!-- Articles connexes (liens internes SEO) -->
<th:block th:each="post,postStat : ${published_posts}">
    <th:block th:if="${!post.uri.equals(content.uri) and postStat.index lt 4}">
        ...
    </th:block>
</th:block>

`published_posts`is een chronologische lijst.`postStat.index lt 4`neemt de vier eerste die niet de huidige post zijn. Dat is alles. Geen logica van similariteit. Geen notie van inhoud. Gewoon een lus`for`verkleed als aanbeveling.

Dit is geen bug van JBake. Het is het standaardgedrag van alles. statische sitegenerator: de lijst met berichten is plat en gesorteerd op datum Het sjabloon doet wat het kan met wat het heeft.

Maar dat is geen reden om het te accepteren.

Diagnose: drie soorten relaties die geen sjabloon ziet

Mijn corpus van artikelen — 23 posts in 4 maanden — heeft een rijke structuur die het chronologische sjabloon overschrijft volledig :

  1. Expliciete referenties: ik gebruik`xref:`massief in mijn artikelen.

Artikel 0122 verwijst naar 0106 (knowledge graph) en 0116 (compartimentering epistemisch). De links zijn hard linking redactioneel — ik heb opzettelijk besloten om deze concepten te verbinden

  1. Tags gedeeld : elk artikel heeft`:jbake-tags:`. Het artikel over

Graphify + PlantUML (0105) heeft`gradle, graphify, plantuml, knowledge-graph`. Het artikel over de Knowledge Graph (0106) heeft knowledge-graph, graphify, plantuml. Drie tags gemeenschappelijk van de zeven — 43% overlap

  1. Co‑occurrende genoemde entiteiten : « pgvector », « RAG », « embedding

verschijnen samen in vier verschillende artikelen. « LangChain4j », Ollama », « Gradle-plugin » in zes andere. Dit zijn geen tags verklaard — dit zijn opkomende patronen van het corpus dat alleen een NLP kan detecteren.

De Oplossing: Een Gradle-Pipeline, Geen Live LLM-Aanroep

De eerste verleiding zou zijn om een LLM aan te roepen tijdens de bake: « Voor dit artikel, vindt de drie meest vergelijkbare artikelen in de corpus Doe dat niet.

Een LLM-oproep bij elke`./gradlew bake`kost tijd, geld, en brengt niet-determinisme in jouw build. Het antwoord van de LLM kan Wisselen tussen twee builds zonder dat de inhoud is veranderd. Uw CI wordt niet reproduceerbaar, uw tests worden flaky.

De oplossing is deterministisch: een Gradle-pipeline die de grafiek vooraf berekent. van gelijkheid en hij bewaart het in`graph.json`. De sjabloon leest het resultaat — Nooit activeert hij een berekening.

De Architectuur: Bakery importeert Graphify, Geen Engine

Dit is het belangrijkste architectonische punt. De verleiding zou zijn om de samenwerking bekabelen in`engine/build.gradle.kts`: toegepaste engine graphify voor de scan, bakery voor de bake, en engine maakt de brug tussen beiden

Dit is een anti-patroon. Engine is een verbruikersterminal — het past toe Het implementeert geen zakelijke logica voor plugins. De regel is: De bewijslast ligt bij het proprietair plugin.

Correcte architectuur — Bakery importe Graphify

Het DAG-contract wordt nageleefd: bakery (N2) importeert graphify (N0), N2 > N0, geen inbreuk. Engine (N3) importeert bakery (N2), N3 > N2, OK.

Engine heeft geen enkele regel code die verwijst`graph.json`, relatedPosts, of enige andere notie van gelijkenis. Hij past bakery toe, punt. De samenwerking is intern bij bakery.

De pijplijn: Scan → Graphe → Template

Hier is de volledige pijplijn in drie stappen:

  1. Scan (grafiek) :`graphify-plugin`scant de werkruimte. In zijn/haar

huidige vorm, het detecteert al de`xref:`tussen`.adoc`en de exposeert in`graph.json`zoals edges van type`reference`.
We verrijken het voor de redactionele inhoud : * Parse de JBake-metadata (:jbake-tags:, :jbake-description:) van elke`.adoc`van het blog Bereken de co-voorkomens van tags → randen`tag_cooccurrence`met gewicht * Haal de genoemde entiteiten op uit beschrijvingen via TF-IDF → randen`entity_overlap` * Voeg een sectie toe`blog_articles`in de`graph.json`bestaande

// Extrait de l'enrichissement graphify pour le blog
fun enrichBlogSection(graphJson: File, blogDir: File): GraphJson {
    val articles = blogDir.listFiles { f -> f.extension == "adoc" }
        .map { parseJbakeMetadata(it) }

    val nodes = articles.map { ArticleNode(it.slug, it.title, it.tags) }
    val edges = mutableListOf<GraphEdge>()

    // Couche 1 : xref (déjà fait par scanWorkspace)

    // Couche 2 : co-occurrences de tags
    for (a in articles) {
        for (b in articles) {
            if (a.slug == b.slug) continue
            val common = a.tags.intersect(b.tags)
            if (common.isNotEmpty()) {
                edges.add(GraphEdge(
                    source = a.slug,
                    target = b.slug,
                    type = "tag_cooccurrence",
                    weight = common.size.toDouble() / (a.tags.size + b.tags.size)
                ))
            }
        }
    }

    return graphJson.copy(
        blogArticles = BlogSection(nodes, edges)
    )
}

  1. Bake (bakkerij) : op het moment van`./gradlew bake`, `BakeryPlugin`bed

`graph.json`en lost de gerelateerde artikelen op voor elke post.

// BakeryPlugin — résolution des articles connexes
fun resolveRelatedPosts(
    currentSlug: String,
    graph: GraphJson,
    maxResults: Int = 4
): List<RelatedPost> {
    val edges = graph.blogArticles.edges
        .filter { it.source == currentSlug || it.target == currentSlug }

    return edges
        .sortedByDescending { it.weight }
        .take(maxResults)
        .map { edge ->
            val relatedSlug = if (edge.source == currentSlug) edge.target else edge.source
            graph.blogArticles.nodes.first { it.slug == relatedSlug }
        }
}

gestructureerd in plaats van een platte chronologische lijst.

De sjabloon is hetzelfde — hij weet niet waar de gegevens vandaan komen. Slechts het contract tussen bakery en JBake is gewijzigd :`published_posts`(lijst chronologisch) wordt`relatedPosts`(gewogen kaart door de graaf).

Het badge « reden » (bijv:`xref 0122`, tag:gradle, cluster:pgvector-rag) verklaar aan de lezer waarom dit artikel gerelateerd is. Dit is niet alleen transparantie — het is pedagogie over de topologie van uw eigen inhoud. </think>

Fallback chronologisch

Si `graph.json`is afwezig (build local zonder voorafgaande scan, eerste implementatie, CI die nog niet heeft geïntegreerd de scan Graphify), het sjabloon moet gratieus degraderen:

fun resolveRelatedPosts(currentSlug: String, graph: GraphJson?): List<RelatedPost> {
    if (graph != null && graph.blogArticles != null) {
        return resolveFromGraph(currentSlug, graph)
    }
    // Fallback chronologique — même comportement qu'aujourd'hui
    logger.warn("[bakery] graph.json absent — fallback chronologique")
    return resolveFromChronology(currentSlug)
}

Het standaardgedrag is identiek aan het huidige gedrag. De aanbevelingsmotor is een progressieve verbetering — geen brekende wijziging.

De opkomende ontologie : wanneer artikelen zich verzamelen zonder elkaar te kennen

De meest interessante laag is de derde: de emergente ontologie. Artikelen die niet geciteerd worden, die niet dezelfde tags hebben, maar die praten over hetzelfde zonder het te weten.

Laten we een concreet voorbeeld nemen. Drie artikelen uit mijn corpus :

  1. 0119 — Benchmark DGX Spark vs Cloud-abonnement LLM

  2. 0121 — Gradle-plugin voor het besturen van twee Ollama Pro-instanties

  3. 0122 — Verhouding Efficiëntie 27x 45x Vloot AI-experts

Deze drie artikelen hebben geen xref onderling. Hun tags ne se overlappen slechts 20 % (« ollama », « llm » gemeenschappelijk). Maar een lichtgewicht NLP Op de beschrijvingen onthult een duidelijk cluster: 'kosten', 'abonnement', cloud », « GPU », « API-sleutel », « Ollama Pro », « efficiëntie », « verhouding

Ze vormen een ontologische cluster: de economie van de LLM self-hosted vs cloud. Deze cluster wordt nergens gedeclareerd. Hij ontstaat uit het corpus.

Het NLP is bewust licht — TF-IDF + cosine similarity op de beschrijvingen. Geen behoefte aan BERT, geen behoefte aan een taalmodel. Het corpus bestaat uit 23 artikelen, de similariteitsmatrix past in een JSON-bestand van 50 KB.

De kracht van NLP komt niet voort uit de verfijning van het algoritme, maar van de grootte van het corpus en van de kwaliteit van de beschrijvingen. Een `:jbake-description:`goed geschreven van 150 tekens bevat meer van signaal voor TF-IDF dat een volledig artikel van 3000 woorden.

Het patroon is: plugin N2 is de hub van zijn eigen afhankelijkheden Engine N3 is geen hub — het is een terminal die hubs toepast.

Wat We Winnen(En Wat We Niet Winnen)

Het belangrijkste voordeel is redactioneel, niet technisch:

Voor Na

Gerelateerde artikelen = 4 recente berichten

Gerelateerde artikelen = top 4 op gewicht in de Knowledge Graph

Lezer leest RAG → aanbeveling Kitty Terminal

Lezer leest RAG → aanbeveling pgvector, chunking, vector store

Geen transparantie over het waarom

badge`xref 0122`, tag:gradle, `cluster:rag`zichtbaar

JBake standaard, geen inspanning, geen waarde

deterministische, reproduceerbare, testbare Gradle-pipeline

Geen leercurve voor de lezer

De lezer ontdekt de topologie van mijn inhoud

Wat men niet verdient:

  • Dit is geen « echte » aanbevelingsmotor (geen samenwerking

filtering, geen A/B-test, geen feedbacklus)

  • De kwaliteit hangt af van de rijkdom van de JBake-metagegevens — als uw

beschrijvingen zijn leeg, TF-IDF ziet niets

  • De NLP is offline — nieuwe artikelen worden alleen geclusterd op de

volgende scan (dat is goed: de build blijft deterministisch)

Perspectieven: De blog als publiek Knowledge Graph

Deze functionaliteit opent een breder perspectief : wat als`cheroliv.com` werd hijzelf een knowledge graph navigable ?

Artikels zijn knooppunten. Tags zijn gemeenschappen. xref zijn de ribben. De lezer leest niet meer een geïsoleerd artikel — hij navigeert in een kennisgraf waarvan het huidige artikel het instappunt is.

Stel je een homepage voor die niet de chronologische lijst weergeeft van de laatste berichten, maar een kaart van het corpus : ontologische clusters, pivoterende artikelen (die de meeste randen hebben), leespaden aanbevolen (« Als je het artikel over Graphify leuk vond, lees dan verder dat over het Knowledge Graph als hulpmiddel voor begrip )

Het is geen blog meer. Het is een semantische atlas.

En dit is geen sciencefiction. De`graph.json`bestaat al. Hij mist alleen de navigatie-interface.

Conclusie: Het bestandssysteem weet wat de template negeert

Wat ik op dinsdagavond heb ontworpen, is de vervanging van een heuristiek. luie (de chronologische volgorde) door een getrouwe weergave van de structuur van mijn corpus (het Knowledge Graph).

De sjabloon`post.thyme`verandert niet. Wat verandert, is wat we hij geeft hem te eten. Eerder: een Java-lijst gesorteerd op`date`. na : een gewogen graaf afkomstig uit drie analyselagen — xrefs, co-occurrences tags, en opkomende ontologie via NLP

De cirkel is rond. graphify scant de workspace. Bakery leest het grafiek en voedt de sjabloon. De lezer ziet aanbevelingen relevant. En engine — de dirigent — weet zelfs niet dat Alles bestaat.

Dat is het, de goede architectuur. Elk plugin doet één ding. En de consumententerminal hoeft niet te weten hoe.
