Optimaliseren van het Gradle-taakbeheer met Kotlin DSL en buildSrc

Gepubliceerd op 11 July 2025

De automatisering van buildtaken is cruciaal voor elk softwareproject, en Gradle, met zijn Kotlin DSL, biedt een uitzonderlijke flexibiliteit. Tijdens ons gesprek hebben we onderzocht hoe we de buildlogica kunnen centraliseren en hergebruiken, met name voor testrapporten, door gebruik te maken vanallprojects, buildSrc, en aangepaste taken in Kotlin.

Centraliseer de configuraties met allprojects en `subprojects

De blokken`allprojects` et `subprojects`in uw`build.gradle.kts`de wortels zijn essentieel om gemeenschappelijke configuraties toe te passen in uw multi-module project

*allprojects { …​ }: Pas de configuratie toe op dehoofdproject en aan alle onderprojecten thereof. Ideaal om een te definiëren`group`, een`version`, of enkele`repositories`gemeenschappelijk. *subprojects { …​ }: Pas de configuratie toeuitsluitend voor de subprojecten, zonder het hoofproject. Perfect voor het toepassen van modulespecifieke plugins (zoals`java` ou kotlin-jvm) of gemeenschappelijke afhankelijkheden voor uw bibliotheken.

Hier is een illustratief voorbeeld:

// build.gradle.kts (projet racine)
plugins {
    base // Appliqué au projet racine
}

allprojects {
    group = "com.example"
    version = "1.0.0"

    repositories {
        mavenCentral()
    }

    tasks.withType<org.gradle.api.tasks.testing.Test> {
        useJUnitPlatform() // Configuration commune des tests pour tous les projets
    }
}

subprojects {
    apply(plugin = "java")
    apply(plugin = "org.jetbrains.kotlin.jvm")

    dependencies {
        implementation("org.jetbrains.kotlin:kotlin-stdlib-jdk8")
    }

}

\==buildSrc: Het Zwitserse zakmes van de Build-logica

Wanneer de logica van uw taken complex wordt of moet worden hergebruikt,buildSrcest de voorkeursoplossing. Het is een speciaal Gradle-module dat wordt gecompileerd vóór de belangrijkste build-scripts, waardoor zijn klassen beschikbaar zijn op het classpath van uw hele build.

\=== Waarom gebruiken`buildSrc`voor de taken ?

  • Herbruikbaarheid: Een gedefinieerde taak in`buildSrc`kan worden toegepast op elk project van de build.

  • Organisatie: Centraliseert de buildcode, waardoor deze schoner en onderhoudsvriendelijker wordt.

  • Type Safety en Autocompleet: De Kotlin-code in`buildSrc`wordt gecompileerd, biedt foutcontrole en automatische aanvulling van uw IDE, waardoor de ontwikkelervaring wordt verbeterd.

\== Aanmaken van abstracte rapporttaken

Om de testrapporten te beheren, hebben we een modulaire aanpak ontworpen met behulp van een abstracte taakklasse in`buildSrc`. Volgens uw behoeften, deze klasse kan erven van`DefaultTask` ou de Exec.

\=== Abstracte taak`OpenTestReportTask`(erfend van`DefaultTask`)

Deze aanpak wordt aanbevolen als je een aangepaste Kotlin-logica nodig hebt die interactie heeft met het bestandssysteem of andere Gradle-API’s, en daarna een externe opdracht uitvoert.

[source,kotlin]

package com.yourpackage

import org.gradle.api.DefaultTask import org.gradle.api.tasks.Input import org.gradle.api.tasks.TaskAction import java.io.File

abstract class OpenTestReportTask : DefaultTask() {

----
----
init {
    group = "verification"
    description = "Opens a test report in Firefox."
    dependsOn("check") // Assure que les rapports sont générés
}

@get:Input
abstract var reportPath: String

@TaskAction
fun openReport() {
    val separator = File.separator
    val reportFile = project.layout.projectDirectory.asFile.toPath()
        .resolve(reportPath.replace("/", separator))
        .toAbsolutePath()
        .toFile()

    if (!reportFile.exists()) {
        logger.warn("Report file does not exist: $reportFile. Ensure 'check' ran.")
        return
    }

    project.exec {
        commandLine("firefox", "--new-tab", reportFile.absolutePath)
    }
    logger.lifecycle("Opened test report: ${reportFile.absolutePath}")
}
----

## }

Deze klassen erven van de abstracte taak en definiëren het specifieke pad van het rapport.

\=== Registratie van de taken

In de`build.gradle.kts`van uw hoofdproject :

## [source,kotlin]

\== Abstracte taak`AbstractJbakeExecTask`(ervend van`Exec`)

Als je taak vooral bestaat uit het uitvoeren van een externe opdracht met variabele argumenten, erf dan rechtstreeks van**Exec**is directer.

## [source,kotlin]

abstracte klasse AbstractJbakeExecTask : Exec() {

\== Zichtbaarheid van taken`buildSrc`

De taken en klassen die u definieert in**buildSrc**zijn :

***Zichtbaar en bruikbaar**door alle projecten van je hoofd-build (root en sub-projecten). Daarom kun je gebruiken`com.yourpackage.ReportUnitTestsTask`in`allprojects { ... }`. ***Niet uitvoerbare**direct als taken van buildSrc (bijvoorbeeld,`gradle :buildSrc:reportTests`zou niet werken als de taak niet specifiek wordt geregistreerd in`buildSrc/build.gradle.kts`).`buildSrc`is een compilatiemodule, geen uitvoerbaar applicatiemodule voor deze taken van de hoofdbuild.

\=== een rapport uitvoeren voor de tests van`buildSrc`zichzelf

Si `buildSrc`heeft zijn eigen tests en genereert rapporten, u kunt een rapporttaak direct registreren in`buildSrc/build.gradle.kts` :

## [source,kotlin]

plugins { `kotlin-jvm` }

dépôts { mavenCentral() }

tasks.withType\<Test\> { useJUnitPlatform() reports.html.outputLocation.set(layout.buildDirectory.dir("reports/tests")) }

import com.yourpackage.ReportJbakeTestsTask // Importeer uw taakklasse

tasks.register\<ReportJbakeTestsTask\>("reportBuildSrcTests") { // Het pad is al gedefinieerd in de klasse, het zal naar de buildSrc-rapporten wijzen }

U kunt vervolgens uitvoeren :`./gradlew :buildSrc:test`gevolgd door`./gradlew :buildSrc:reportBuildSrcTests`.

Door deze praktijken te volgen, bouw je Gradle-buildsystemen in Kotlin DSL die niet alleen krachtig zijn, maar ook buitengewoon modulair, onderhoudbaar en gemakkelijk te begrijpen.
