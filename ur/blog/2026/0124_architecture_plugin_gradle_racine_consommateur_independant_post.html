آپ ایک گرائیڈل پلاگِن ریپوزٹری کلون کر رہے ہیں۔ آپ ایک ٹرمنل کھول رہے ہیں۔ آپ کیا ٹائپ کر رہے ہیں؟ پھر؟./gradlew tasks, بالکل. لیکن کون سا فولڈر؟ جڑ؟ سب‑ماڈیول؟ کیا پہلے ایک README پڑھنا چاہیے تاکہ بنانے کے طریقے کا علم ہو؟ اگر آپ جھجکاتے ہیں تو کیا یہ نہیں ہوگا؟ ایک سیکنڈ میں، پروجیکٹ کی مِعماری ٹوٹ گئی ہے۔

یہ ہے کہ میں اس مسئلے کو ایک بار لیے سب کے لئے حل کیا — اور کیون یہ پターن آج میرے تمام گریڈل پلاگنز کی شناخت میں`foundry/public/`.

مسلّہ : تین معمارتیں جنہوں نے مجھے وقت ضائع کر دیا

موجودہ پٹرن تک پہنچنے سے پہلے، میں تین طریقوں کے درمیان ڈھونڈ رہا تھا کلاسیک طریقے جن سے گریڈیل پلاگن کو منظم کیا جاتا تھا۔ ہر ایک کا ایک قاتل عیب۔

اختیار 1: ایسولیٹڈ پلاگین (dogfooding نہیں)

پروژکٹ صرف پلاگ‑ن ہی شامل ہے۔ استعمال کی کوئی مثال نہیں۔ کوئی پروجیکٹ جو اسے استعمال کرتا ہے۔ اسے ٹیسٹ کرنے کے لیے، ایک بیرونی پروجيٹ بنانا پڑتا ہے، y پلاگین کو ذریعے رجح کریں`mavenLocal`یا ایک کمپوزٹ بنڈ، اور صرف یہاں جانچ کریں کہ یہ چل رہا ہے۔

$ git clone mon-plugin
$ cd mon-plugin
$ ./gradlew build          # le plugin compile
$ # ... et maintenant ? comment je l'essaie ?

گریڈیل پلاگائن جس میں استعمال کا کوئی مثال نہیں، ایک کتابخانه جس میں انٹیگریشن ٹیسٹس. آپ کبھی نہیں جانتے کہ آخری تبدیلی صارف کے تجربے کو خراب کر دیا

اختیار 2 : کلاسیک مونوریپو (include(":plugin"))

گریڈل`init`پیدا کرتا ہے`settings.gradle.kts`ساتھ`include("plugin")`. رُوٹ اور سب-ماڈیول ایک ہی ڈیمون اور ایک ہی کنفیگریشنز کو شیئر کرتے ہیں، یہے catalogue۔ مفید، لیکن جوڑا ہوا۔

.
├── settings.gradle.kts   → include("plugin")
├── build.gradle.kts      → plugins { id("mon-plugin") }
├── plugin/
│   └── build.gradle.kts  → java-gradle-plugin
└── gradle/
    └── libs.versions.toml

رکاوٹ :

  • جڑچاہیےGradle کی وہی ورژن رکھنا جس ورژن کا سب ماڈول استعمال کرتا ہے۔

  • `libs.versions.toml`ہے شیئر — ورژن کیٹالوگس مشترک، انحصاریات

جinho ایک مाडول سے دوسرے ماضول تک بھتے ہیں

  • پلاگن کو جڑ سے مستقل طور پر بنانا ممکن نہیں۔

  • سی آئی کو دونوں ماڈیول بنانے ہیں، اگرچہ صرف پلاگین بدل گیا ہے۔

اختیار 3 : کامپوزٹ بيلڈ (includeBuild())

ہم ان دو چیزوں کو الگ الگ Gradle بنڈس میں علیحدہ کرتے ہیں اور انہیں اس کے ذریعے جوڑتے ہیں includeBuild("mon-plugin")`میں`settings.gradle.kts.

یہ پہلے سے بہتر ہے۔ پلاگ ان کا بِلڈ الگ ہو گیا ہے۔ لیکن صارف اس کو واضح طور پر بیرونی ڈیلڈ کا حوالہ دینا چاہیے — اور اس کا آؤٹ پوٹ `./gradlew tasks`جذور کی درست تنظیم پر انحصار کرتا ہے مکمل. کلوننگ صفر کانفیگریشن نہیں ہے: جاننا ضروری ہے کہ پلاگ ان الگ فاؤلڈر میں ہے، جو روت اس کی حوالہ دیتا ہے، او غیر۔

.
├── settings.gradle.kts   → includeBuild("plugin-build/")
├── build.gradle.kts      → plugins { id("mon-plugin") }
└── plugin-build/
    ├── settings.gradle.kts
    └── build.gradle.kts

میں بہتر کی تلاش کر رہا تھا۔ بہت بہتر۔

حل: دو مستقل بیلڈز، صرفی

یہ وہ پٹرن ہے جو میں نے سرانجام میں اپنا لیا :

.
├── settings.gradle.kts          ← racine consommateur
├── build.gradle.kts              ← 3 lignes : apply plugin + dogfood
├── gradle/
│   └── libs.versions.toml        ← catalogue du consommateur
├── {name}-plugin/                ← BUILD INDÉPENDANT
│   ├── gradlew                    ← son propre wrapper
│   ├── settings.gradle.kts        ← rootProject.name = "{name}-plugin"
│   ├── build.gradle.kts           ← java-gradle-plugin, signing, publish
│   ├── gradle/
│   │   ├── libs.versions.toml     ← catalogue du plugin
│   │   └── wrapper/
│   ├── src/                       ← sources du plugin
│   ├── .agents/                   ← gouvernance agent
│   └── *.adoc                     ← AGENT, PROMPT_REPRISE, snapshot, etc.
└── site.yml / slides-context.yml / ...   ← configs dogfood

چابی :`{name}-plugin/`ہے ایک پروجیکٹ گریڈیل مکمل اور خودمختار. اس کا apna wrapper، اس کا apna settings، اس کا apna catalogue کا نسخہ. یہ خود کو کلون کرتا ہے، خود کو بناتا ہے، خود کو آزماتا ہے اور خود کو شائع کرتا ہے، رُوت کے بغیر اس کی وجود کا علم رکھو

رُوٹ، وہ صرف ایک کام کرتا ہے: پلاگین لاگو کریں۔

    alias(libs.plugins.bakery)
}

repositories {
    mavenLocal()
    mavenCentral()
}

bakery { configPath = file("site.yml").absolutePath }

کیوں یہ معمارتی نے مجھے جیت لیا؟

تین فائدے جو، مل کر، « ڈپلیکیشن» کی لاگت کے برابر ہیں :

نایٹیو ڈاگ فودنگ، فوری فیڈبیک

گریڈیل پلاگین کا بہترین ٹیسٹ اس کا استعمال کرنا ہے۔ مockeڈ یونٹ ٹیسٹ نہیں. نہیں ایک`GradleRunner`ایک پروجیکٹ کے ساتھ ٹیسٹ کا۔ ایک سچ بِلڈ جو پلاگ‑إن لاگو کرتا ہے سچ فائله‌وں پر

$ git clone bakery-gradle
$ cd bakery-gradle
$ ./gradlew bake    # ← le plugin est exercé immédiatement

اگر پلاگین ٹوٹا ہے، جڑ بناؤ اسے کہتا ہے۔ جنے کی ضرورت نہیں۔ باہری ٹیسٹ پروجیکٹ ڈھونڈنا۔ ڈگ فُڈنگ پہلا ہے۔ ایک نئے مشارکت کنندہ کی لانس کرنے والی ٹاسک۔ یہ آخری سموک ٹیسٹ ہے۔

قاعدہ سادہ ہے: اگر جڑ کامپائل ہوتی ہے اور`./gradlew tasks` دکھاتا ہے آپ کے پلاگین کے کام، پلاگین فعال ہے۔ کوئی تعجب نہیں پروڈکشن میں.

2. زیرو-کنفیگ کلوننگ

Un `git clone && ./gradlew tasks`اور نئے داخلہ کرنے والا سب کچھ دیکھتا ہے کوئی شيء کنفیجر کیے بغیر چلنا۔ ال`build.gradle.kts`جڑ ہے پلاگین ka Installation ka zombie documentation`site.yml`کے ساتھ متوقع کنفیگری دکھاتا ہے.

الیکسج کے ساتھ متقابل کریں : تین پاراگرافوں کا ایک README جس میں وضاحت کریں builder پلاگین کیسے بنائیں اور builder پروژیکٹ کیسے بنائیں ٹیسٹ کا۔ ایک نیا مشارکت کنندہ README کو ڈائیگونل طور پر پڑھتا ہے, غلط کرتا ہے، ایک اشو کھولتا ہے — جہاں کے ملومات ہو سکتا ہے ہونا قابلِ eseguibile.

سب سے مضبوط دستاویزات وہ نہیں ہے جو پڑھی جاتی ہے. یہ وہ ہے جو ہمنفذ. جڑ بنائی وثائق ہے پلاگ اِن کا قابلِ esegu.

3. منافذ بنائیں، مستقل CI

پلاگ ان کا خود کا گریڈیل وریپر ہے، خود کا زندگی کا دور ہے، اپنے ٹیسٹس. آپ سکتے ہیں:

  • پلاگن میں Gradle کو اپ گریڈ کریں، جڑ کو چھوئے بغیر

  • پلاگین میں ایک انحصار شامل کریں تاکہ وہ روت میں لیک نہ ہو

  • پلاگین کو ٹوٹنا بنیادی بنڈ پر اثر ڈالے بغیر (جس وقت آپ

ٹوٹا ہوا نسخہ شائع نہ کریں)

  • ایک CI رکھنا جو پلاگائن کو build/test کرے، اور دوسری جو اسے استعمال کرے

جب میں اس ساخت کو کسی کو دکھاتا ہوں، پہلا ردعمل اکثر یہ ہوتا ہے : « تم کے دو`gradlew`, دو`settings.gradle.kts`, دو`libs.versions.toml`— یہ نقل ہے !

ہاں۔ اور نہیں۔

ڈپلیکیشن » کا مطلب ہے ایک ہی معلومات کو دو جگہوں پر بنانا۔ یہاں، یہ دو مختلف فائل ہیں جو دو مختلف مقاصد کے لیے ہیں : پلاگ ان کا کیٹالوج (30+ انحصارات بِلڈر کے لیے) اور کیٹالوج جڑ سے (2-3 انحصارات استعمال کرنے کے لیے). پلاگین کا ورےپر (ترقی کے لیے قفل شدہ ورژن) اور جڑ کا واپر (امکان پر مختلف ورژن، پلاگن کے مشق کے لیے).

یہ ڈپلیکیشن نہیں ہے۔ یہ الگ کرنے کا ذمہ داریاں بیلڈ نظام پر لاگو. ہر بیلڈ ایک چیز کرتا ہے، اور صرف ایک۔ جڑ استعمال کرتی ہے۔ پلاگین خود بنتا ہے۔

لاگت؟ ایک آرڈر`publishToMavenLocal`پلاگین کے بیلڈ کے درمیان اور جڑ کا بیلڈ۔ فائدہ؟ معمارتی صفائی جو ڈاؤن اسٹریم ڈیبگنگ کے گھنٹے بچاتا ہے

میں اس نمونے کو ڈپلوائی کرنے کے بعد سے`bakery-gradle`, plantuml-gradle, codebase-gradle, اور دیگر پلاگینوں کا`foundry/public/, میں نہیں کبھی نہیں جھجھکا ایک ٹرمنل کھلتے وقت میں میرے ایک ریپوزٹری. پہلا انعکاس —./gradlew tasks`— ہمیشہ چلتا ہے، ہمیشہ دیتا ہے اچھی کاروں، اور وہ فوراً بتا دیتا ہے کہ ہر چیز صحت مند ہے۔
