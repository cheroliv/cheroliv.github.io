منظر: ایک JHipster پروجیکٹ، ایک بیلڈ جو اب لاڈ نہیں ہو رہا

پروجیکٹ`edster`یہ 2024 میں جنریٹ کردہ JHipster ایپلیکیشن ہے۔ جڑو بنڈ سکرپٹ`build.gradle`یہ ماہوں تک مستقر رہا۔ پھر ہم نئی ورژن میں اپ گریٹ کرنے کا فیصلہ کرتے ہیں :

حصہ

قصد شدہ ورژن

گریڈل

9.4.1

جاوا

21.0.11-tem (Eclipse Temurin)

JHipster

8.x (فریم ورک`tech.jhipster:jhipster-framework:8.11.0`)

Spring Boot

3.4.5

کاتلن

2.3.0

ڈاکر انجن

29.4.1 (API 1.54)

جاوے کی ورژن تبدیلی SDKMAN کے ذریعے ہوتی ہے:

sdk use java 21.0.11-tem

پہلا لاونچ:

$ ./gradlew build --no-daemon

FAILURE: Build failed with an exception.

* Where:
Build file '/home/.../edster/build.gradle' line: 18

* What went wrong:
An exception occurred applying plugin request [id: 'jhipster.cucumber-conventions']
> Failed to apply plugin 'jhipster.cucumber-conventions'.
   > Could not create task ':cucumberTest'.
      > Could not create task ':consoleLauncherTest'.
         > Could not set unknown property 'reportsDir' for task ':consoleLauncherTest'

ہم بیلڈ اسکرپٹ کے لوڈ ہونے سے بھی نہیں اٹھ سکتے۔ مسئلہ یہ ہے کہ`buildSrc/src/main/groovy/jhipster.cucumber-conventions.gradle`.

غلطی 1 : متغیر الوهمی `reportsDir

اسکریپٹ`jhipster.cucumber-conventions.gradle`شامل ہے :

tasks.register('consoleLauncherTest', JavaExec) {
    dependsOn(testClasses)
    String cucumberReportsDir = file("$buildDir/reports/tests")
    outputs.dir(reportsDir)           // <-- reportsDir n'existe PAS
    classpath = sourceSets["test"].runtimeClasspath
    main = "org.junit.platform.console.ConsoleLauncher"
    // ...
}

معین متغیر ہے`cucumberReportsDir`. جسے استعمال کیا گیا ہے`reportsDir`-- جس کو کहीं بھی معین نہیں کیا گیا۔

تصحیح:`outputs.dir(cucumberReportsDir)`

غلطی 2 : main = "…​" Gradle 9 میں موجود نہیں ہے

فوری دوبارہ شروع :

Could not set unknown property 'main' for task ':consoleLauncherTest' of type org.gradle.api.tasks.JavaExec.

Gradle 9 خصوصیت کو حذف کرتا ہے`main`کے فائدے کے لیے`mainClass`کاموں پر`JavaExec`.

تصحیح:`mainClass = "org.junit.platform.console.ConsoleLauncher"`

غلطی 3 : sourceCompatibility اب پروเจکٹ کی خاصیت نہیں ہے۔

نئی خرابی :

Could not set unknown property 'sourceCompatibility' for root project 'edster' of type org.gradle.api.Project.

رُوٹ سکرپٹ میں تھا:

sourceCompatibility=17
targetCompatibility=17

گریڈل 9 انخصوصیات جڑ کی سطح پر حذف کرتا ہے۔ انخصوصیات ایک بلوک میں رہنا چاہیے`java`.

اصلاح:

java {
    sourceCompatibility = JavaVersion.VERSION_21
    targetCompatibility = JavaVersion.VERSION_21
}

غلطی 4 : Groovy کی تین آپیریینڈز والی تصدیق

پرانا سکرپٹ شامل تھا :

assert System.properties["java.specification.version"] == "17" || "21" || "24"

گراووی میں،"21" et "24"`سچے سٹرنگز ہیں. Expression حل ہوتا ہے میں(…​ == "17") || true || true`, جو ہمیشہ سچ ہے — لیکن سینٹکس غلط ہے مطلوب سخت استعیان کے لیے

صحیحی(empty)

assert System.properties["java.specification.version"] in ["17", "21", "23", "24"]

غلطی 5 : ضمنی انحصار compileKotlin → `openApiGenerate

билڈ پیشروج ہو رہا ہے۔ کاتلن کامپائلیشن کامیاب ہو گئی۔ پھر :

Task ':compileKotlin' uses this output of task ':openApiGenerate'
without declaring an explicit or implicit dependency.

Gradle 9 انحصاراتِ ضمنی کے کاموں کے درمیان کو رد کرتا ہے۔ کیونکہ`compileKotlin`او جنریٹ شدہ منابع کے ذریعے پڑھتا ہے`openApiGenerate`, لینک کا اعلان کرنا ضروری ہے۔

تصحيحاندر`build.gradle` :

afterEvaluate {
    tasks.named("compileKotlin").configure {
        dependsOn(tasks.named("openApiGenerate"))
    }
}

Le `afterEvaluate`ضروری ہے کیونکہ`openApiGenerate`یہ OpenAPI Generator پلاگین ایک ایکسٹینشن ہے اور سیٹ اپ کے مرحلے میں مستقیم قابل رسائی ہونے والا کام نہیں ہے۔

غلطی 6 : generateGitProperties ٹوٹ جاتا ہے FilterOutputStream.write() پر

جاوے کی کامپائلیشن کامیاب ہو جاتی ہے۔ وسائل پر عمل کیا جاتا ہے۔ بعد میں :

> Task :generateGitProperties FAILED

No signature of method: java.io.FilterOutputStream.write() is applicable for argument types: (Integer) values: [103]

پلاگ ان`gradle-git-properties`ورژن 2.5.0 Java 21 / گریڈل 9 کے ساتھ متوافق نہیں ہے۔ اندرونی بگ کال کرنے کی کوشش کر رہا ہے۔`write(int)`Groovy کے ذریعے ایک سٹریم جس نے اسے بند کر دیا

تصحیحمیں`gradle.properties` :

gitPropertiesPluginVersion=2.5.7

آخر کار : Testcontainers صحنے میں آتا ہے

اب تک، یہ صرف 'build script debugging' تھا۔ ہر غلطی Gradle 9 یا Java 21 کی ناسازگوشی thi بیلڈ سکرپٹس میں۔ اوپر دیے گئے چھ ٹھیک کرنے کے بعد،`./gradlew assemble`کامیابی سے پاس کرتا ہے

لیکن`./gradlew build`یہ ٹیسٹس بھی چلاتا ہے اور کیوکربر ٹیسٹس ایک موقت پوسٹگریSQL চালانے کے لیے Testcontainers استعمال کرتے ہیں۔

مرحلہ 1 : ڈاکر-جیوا ٹریک

پہلا رفلیکس: ٹیسٹ کونٹینرز کے استعمال ہونے والی جاووا ڈوکر کلائنٹ API کی ورژن بھیجتا ہے۔1.32`اس کے HTTP ہینڈشیک میں، لیکن Docker Engine 29.4.1 کم از کم طلب کرتا ہے`1.40. مشکل کلائنٹ کے سطح پر ہے، ڈیمون پر نہیں۔

Testcontainers 1.20.6 سے حل کردہ docker-java ورژن کی تصدیق :

$ ./gradlew dependencies --configuration testRuntimeClasspath | grep docker-java

+--- com.github.docker-java:docker-java-api:3.4.1
+--- com.github.docker-java:docker-java-transport:3.4.1

docker-java 3.4.1, Testcontainers 1.20.6 سے منسوب. داکر-جا کی آخری عامی ورژن 3.5.1 ہے. ہم ورژن اپ گریڈ کرنے کی کوشش کرتے ہیں، ذریعے`resolutionStrategy`بلاک میں`configurations` de build.gradle:

configurations {
    all {
        resolutionStrategy.eachDependency { details ->
            if (details.requested.group == "com.github.docker-java"
                && details.requested.name.startsWith("docker-java")) {
                details.useVersion("3.5.1")
            }
        }
    }
}

بیَلڈ کی ری لاينچ۔ یہی خطا:`client version 1.32 is too old`.

Gradle کیش کی تصدیق: JARs کامیابی سے دوبارہ ڈاؤنلوڈ کر لیے گئے ہیں، لیکن خرابی مست ہے۔ docker-java 3.5.1 ابھی بھی بھیج رہا ہے`1.32`. یہ ورژن اس لیے Docker Engine 29.4.1 کے لیے کافی نہیں ہے۔

صافی کرنے کا عملGradle کیش کو مکمل طور پر صاف کریں، صرف یقینی کے لیے

rm -rf ~/.gradle/caches
rm -rf /path/to/project/.gradle

پرج کے بعد مکمل ری استارت۔ ایک ہی غلطی۔

مرحلہ 2 : وéb تلاش اور GitHub کی بريكرumb

docker-java 3.5.1 کافی نہیں ہے. اب صرف یہ دیکھنا باقی ہے کہ کیا کسی نے اس Exact مسئلے کا سامنا کیا ہے۔

testcontainers-java اور docker-java کے مسائل پر مستهدف شدہ تلاش :

site:github.com/testcontainers "client version 1.32 is too old"
site:github.com/docker-java "client version 1.32" Docker Engine 29

پہلے فوری نتائج :

  • testcontainers-java#11210—[Bug]: client version 1.32 is too old. Minimum supported API version is 1.44

  • testcontainers-java#11212—[Bug]: Docker 29.0.0 could not find a valid Docker environment

  • testcontainers-java#11491—[Bug]: Incompatibility in Ubuntu Github runners with Docker Engine 29.1.*

برانڈ کرام واضح ہے: Docker Engine 29.x نے اپنی کم سے کم API ورژن بڑھا دی تک`1.24`(قدیمی عيب) کی طرف`1.40`. Testcontainers 1.20.x docker-java 3.4.x استعمال کرتا ہے جو API کی ورژن مذاکرت کرنے کیلئے بھیجتا ہے`1.32`. ڈیمَن خوشِ اخلاق سے لیکن سختانه سے انکار کرتا ہے۔

mas’alah #11491 mein, ek muhawil jawab deta hai:

_ ہائے، میرا پروژیکٹ ورژن 2.0.3 کے ساتھ GH رنر پر انجن 29.1 کے ساتھ چل رہا ہے اور یہ کام کرتا ہے۔ کیا آپ سب براہِ مہربانی چیک کر سکتے ہیں کہ ورژن کے ساتھ کوئی تصادم نہیں ہے؟ براہِ کرم، یاد رکھیں کہ تمام ماڈیولز کا پیشوند لگایا گیا تھا`testcontainers-. لہذا، ورژن 2.x سے شروع کرتے ہوئے ہم …​ سے منتقل ہوگئے`postgresql to testcontainers-postgresql _

یہ جواب شامل ہےدو اہم معلومات:

  1. Testcontainers 2.0.3+ مسئلے کا حل کرتا ہے

  2. مائوڈولز ہوئے ہیںپرفکس کے ساتھ بدل دیے گئے `testcontainers-

نام بدلنا سخت ہے۔ Testcontainers 2.x میں، کونی بھی پرانا نام اس نام کے تحت کار نہیں کرتا:

بدون تغيير

پہلی کوشش : Testcontainers BOM 2.0.5 لاگو کریں اور نئے آرٹیفیکٹ ناموں میں`build.gradle`.

dependencies {
    testImplementation platform("org.testcontainers:testcontainers-bom:2.0.5")
    testImplementation "org.testcontainers:testcontainers-postgresql"
    testImplementation "org.testcontainers:testcontainers-jdbc"
    testImplementation "org.testcontainers:testcontainers-junit-jupiter"
    testImplementation "org.testcontainers:testcontainers"
}

./gradlew build

FAILURE: Could not find org.testcontainers:jdbc:2.0.5.
Could not find org.testcontainers:junit-jupiter:2.0.5.

testcontainers-bom BOM کافی نہیں ہے۔کیوں؟ کیونکہ Spring Boot 3.4.5 اپنی خود کی BOM (اعتمادوں کی نظام) ظاہر کرتا ہے (spring-boot-dependencies) جوجیتاٹیسٹ کونٹینرز بی او ام کے بارے میں مترابط حل میں. سپرینگ بُوٹ سیٹ کرتا ہے.testcontainers à 1.20.6، اسلیے سب artifacts jo wazahat se Spring Boot BOM mein nahi hain (jaise naye`testcontainers-*) پرانے نام کی طرف حل کرتے ہیں`1.20.6-- jo is version mein ab nahi rehtay.

جائزہ لیتے وقت`dependencies --configuration testRuntimeClasspath`, پاتا ہے :

+--- org.testcontainers:testcontainers -> 1.20.6 (*)
|    \--- org.testcontainers:testcontainers:2.0.5 -> 1.20.6

Le →`indique بدل کی اشارہ دیتا ہے: Testcontainers 2.0.5 مطلوب ہے، لیکن Spring Boot مجبور کرتا ہے`1.20.6.

آخری ترمیممیں`build.gradle`:

configurations {
    all {
        resolutionStrategy.eachDependency { details ->
            if (details.requested.group == "com.github.docker-java"
                && details.requested.name.startsWith("docker-java")) {
                details.useVersion("3.7.1")
            }
            if (details.requested.group == "org.testcontainers"
                && details.requested.name == "testcontainers") {
                details.useVersion("2.0.5")
            }
        }
    }
}

dependencies {
    testImplementation platform("org.testcontainers:testcontainers-bom:2.0.5")
    testImplementation "org.testcontainers:testcontainers-jdbc"
    testImplementation "org.testcontainers:testcontainers-junit-jupiter"
    testImplementation "org.testcontainers:testcontainers-postgresql"
    testImplementation "org.testcontainers:testcontainers"
    // ... autres dépendances Spring Boot
}

Le `resolutionStrategy.eachDependency`یہ بوم کو باپس کرنے کا ایک صرف طریقہ ہے`spring-boot-dependencies`Spring Boot پلاگین کے ذریعے منظم. مساوات کا ٹیسٹ پر`details.requested.name == "testcontainers"`یہ عمداً محدود ہے: ہم صرف کور ماڈیول کو زبردست کرتے ہیں۔ ماڈیولات`testcontainers-*`انہوں نے Testcontainers 2.0.5 کے BOM کیپیروی کی ہے جو ہم نے صریحاً اعلان کیا ہے۔

اگر آپ کا JHipster/Gradle بِلڈ گرائیل 9 + ڈاکر انجن 29 میں ورژن اپ گریڈ کے بعد خراب ہو جاتی ہے، تو خرابی دو درجے میں تقسیم ہوتی ہے :

بلڈ سکرپٹ کی غلطیاں(پہلے 6) : گرڈل 9 خصوصیات اور سائنٹکس کو حذف کر دیتی ہے جو سالوں سے چل رہی تھیں (sourceCompatibility=, main =, reportsDir) یہ میکانیائی ہجرت ہیں جب ہم نئی API کو جان لیتے ہیں

ڈاکر رن ٹائم کی خرابی(آخری دو) : Docker Engine 29.4.1، 1.40 سے کم API کلائنٹوں کو خارج کر دیتا ہے۔ Testcontainers 1.20.6 (Spring Boot 3.4.5 کے تحت مجبور) docker-java 3.4.1 استعمال کرتا ہے jo 1.32 API ورژن بھیجتا ہے۔ صرف Testcontainers 2.0.5 + docker-java 3.7.1 مسئلے کو حل کرتا ہے، آرتЕФАکٹوں کے نام بدل کر اور ورژن کو زبردست کر کے ذریعے`resolutionStrategy.eachDependency`Spring Boot کے ضمنی BOM کو منفی کرنے کا صرف ایک طریقہ
