دیلما دروغ معماری مدرن

هنگامی که یک برنامه مدرن با یک frontend استاتیک ساخته می‌شود، معمولاً به یک انتخاب باینری (دودویی) مواجه می‌شویم:

  • همه چیز را بر روی یک راه‌حل Backend-as-a-Service بگذار(Supabase, Firebase) - ساده اما محدود

  • یک بک‌اند کامل بسازید(Spring Boot, Node.js) - قوی اما پیچیده

این گزینش یک معضل کاذب است. معماری هیبریدی یک راه سوم پیشنهاد می‌دهد: استفاده از هر فناوری جایی که بهتر است

دیده معماری

معماری سنتی : تک‌بلوک

در این رویکرد، حتی عملیات ساده‌ترین‌ها (خواندن یک مقاله، ایجاد یک نظر) باید از طریق بک‌اند شما عبور کنند. از روز اول هزینهٔ پیچیدگی را می‌پردازید.

معمار BaaS : herald نماینده

به عکس، واگذاری کامل به یک BaaS در ابتدا جذاب به‌نظر می‌رسد اما هرچون که منطق کسب‌وکار پیچیده می‌شود، به سرعت محدودیت‌هایش آشکار می‌شود.

معماری هیبریدی : جداسازی مسئولیت‌ها

معماری هیبرید مسئولیت‌ها را به صورت واضح بر اساس پیچیدگی و طبیعت عملیات‌های آن جدا می‌کند.

اگر به Spring Boot نیاز ندارید، آن را ساخت نکنید.با Supabase شروع کنید، Spring Boot را وقتی پیچیدگی آن را justified می‌دانید، اضافه کنید.

كي انتخاب این架构؟

این معماری ایده‌آل است اگر :

  • می‌خواهید به‌سرعت شروع کنید (MVP به‌روز، نه ماه)

  • شما پیش‌بینی می‌کنید رشد پیچیدگی کاری

  • شما می‌خواهید هزینه‌های اولیه را به حداقل برسانید

  • شما PostgreSQL را دوست دارید و می‌خواهید منبع یکتا از حقیقت داشته باشید

  • شما Kotlin و Coroutines را برای کد کسب‌وکار دوست دارید

  • شما می‌خواهید vendor lock-in کامل را جلوگیری کنید.

❌ این معماری برای این مناسب نیست اگر:

  • پروژه شما ساده است و همچنان ساده خواهد بود (وبلاگ شخصی → 100% Supabase کافی است)

  • شما یک پشته بک‌اندی (backend) مستقر دارید که آن را تسلط دارید

  • یک منولیت سنتی را ترجیح می‌دهید

  • شما نیاز دارید به .NET، Python یا یک زبان backend دیگر

منظورهای تکامل

افزودن توانمندی‌های جدید

مقیاس افقی

هنگامی که برنامه شما رشد می‌کند، معماری هیبریدی به‌طور خودکار مقیاس‌پذیر می‌شود:

Supabase:

  • به‌صورت خودکار تا میلیون‌های opérations مقیاس‌پذیر می‌شود

  • Read replicas برای عملکرد خواندن

  • بازیابی نقطه‌ای برای امنیت

اسپرینگ بوت :

  • چندین نمونه پشت load balancer

  • طراحی بی‌حالت مقیاس‌گیری افقی را تسهیل می‌کند

  • Kubernetes برای orchestretion در صورت نیاز

PostgreSQL :

  • پارتیشن‌بندی برای جداول حجیم

  • Connection pooling (PgBouncer)

  • شاردینگ واقعاً ضروری (نادر)

گواهینماری‌های معماری

استارتاپ SaaS (۵۰هزار کاربر)

_ ما با 100% Supabase شروع کردیم. در 5k کاربر، Spring Boot را صرفاً برای پرداخت Stripe و گزارش‌های ماهانه اضافه کردیم. یک سال بعد، 80% از عملیات‌های ما همچنان از طریق Supabase انجام می‌شود. Spring Boot فقط بخش حیاتی را مدیریت می‌کند. این جداسازی به ما اجازه داد تا مقیاس کنیم بدون نیاز به بازنویسی. _

پلتفرم E-learning (10k کاربر)

_ احراز هویت OAuth2 Supabase ما را سه هفته زمان توسعه صرفه‌جویی کرد. API‌های خود تولید شده فهرست دوره‌های ما را مدیریت می‌کنند. Spring Boot فقط برای گواهینامه‌های PDF و ایمیل‌های پیشرفت به کار می‌رود. معماری ساده، قابل‌ حفظ، قابل‌ گسترش. _

B2B مارکت‌پلیس (3k کاربر)

_ Spring Boot تراکنش‌ها بین خریداران و فروشندگان را مدیریت می‌کند (مهم). Supabase باقی موارد را مدیریت می‌کند: پروفایل‌ها، پیام‌رسانی در زمان واقعی، اسناد. این که آنها پایگاه داده PostgreSQL یکسانی را به اشتراک می‌گذارند، ما را از هرگونه همگونی‌سازی پیچیده در امان نگه می‌دارد. بهترین انتخاب معماری که تا به امروز کرده‌ایم. _
