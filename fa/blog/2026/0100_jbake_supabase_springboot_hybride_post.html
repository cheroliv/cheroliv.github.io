دشواه جعلی معماری مدرن

هنگامی که یک برنامه مدرن با frontend ایستا می‌سازیم، اکثر اوقات به یک انتخاب دودویی می‌برسیم:

  • هر چیزی را بر روی یک راه‌حل Backend-as-a-Service متمرکز کنید(Supabase, Firebase) - ساده اما محدود

  • یک بک‌اند کامل بسازید(Spring Boot, Node.js) - قوی اما پیچیده

این انتخاب یک دروغین معضل است. معماری هیبردی یک راه سوم پیشنهاد می‌دهد: استفاده از هر فناوری جایی که بهتر عمل می‌کند.

دیدگاه معماری

معماری سنتی: تک‌بلوک

در این رویکرد، حتی عملیاتی که ساده‌ترین هستند (خواندن یک مقاله، ایجاد یک نظر) باید از طریق backend شما عبور کنند. از اولین روز هزینه پیچیدگی را می‌پردازید.

معمارى BaaS : هر نماینده

به‌عکس، واگذاری تمام امور به یک BaaS در آغاز جذاب به‌نظر می‌رسد اما به‌سرعت محدودیت‌هایش را نشان می‌دهد هنگامی که منطق کسب‌وکار پیچیده می‌شود.

معماری هیبریدی : جداسازی مسئولیت‌ها

معماری هیبرید مسئولیت‌ها را بر اساس پیچیدگی و طبیعت عملیات به‌طور واضح جدا می‌کند.

مبادئ طراحی

مبدأ ۱ : شروع ساده، پیشرفت هوشمندانه

اگر به Spring Boot نیاز ندارید، آن را ایجاد نکنید.Supabase را شروع کنید؛ Spring Boot را زمانی اضافه کنید که پیچیدگی آن را توجیه کند.

اصول ۲ : جداسازی بر پایهٔ نوع عملیات

مبدأ 3: منبع یگانه حقیقت

با به اشتراک‌گذاری همان instance PostgreSQL، Supabase و Spring Boot روی داده‌های یکسان کار می‌کنند بدون نیاز به همگام‌سازی پیچیده.

همگام‌سازی جریان‌ها

جریان 1 : احراز هویت مرکزی

نقطه کلیدییک فرآیند احراز هویت، یک JWT، قابل استفاده در هر مکان.

فلو 2 : همگام‌سازی یک فرآیند تجاری پیچیده

چه چیزی Spring Boot ارائه می‌دهدهمگام‌سازی قابل اعتماد از فرآیندهای پیچیده شامل چندین سیستم با تضمین ترنزاکیونی.

جريان 3 : کارها برنامه‌ریزی شده و همگام‌سازی‌ها

چه چیزی Spring Boot به ارمغان می‌آورد: کارهای برنامه‌ریزی‌شده قابل اعتماد با مدیریت وضعیت، تلاش خودکار و اجرای تضمین‌شده.

اصول‌های لازم به یادداشت

کیبای این معماری را انتخاب کنیم؟

✅ این معماری برای موارد زیر ایده‌آل است :

  • شما می‌خواهید به سرعت شروع کنید (MVP به صورت روز، نه ماه)

  • شما یک افزایش در پیچیدگی کسب‌وکار را پیش‌بینی می‌کنید

  • شما می‌خواهید هزینه‌های اولیه را به حداقل برسید

  • شما PostgreSQL را دوست دارید و می‌خواهید منبع یکتای حقیقت داشته باشید.

  • شما Kotlin و Coroutines را برای منطق کسب‌وکار دوست دارید

  • شما می‌خواهید از قفل‌گیری کامل فروشنده جلوگیری کنید

❌ این معماری برای این شرایط مناسب نیست :

  • پروژه شما ساده است و چنین خواهد بود (وبلاگ شخصی → 100٪ Supabase کافی است)

  • شما یک استک بک‌اند پیش‌ساخته دارید که آن را به خوبی می‌دانید

  • شما یک مونولیت سنتی ترجیح می‌دهید

  • شما به .NET، پایتون یا هر زبان دیگری سمت بک‌اند نیاز دارید.

منظورهای تکامل

افزودن قابلیت‌های جدید

مقیاس‌گیری افقی

هنگامی که برنامه شما بزرگ می‌شود، معماری هیبریدی به طور طبیعی مقیاس‌پذیر می‌شود :

Supabase :

  • به صورت خودکار تا میلیون‌های عملیات مقیاس‌پذیر می‌شود

  • Read replicas برای عملکرد خواندن

  • بازیابی نقطه در زمان برای امنیت

Spring Boot :

  • چندین نمونه پشت یک موزن‌ساز بار

  • طراحی بی‌وضعیت مقیاس‌پذیری افقی را تسهیل می‌کند

  • Kubernetes برای orchestra­tion در صورت نیاز

PostgreSQL :

  • پارتیشن‌سازی برای جداول حجیم

  • گروه‌بندی اتصالات (PgBouncer)

  • شاردینگ واقعاً ضروری است (نادر)

شواهد معماری

Startup SaaS (50k کاربران)

تمام Span‌های کد backtick (…​) را به‌صورت دقیق حفظ کنید — هیچ‌گاه محتوای backtick، فاصله یا مکان را تغییر ندهید. این متن ممکن است parçهٔ یک جمله بزرگتر باشد — پارچ را بدون درخواست contextual بیشتر ترجمه کنید. فقط متن ترجمه‌شده را خروجی دهید — بدون توضیح، بدون نظر، بدون مقدمة، بدون گزینش، بدون گزینند. ما 100% Supabase را شروع کردیم. وقتی به 5k کاربر رسیدیم، Spring Boot را فقط برای صورتحساب Stripe و گزارش‌های ماهانه اضافه کردیم. یک سال بعد، 80% از operaciones‑های ما همچنان از طریق Supabase انجام می‌شوند. Spring Boot فقط بخش بحرانی را مدیریت می‌کند. این جداسازی به ما اجازه داد تا بدون بازسازی مقیاس‌پذیری داشته باشیم. __

پلتفرم E-learning (10k کاربر)

(Empty output) احراز هویت OAuth2 Supabase سه هفته از زمان توسعه ما را به ما صرفه‌جویی کرد. API‌های خودکار تولید شده تمام فهرست دوره‌های ما را مدیریت می‌کنند. Spring Boot فقط برای گواهینامه‌های PDF و ایمیل‌های پیشرفت استفاده می‌شود. معماری ساده، قابل نگهداری و مقیاس‌پذیر. __

Marketplace B2B (3k کاربران)

_ Spring Boot معاملات بین خریداران و فروشندگان (مهم) را مدیریت می‌کند. Supabase همهٔ بقیه را مدیریت می‌کند: پروفایل‌ها، پیام‌رسانی زمان واقعی، اسناد. اینکه آنها پایگاه داده یکسانی PostgreSQL دارند، نیاز به هم‌سنجازی پیچیده‌ای را رفع می‌کند. بهترین انتخاب معماری که تا کنون کرده‌ایم. _

گام بعدی شما

اگر این معماری با شما صحبت می‌کند، اینجا جایی است که باید شروع کنید:

  1. یک حساب Supabase ایجاد کنید(رایگان)

  2. اسخیم داده‌های حداقل خود را تعریف کنید

  3. احراز هویت OAuth2 را پیکربندی کنید

  5. در گیت‌هاب پیج‌ها مستقر شوید
