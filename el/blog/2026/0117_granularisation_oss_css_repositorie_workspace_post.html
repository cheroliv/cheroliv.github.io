foundry/— η λειτουργική ζώνη που φιλοξενεί τον κώδικα του χώρου εργασίας μου — περιέχει 18 έργα. Οκτώ είναι ανοιχτού κώδικα υπό την άδεια Apache 2.0. Μόνος είναι closed source — το SaaS Edster. Για μήνες, αυτά τα εννέα έργα συνέζησαν στο ίδιο φάκελο, διαχωρισμένοι μόνο με…​ τίποτα. Η δημόσια/ιδιωτική κατάστασή τους Ήταν μια πληροφορία στο κεφάλι μου, όχι στο σύστημα αρχείων.

Και έπειτα ήθελα να συνδέσω ένα RAG. Και τότε, όλα έπεσαν.

Το ατύχημα που περίμενε να συμβεί

Στον Απρίλιο 2026, άρχισα να υλοποιώ το RAG pgvector για το slider-gradle. Η αρχή: να ευρετηριάζει όλα τα αποθετήρια του`foundry/, να παράγει embeddings, και να τα εγχέσουν στο πλαίσιο του LLM ώστε να έχει μια αντίληψη" του φακέλου`foundry/.

Το pipeline ήταν απλό :

val repos = fileTree(rootDir) {
    include("**/*.adoc", "**/*.kts", "**/*.kt", "**/*.json", "**/*.yml")
}
val chunks = repos.map { chunk(it) }
val embeddings = chunks.map { embed(it) }
pgvector.insert(embeddings)

Απλό. Αποτελεσματικό. Καιεπικίνδυνος.

Επειδή αυτό`fileTree`Δεν κάνει διάκριση μεταξύ`plantuml-gradle/` (Apache 2.0, δημόσια) και`edster/`(κλειστός κώδικας, ιδιωτικό). Καταπίνει ό,τι. Και αν έναν μέρα δημοσιεύσω αυτά τα embeddings — σε ένα dashboard, σε μια απάντηση LLM, σε ένα dataset εκπαίδευσης — ο ιδιοκτησιακός κώδικας του Edster διαρρέει.

Το πρόβλημα δεν είναι ότι ένα LLM διαβάζει κλειστού κώδικα. Το πρόβλημα, Το είναι ότι αυτός ο κώδικας τελειώνει σε ένα δημόσιο vector embedding — ανύστροφος, μη διαγραφέτος, μη ελεγχόμενος.

Η Αληθινή Ερώτηση

Δεν είναι "πώς να αποτρέψουμε το LLM να διαρρεύει κώδικα ?". Είναι "πώς Κάνετε τη φυγή δομικά αδύνατο;

Η απάντηση δεν είναι ένα prompt. Η απάντηση είναι να κοπεί το φάκελο σε δύο.

Η Λύση : OSS/ και CSS/

Πριν :

foundry/
├── plantuml-gradle/       ← public
├── bakery-gradle/         ← public
├── magic-stick/           ← public
├── edster/                ← PRIVÉ
├── slider-gradle/         ← public
└── ...                    ← mélange invisible

Μετά :

foundry/
├── OSS/                   ← tout est Apache 2.0
│   ├── plantuml-gradle/
│   ├── bakery-gradle/
│   ├── magic-stick/
│   ├── slider-gradle/
│   └── ...
└── CSS/                   ← tout est closed source / private
    └── edster/

Le `fileTree`γίνεται :

val ossRepos = fileTree(File(rootDir, "OSS")) {
    include("**/*.adoc", "**/*.kts", "**/*.kt", "**/*.json", "**/*.yml")
}
val cssRepos = fileTree(File(rootDir, "CSS")) {
    include("**/*.adoc", "**/*.kts", "**/*.kt", "**/*.json", "**/*.yml")
}

// Embeddings publics — OSS seulement
pgvectorPublic.insert(ossRepos.map { chunk(it) }.map { embed(it) })

// Dataset fine-tuning privé — CSS seulement
fineTuningDataset.insert(cssRepos.map { chunk(it) })  // jamais publié

Η δημόσια RAG δεν βλέπει ποτέ`CSS/`. Ο κώδικας closed source τροφοδοτεί ένα dataset χωρίς fine‑tuning — εσωτερικό μοντέλο που δεν βγαίνει ποτέ από το σπίτι μου. Η ο χωρισμός είναι μηχανικός, όχι δηλωτικός.

Γιατί "OSS" και "CSS" και όχι "Public" και "Private

Η επιλογή των ακροστιχισμών OSS (Open Source Software) και CSS (Closed Source Software) αποφασίζεται :

  • Public"/"Private" περιγράφει τηορατότητα(τι βλέπει το GitHub)

  • OSS"/"CSS" περιγράφει τοφύσητου κώδικα (ότι το LLM πρέπει να γνωρίζει)

Η ορατότητα του GitHub είναι ένα μετα-δεδομένο του απομακρυσμένου αποθετηρίου. Η φύση του κώδικα είναι Μια ιδιότητα του περιεχομένου. Το LLM δεν έχει πρόσβαση στην API του GitHub — αλλά έχει πρόσβαση στο σύστημα αρχείων.CSS/`Αυτό του είπε "Προσοχή, αυτός ο κώδικας δεν είναι άδεια ελεύθερος" χωρίς να χρειάζεται να διαβάσεις ένα`LICENSE`ή να αναλύσει ένα`package.json.

Το όνομα του φακέλου είναι η πιο ισχυρή μεταδεδομένη που μπορείτε να δώσετε σε Ένα LLM. Δεν μπορεί να είναι λανθασμένα διατεταγμένη, αγνοημένη ή λανθασμένα ερμηνευμένη. Το LLM. βλέπει`CSS/edster/`στο μονοπάτι του αρχείου — ξέρει.

Το Ολοκληρωμένο Δέντρο — Τέσσερις Ζώνες, Όχι Τρεις

bakery-gradle δεν του κάνει τίποτα

Και αυτό είναι όμορφο. Το plugin`bakery-gradle`δεν έχει τροποποιηθεί. Λαμβάνει ένα κατάλογο περιεχομένου AsciiDoc, παράγει HTML, το push σε GitHub Pages. Τι ονομάζεται αυτός ο φάκελος`site/jbake/content/` ou office/sites/cheroliv/— το plugin δεν του ενδιαφέρει.

// engine/build.gradle.kts
task("publishBlog") {
    doLast {
        val articles = fileTree("../../office/sites/cheroliv/2026/")
        bakery.generate(articles)  // ← bakery ne sait pas d'où ça vient
    }
}

Η σύμβαση διεπαφής είναι μια εργασία Gradle. Δεν είναι μια API REST. Δεν είναι ένα webhook. Μια εργασία — τυπημένη, δοκιμάσιμη, εκτελέσιμη τοπικά και στο CI.

à foundry/public/+office/Vision/. Ο κώδικας closed source Εξαιρείται από το ευρετήριο μέσω ρύθμισης εργασίας, όχι μέσω εντολής.

*office/graph.json(δημόσιος) — σχέσεις μεταξύ αντικειμένων OSS + office/Vision *configuration/graph_private.json(gitignored, ιδιωτικό) — σχέσεις μεταξύ αρτεφάκτα CSS, που δεν δημοσιεύτηκε ποτέ

Συμπερασμα : το φυσικό señal νικά το λογικό señal

Το που έκανα αυτό το απόγευμα ήταν να αντικαταστήσω έναν αόρατο κανόνα. μέσα από έναν ορατό διαχωρισμό στην περιοχή`foundry/Προηγουμένως, θα έπρεπες ξέρω ότι`edster/`ήταν κλειστός κώδικας. Τώρα, το βλέπετε — ο φάκελος ονομάζεται`CSS/.

Είναι η ίδια αρχή όπως τα δικαιώματα Unix, τα VLAN δικτύου ή τα πυροπροστατευτικά τμήματα σε μια βάση δεδομένων. Η ασφάλεια δεν πρέπει Πρέπει να είναι μια πληροφορία που πρέπει να θυμάστε. Πρέπει να είναι μια ιδιότητα. φυσικήτου συστήματος.

Η γρανυλοποίηση OSS/CSS είναι η μετάφραση αυτού του αρχικού στο πεδίο. της διακυβέρνησης LLM. Ο LLM δεν χρειάζεται να ξέρει ότι το Edster είναι συκρετικό. Χρειάζεται να μην είναι ικανός να το ευρετογραφήσει.

Και αυτό είναι ακριβώς αυτό που`CSS/`εγγυάται
