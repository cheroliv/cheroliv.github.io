χρόνος ανάγνωσης : 20 minutes

Το prompt engineering είναι ευαστό. Στο 80.000 tokens, οι κανόνες σας ευθύνσεως χάνονται στον θόρυβο, και το LLM ξεχνά τι του ζητήσατε στην αρχή της συζήτησης. Η λύση μου; Μη ευθυντείτε με το κείμενο, αλλά με l'χώρος. Έχω δομημένο τον χώρο εργασίας μου ανάπτυξης σε τέσσερα κενθρικά κύκλους εμπιστοσύνης — από τον εσωτερικό μυστικό κήπο έως τις δημόσιες φυλές — και κάθε κύκλος είναι μια φυσική περιοχή του συστήματος αρχείων. Το LLM δεν χρειάζεται να του υποθυμίσουν τους κανόνες: η διαδρομή του αρχείου τα περιέχει. Αυτός είναι ο τρόπος που λειτουργεί, και γιατί αυτή η αρχιτεκτονική ευθυγράμμισης με βάση τον χώρο είναι πιο ανθεκτική από ένα`system prompt`από 500 γραμμές.

Κατά τις τρεις εβδομάδες, έχω αναπτύξει plugins Gradle με Opencode, χρησιμοποιώντας τρεις διαφορετικούς LLMs — Kimi K2.6, GLM-5.1, et DeepSeek-V4-Pro (ο μόνος επιζώσας, αλλά είναι μια άλλη ιστορίαDéjà couverte ici.). Η μέθοδος μου διακυβέρνησης Je l’ai documentée en détail dans un précédent article. βαziται σε αρχεία AsciiDoc —AGENT.adoc, INDEX.adoc, PROMPT_REPRISE.adoc— που φορτώνουν περίπου 30 000 διακριτικά κανόνων, υπολοίπου και ιστορικού στο ξεκίνημα każde συνεδρίας.

Και παρ' αυτή την υποδομή εγγράφων, δύο πράγματα με έκπληξαν:

  1. Το LLM ξεχαίνει. Ακόμη και με τους απόλυτους κανόνες στην αρχή του κάθε αρχείου EAGER, πέρα από 60 000 tokens που έχουν συσσωρευτεί (αρχικό πλαίσιο + συνομιλία), Ο Kimi K2.6 άρχισε να προτείνει`Write`επιβαρυντικά σε αρχεία ρυθμίσεων. Το GLM-5.1 σύγχυσε ένα token Firebase με ένα placeholder που πρέπει να αντικατασταθεί. Οι κανόνες habían γραφτεί — ο LLM δεν τα βλέπε πλέον.

  2. Η διακυβέρνηση και αυτή γίνεται ένα πρόβλημα. Μετά από την εφαρμογή του μηχανισμού Hot/Warm/ColdΑρθρο για την περιστροφή αντιγράφων ασφαλείας. για να αποφύγω την έκρηξη του context, τα αρχεία μου EAGER είχαν ακόμα 1414 γραμμέςΈχω τεκμηριώσει αυτό το έλεγχο εδώ. Η διακυβέρνηση — σχεδιασμένη για την προστασία του LLM από την υπερφόρτωση — επιβαρύνετο το LLM.

Χρειαζόμουν ένα μηχανισμό ευθυγραμμίσεως που δεν εξαρτάται από τον αριθμό των tokens στο prompt.

Η απάντηση: να σταματήσει να ευθυγραμμίζει με το κείμενο, και να αρχίσει να ευθυγραμμίζει με τηνχώρος.

Κάθε επίπεδο απαντά σε μια συγκεκριμένη ερώτηση :

  • Πού να αποθηκεύσω μια ιδέα που δεν είναι ακόμα έτοιμη για να διαμοιραστεί, ακόμα και με ένα στενό κύκλο; → Ο μυστικός κήπος. Χωρίς Git. Χωρίς πίεση.

  • Πού να βιομηχανίσουμε ένα plugin Gradle ανοιχτού κώδικα; → Οι σιδηρουργεία`foundry/`). Δημόσιο, forkable, δοκιμασμένο σε CI.

Αυτή η οντιλογία είναικαταναλώσιμο από ένα LLM. Όταν διαβάζει ένα αρχείο στο`foundry/plantuml-gradle/src/`, ξέρει εμμέσως: "Είμαι στον κύκλο 4 — δημόσιος κώδικας, υποχρεωτικά τεστ, χωρίς μυστικά, χωρίς εκπαιδευτικά δεδομένα". Δεν χρειάζεται ένα prompt που του να το θυμίζει.

Ο μυστικός κήπος : Ο χώρος εκτός CVS

Αυτή είναι η πιο σημαντική — και η πιο αντιενυπηρετική.

Η ρίζα`workspace/δεν έχει.git/. Τα έγγραφα που ζουνieke (`WORKSPACE_VISION.adoc, WORKSPACE_AS_PRODUCT.adoc, WORKSPACE_ORGANIZATION.adoc— και αυτό που διαβάζεις τώρα, που προέρχεται από αυτό) δεν είναι προορισμένα για να εκδοθούν, να κοινοποιηθούν ή να διαβαστεί από κάποιον άλλον εκτός εμένα. Αυτά είναιενθυμήματα σε φάση φυτώσης.

Το μυστικό κήπο είναι out-of-CVS φύσης. Η έλλειψη εκδοσιογραφίας είναι η συνθήκη της ελευθερίας της σκέψης. Δεν γράφουμε εκεί για να διαβαστεί — γράφουμε εκεί για να διευκρινίσουμε τη δική μας όραση.

Αλλά αυτή η ελευθερία έχει ένα κόστος: ένα`rm`Τυχαίο, και είναι μήνες στρατηγικής σκέψης που εξαφανίζονται. Η λύση δεν είναι να εφαρμόσουμε versioning στον κήπο (γιατί θα τον καταστρέφουμε) — είναι να τοκατοπτρίζωστο πιο περιορισμένο κύκλο

Το .gitignore ως ρύθμιση διακυβέρνησης

Στηρίζεται`workspace/, ένα αρχείο.gitignore`ελαχιστό δηλώνει τοπολιτική ιστορικόποίησηςαρχεια του κρυφου κηπου :

.goosehints
.goose

Ce .gitignore`δεν έχει κλασική λειτουργία Git (δεν υπάρχει.git/`στη ρίζα). Ενεργεί ως ένααρχείο διαμόρφωσης κυβέρνησηςqui répond à une question précise : ποια αρτεφάκτα του μυστικού κήπου αξίζουν να ιστοριοποιηθούν, και ποια είναι纯粹 εφήμερα ?

  • Τα αρχεία που παρατίθενται σε`.gitignore`—.goosehints, .goose— είναι άρτεφакτα εφημερείς που δημιουργούνται από τους πρακτόρες. Χωρίς στρατηγική αξία. Χωρίς ιστορικοποίηση.

  • Τα αρχεία`.adoc`της ρίζας—WORKSPACE_VISION.adoc, WORKSPACE_ORGANIZATION.adoc, WORKSPACE_AS_PRODUCT.adoc, WHAT_THE_GAMES_BEEN_MISSING.adoc, depots_implementes_strategie.adoc, synthese-LLMs-long-contexte.adoc— δεν είναιβήμαστόν`.gitignore`. Αυτά είναι τα αντικείμενα που πρέπει να ιστοριστούν.

Le `.gitignore`είναι τοσχήμα διακυβέρνησης: Τίποτα που δεν παρατίθεται εδού είναι υποψήφιο για το snapshot. Και το LLM, διαβάζοντας αυτό το αρχείο, γνωρίζει ακριβώς τι πρέπει να αρχειοθετηθεί και τι μπορεί να αγνοηθεί — χωρίς την ανάγκη να του υπενθυμίσουμε αυτό σε ένα prompt.

Το μηχανισμό του Snapshot

Έχω δημιουργήσει`configuration/vision-archive/: ημερομηνιακά στιγμιότυπα όλων των.adoc`της ρίζας, υποβεβαιωμένοι στο ιδιωτικό αποθετήριο`configuration/`.Χάθε ευρηματική συνεδρία δημιουργεί ένα snapshot :

DATE=$(date +%Y-%m-%d)
mkdir -p /home/cheroliv/workspace/configuration/vision-archive/$DATE
cp /home/cheroliv/workspace/*.adoc /home/cheroliv/workspace/configuration/vision-archive/$DATE/
cd /home/cheroliv/workspace/configuration && git add vision-archive/ && \
  git commit -m "vision-archive: snapshot $DATE"

Η διαδικασία ενεργοποιείται στο τέλος της συνεδρίας από τον LLM τον εαυτό του, που εκτελεί αυτή τη γενική εργασία δρομολόγησης. Κάθε snapshot καταλαμβάνει την πλήρη κατάσταση της στρατηγικής σκέψης σε ένα στιγμίο T.

Το ιστορικό Git του`configuration/`γίνεται ηβιογραφία της στρατηγικής μου σκέψης. Μπορώ να κάνω ένα`git log — vision-archive/`και να δώω την εξέλιξη της όρασης μου, συνεδρία ανά συνεδρία, ημερομηνία ανά ημερομηνία.

Παράδειγμα πραγματικού ιστορικού μετά από μια μέρα εργασίας :

$ git -C configuration log --oneline -- vision-archive/
1089d1b vision-archive: fin de session finale 2026-05-03
6b21eaf vision-archive: fin de session 2026-05-03-1300
1690f82 vision-archive: post-article 2026-05-03
28e6593 vision-archive: post-migration 2026-05-03
3707b78 vision-archive: snapshot 2026-05-03 — jardin secret initial

Πέντε σναπσκότ σε μια ημέρα. Κάθε ένα είναι ένα σημείο επαναφοράς. Κάθε ένα είναι ένα ορόσημο στη γένεση της στρατηγικής.

Το φάκελο`configuration/vision-archive/latest/`περιέχει μονίμα έναεργατικό αντίγραφοτου τελευταίου σναπσhoτ, που λειτουργεί ως γρήγορη αναφορά χωρίς να χρειάζεται να πλοηγηθείς στον ιστορικό Git.

Και για το LLM, είναι έναορακέλο συνεχείας: όταν παρατηρεί μια αντίφαση μεταξύ της τρέχουσας υλοποίησης και της αρχειοθετηθείσας όψης από μια προηγούμενη ημερομηνία, μπορεί να την αναφέρει.

Το Vault : configuration/ ως το Spring Cloud Config

`configuration/`Δεν περιέχει μόνο το αρχείο της όρασης. Η κυρία — και μελλοντική — λειτουργία του είναι να είναι ένασέρβερ Spring Cloud Config. Όλα τα μυστικά, tokens, credentials και οι περιγραφές υποδομής βρίσκονται εδώ, σε ένα ιδιωτικό αποθετήριο Git προσβάσιμο μόνο από τον ιδιοκτήτη.

Γιατί ένα αποθετήριο ξεχωριστό αντί για ένα αρχείο`.env`σε каждый έργο ?

  • Ατυχέμενο push ενός μυστικού : αδύνατο. Τα μυστικά βρίσκονται σε ένα ιδιωτικό αποθετήριο που τα δημόσια έργα δεν μπορούν να αναφέρουν λάθος.

  • Audit : το Git ιστορικό δίνει το ίχνος κάθε αλλαγής ρύθμισης. Ποιος άλλαξε τι, πότε, με ποιο hash SHA.

  • Ανακύκλωση :`git revert`σε μια κατεστραμμένη διαμόρφωση. Αμέσως, χωρίς χειροκίνητο backup.

Η Βιβλιοθήκη : office/ ως δεδομένα καταναλωτικού

`office/`είναι το τεκμηριωτικό αντίστοιχο της εργασίας ανάπτυξης. Περιέχει τα άρθρα του blog, τις τεχνικές προδιαγραφές, το υλικό εκπαίδευσης (38 φακέλοι μαθημάτων FPA, SPG/SPD, σχήματα JSON, ταξινομίες Bloom/Harrow/Krathwohl) — όλο αυτό που αποτελεί τοεκπαιδευτικό υλικό.

αλλά`office/`Δεν είναι μόνο ένα αποθήκη εγγράφων. Είναι μιπηγή δομημένων δεδομένωνότι τα plugins του Gradle του`foundry/`καταναλώνουν. Μια δημοσίευση ιστολογίου στο`office/`είναι μια καταχώριση που θα μετατρέψει ένα plugin σε HTML. Ένας SPG AsciiDoc σε`office/metiers/FPA/`είναι ένα αντικείμενο που ένας ορχεστράτορας θα αναλύσει για να παράγει διαφάνειες, quiz και βίντεο καψούλες.

Et le `build.gradle.kts`στη ρίζα του`office/`不是代码。-- 这是一段代码。σκόλος κατανάλωσης του οικοσυστήματος των προσθηκών. Ο λέει: "εδώ είναι τα plugins Gradle που χρησιμοποιώ, εδώ είναι ο χώρος εργασίας μου".

Οι φονές : foundry/ ως υλοποίηση

foundry/`περιέχει τοβιομηχανικός κώδικας. 54 αποθετήρια Git, από τα οποία 7 διαχειρίζονται τρέχοντα από.agents/`. Εδώ γίνεται η όραση εφικτή — πρόσθετα Gradle, CI/CD, δοκιμές JUnit5 + Cucumber.

Η σχέση με`office/`είναι διπλής κατεύθυνσης

  • office/→foundry/: τα διδακτικά δεδομένα είναι η πρώτη ύλη που τα πρόσθετα καταναλώνουν.

  • foundry/→office/`Τα προσθήκματα παράγουν δεδομένα που ενισχύουν`office/ — le `graph.json`από το graphify-gradle, τα decks slider συναρμολημένα, τα αναφορές κατασκευής

Pro/Contra : Συγκρότηση Χωρικού vs Συγκρότηση με Prompt

Συγκρίνουμε τις δύο προσεγγίσεις.

Κλασική προσέγγιση : Ευθυγράμμιση με Pré-Prompt

✅ Pro

αντί

Εύκολο στην υλοποίηση. Ένα μπλοκ κειμένου στο system prompt.

Ασθές σε μεγάλο πλαίσιο: ο κανόνας χάνεται μετά 80K tokens.

Λειτουργεί για γενικούς κανόνες (τονος, μορφή).

μη επαληθεύσιμο : Τίποτα δεν εμποδίζει το LLM να παραβιάσει τον κανόνα.

Δεν χρειάζεται να ανασυγκροτούμε την αρχιτεκτονικό του έργου.

Μη μεταβαίσιμος : Κάθε αποθετήριο ανακαθορίζει τους κανόνες.

καθαρώς δηλωτικό : ο LLM ξέρει ότι πρέπει, αλλά δεν υπάρχει τίποτα που τομπομπούτ.

Αυτή η Προσέγγιση: Συμμόρφωση με Χωρική Οντολογία

επαγγελματίας

❌ κατά

Ανθεκτικό στο μεγάλο πλαίσιο : ο κανόνας είναι στη διαδρομή του αρχείου, όχι σε μια απομακρυσμένη προτροπή.

Αρχικό κόστος υποδομής : Η οργάνωση του χώρου εργασίας σε κύκλους παίρνει χρόνο.

Μηχανικά ελέγχσιμο : ένα μυστικό σε`foundry/είναι ανιχνεύσιμο από`git check-ignore.

Απαιτεί disciple : ένας νέος συνεισφέρων πρέπει να καταλάβει τους κύκλους.

μεταφερόμενο : ένας`AGENT.adoc`το πρότυπο παρέι τους κύκλους σε κάθε νέο έργο

Καλύπτει μόνο τους χωρικούς περιορισμούς — ο στυλ κώδικα παραμένει στο prompt.

Ασφάλεια από σχεδίαση : ένας`git push`από`foundry/δεν μπορεί να εκθέσει`configuration/.

Καταναλώσιμο από μη-LLM αντικείμενα : ένα ορχηστράτο Gradle μπορεί να δρομολογεί σύμφωνα με τον κύκλο.

Ο κύριος οφέλος δεν είναι αμυντικός (ασφάλεια, ορατότητα) — είναιδημιουργικός. Όταν το LLM λειτουργεί σε ένα χώρο που είναι δομημένος από μια οντολογία, μπορεί να κάνει αυτό που καμία πρόταση δεν του επιτρέπει: παρατήρηση της διαφοράς.

Η Σχετική Άλγεβρα του Workspace και το Delta Observable

Όταν το LLM διασχίζει`foundry/, διαθέτει έναπλέγμα δομημένων δεδομένων: κόμβοι (plugins, αρχεία, δοκιμές, εξαρτήσεις), τυποποιημένες άκρες (`import, depends_on, generates, tests), σχέσεις σύνθεσης και τάξης (`training-gradle`εξάγει το αποθετήριο`slider-gradle`γεννεί τις διαφάνειες →`capsule-gradle`Ανεβάστε το βίντεο).

Αυτή η άλγεβρα δεν είναι γραπτού πουθενά σε φανερή μορφή — αλλά είναι παρατηρήσιμο. Κάθε`build.gradle.kts`απεκθέτει τις εξαρτήσεις. Κάθε`INDEX.adoc`εμφανίζει διασχετεμένες αναφορές.

Ο LLM παρατηρεί αυτή την άλγεβρα και εντοπίζει τοδέλταη διαφορά μεταξύ αυτού που το σύστημα ξέρει ήδη να παράγει και αυτού που η όραση περιγράφει.

Από αυτό το δέλτα, μπορεί να ορίζει μερικάχαρτογραφίες ειδικών επαγγελματιών— CDA (Σχεδιαστής-Αναπτυξιακός Εφαρμογών, Kotlin/Gradle/JHipster) και FPA (Επαγγελματίας Εκπαιδευτής Ενήλικων, Παιδαγωγική/Qualiopi/Bloom) — και να εντοπίσουμε τι λείπει για κάθε ειδικό.

Expert CDA (Kotlin/Gradle/JHipster)

Το LLM δεν χρειάζεται να του πούμε τι να κάνει. Το δέλτα προκύπτει από τη δομή.

Το σύνθετο βέκτορας του πλαίσιοι : RAG + pgvector + Graphify

Η σχετική άλγεβρα δεν είναι μια θεωρητική κατασκευή. Είναι υλοποιημένη από τρία συστατικά που σχηματίζουν ένασυνθετικό διάνυσμα περιβάλλοντοςγια το LLM.

Μέρος 1 — RAG LangChain4j + PostgreSQL pgvector

Έχω ήδη LangChain4j σε παραγωγή σε δύο plugins :`slider-gradle`(4 παροχείς LLM) και`plantuml-gradle`(7 providers). Τα ενθετές ONNX (AllMiniLmL6V2) ευρετοδοούν τα δεδομένα του`office/`και ο κώδικας πηγής του`foundry/`στο PostgreSQL + pgvector.

Το RAG λειτουργεί σε δύο διαστάσεις:

  • Διαστάσεις δεδομένων : τα έγγραφα`office/`(SPG, άρθρα, εκπαιδεύσεις, σχέματα JSON)

  • Κώδικας διαστάσεων : οι βάσεις κώδικα`foundry/`(πηγές Kotlin, δοκιμές Cucumber, AGENT.adoc)

Η τομή καλύπτει τόσο το τι (ο κλάδος της επιχείρησης) και το πώς (η υλοποίηση).

Σύστατο 2 — Knowledge Graph Graphify

Το Graphify είναι ενσωματωμένο στο`plantuml-gradle`(109 tests, 380/380 PASS) και παράγει ένα`graph.json`— ένα δομημένο knowledge graph με κόμβους, ακμές, και κοινότητες που ανιχνεύονται αυτόματα.

Αντιθέτως με το RAG που λειτουργεί βάσει διανυσματικής ομοιότητας (αμβλύ), ο γράφος γνώσης λειτουργεί βάσεισχέσεις ακριβείς(καθοριστικός) :`graphify query`για τις σεμαντικές ερωτήσεις (~50 διακριτικά),`graphify path`για να πλοηγηθείς,`graphify explain`για να εξηγήσει.

Συστατικό 3 — Graphify Προσθετικό: Διασπαρμένο, Συγκρόσιμος, Καταναλωτό

Αυτή είναι η κρίσιμη αρχιτεκτονική απόφαση.

Graphify δεν πρέπει να ζεί σε έναν μόνο αποθετήριο. Πρέπει να ζεί με τρόποδιασπαρμένησε κάθε προσθέτο:

  1. Κάθε plugin εμπεριέχει μια Gradle úλο`updateKnowledgeGraph`ο οποίος καλεί το Graphifyστο δικό του scopeκαι παράγει ένα`graph.json`τοπικός.

  2. Το build script του`office/ καταναλώνει`graphify-gradle`με`rootDir = /home/cheroliv/workspace`και παράγει ένα`graph.json παγκόσμιοςπου συγκεντρώνει τα τοπικά γραφήματα.

  3. Το RAG του κάθε plugin ενεσκεί το`graph.json`global ωςφίλτρο περιβάλλοντοςγια τα ερωτήματα LLM.

TÂCHE GRADLE (dans chaque plugin)
    ↓
graphify → graph.json (scope local)
    ↓
office/build.gradle.kts → graph.json (scope global)
    ↓
RAG pgvector (dans slider, plantuml, codebase...)
    ↓  ← injection du graph.json comme filtre
LLM (deepseek-v4-pro)
    ↓  ← observation algèbre relationnelle
    ↓  ← détection delta vs cartographies experts
PRIORISATION → prochaine tâche

Αποτέλεσμα: ο LLM δεν ψάχνει στο κενό — περιηγείται σε ένα χώρο που είναι δομημένος από το knowledge graph. Μια ερώτηση για "γενέσει ένα διάγραμμα" ξέρει να φτάσει στους σχετικούς κόμβους του γραφήματος.

Τέλος της συνεδρίας, το LLM εκτελεί μιαπαγκόσμια εργασία:

  1. Ανάγνωση του`.gitignore`ρίζα για να προσδιορίζουμε τα εφαμενα αρτέφασμα (για την εξαίρεση από το snapshot) vs τα στρατηγικά αρτέφασμα (για την ιστορikoποίηση)

  2. Κατάλογος όλων των αρχείων`.adoc`της ρίζας`workspace/`

  3. Φιλτράρισμα : απόκλειση των καταγεγραμμένων αρχείων σε`.gitignore`, ένταξη όλων των άλλων

  4. Αντιγραφή σε`configuration/vision-archive/$DATE/και ενημέρωση του symlink`latest/

  5. commit στο αποθετήριο`configuration/`με ένα δομημένο μήνυμα

  6. Αυτόματη ταξινόμηση GDPR каждый τροποποιημένου αρχείου (όλεςοι κύκλοι)

  7. Δρομολόγηση: δεδομένα`office/→ ιδιωτικό commit, κώδικα`foundry/→./gradlew check, ρύθμιση → υποβολή

  8. Δομημένη αναφορά με προειδοποιήσεις GDPR και επιβεβαίωση αρχειοθέτησης

Le `.gitignore`η ρίζα δεν είναι ένα αρχείο ρύθμισης του Git — είναι ένααρχείο κυβερνέτευσης της ιστορικοποίησης. Ορίζει το σχήμα που το LLM καταναλώνει για να αποφασίζει ποια αρχεία του μυστικού κήπου εισάγονται στη στρατηγική βιογραφία και ποια είναι απορρίψιμα.

Ο LLM δεν είναι πια απλώς ένας γεννήτρας κειμένου. Είναι οδιαχειριστής πληροφοριώντου οικοσυστήματος — παραγωγός, ταξινομητής, διαδρομητής.

Δρομολόγιο: από το AsciiDoc στο LangGraph4j

Σήμερα, αυτή η διακυβέρνηση είναι deterministiki : το LLM εφαρμόζει μία διαδικασία περιγραμμένη σε αρχεία AsciiDoc. Είναι ηφάση 1— η μηχανική προτύπων με μνήμη LLM.

La φάση 2Εξάγει κάθε βήμα της διαδικασίας σε μιατυπωμένη εργασία Gradle:

./gradlew endSessionWorkspace    → snapshot vision-archive
./gradlew endSessionProject      → archive .agents/
./gradlew endSessionReport       → rapport multi-zones

La φάση 3θα μοντελοποιήσει τη διαδικασία λήξης της συνεδρίας ως ένανδιάγραμμα κατάστασηςμεhttps://github.com/langgraph4j/langgraph4j[LangGraph4j]:

[Start] → [Inventaire fichiers modifiés]
       → [Classification RGPD] (nœud ONNX)
       → [Branchement par cercle]
            ├→ cercle 0 → snapshot → commit
            ├→ cercle 2 → anonymisation → commit
            ├→ cercle 4 → archive → commit
            └→ cercle 1 → commit configuration/
       → [Rapport] → [End]

Το γράφημα θα εκδοθεί στην CI/CD, θα εκτελεστεί από το Gradle, θα ρυθμιστεί μέσω των GitHub Secrets των plugins. Το LLM δεν θα χρειάζεται πλέον να αποφασίσει για το δρομολόγηση — το γράφημα θα το κάνει.

Τι λύνει αυτή η αρχιτεκτονική (και τι δεν λύνει)

Η χωρική οντολογία δεν καλύπτει όλα. Οι συνθήκες στυλ κώδικα, η ονομασία, οι επιλογές αρχιτεκτονικού σχεδιασμού — όλα αυτά παραμένουν στο πρόμ프트. Τι λύνει η χωρική οντολογία, είναι τοστρώμα ασφάλειας και ορατότητας:που κάθε byte πρέπει να ζει, και ποιος μπορεί να το δει.

Εδώ είναι αυτό που φέρνει συγκρικέμενα :

  1. Κανένας`git push`τυχαίο ενός μυστικού : τα μυστικά είναι σε`configuration/(κύκλος 1). Τα δημόσια έργα είναι σε`foundry/(κύκλος 4). Καμία διαδρομή δεν περνάει και τα δύο.

  2. Δεν υπάρχει κωδικός επιχείρησης στα δεδομένα :`office/περιέχει ορισμένα.adoc`, YAML, JSON Schemas — αλλά όχι`.kt`. Le `build.gradle.kts`οστις ζει εκεί είναι ένα σενάριο κατανάλωσης, όχι κώδικας επιχείρησης.

  3. Δεν υπάρχει εμφανισμένη στρατηγική σκέψη : Τα έγγραφα όρασης ζουν στον μυστικό κήπο (ρίζα εκτός CVS). Οι στιγμιότυπα είναι σε`configuration/`(ιδιωτική θάλαμή). Κανένας, ακόμα και σε ένα επεκταμένο κύκλο εμπιστοσύνης, δεν διαβάζει τη γένεση της στρατηγικής.

  4. Αυτο-προτεραιότητα : το LLM παρατηρεί τη διαφορά μεταξύ της σχετικής άλγεβρας (το υπάρχον) και των χαρτογραφιών των ειδικών (το απαραίτητο). Η επόμενη εργασία ανάπτυξης προκύπτει από αυτή τη διαφορά.

Συμπέρασμα: Η Αρχιτεκτονική ως Λόγος

Δεν βάζω πολιτικό μανιφέστο στο footer του ιστότοπού μου. Δεν βάζω ηθικούς κανόνες στους prompts μου. Η ευθυγράμμιση δεν βρίσκεται στο κείμενο — είναι στοσύστημα αρχείων.

Όταν ένα LLM εργάζεται σε αυτόν τον χώρο, δεν μπορεί να διαρρέει ένα μυστικό (ο δρόμος τομπού το αποτρέπει). Δεν μπορεί να συγχέει μια παιδευτική δεδομένη με τον πηγαίο κώδικα (η φυσική zona είναι διαφορετική). Δεν μπορεί να ξεχάσει έναν κανόνα ασφαλείας σε 80 000 żeton — επειδή ο κανόνας δεν είναι στο πρόμπτ, είναι στο`workspace/→`configuration/→office/→`foundry/`που κάθε ανάγνωση αρχείου είναι ανταποκρινόμενη.

Αυτό είναι το αρχέριο του secure by design εφαρμοσμένο στην ευθυγράμμιση του αντιπροσώπου: μην ζητάτε από το LLM να θυμάται τους κανόνες. Βεβαιωθείτε ότι η αρχιτεκτονική κάνει το λάθος δομικά αδύνατο.

Αpropos, δίνει στο LLM αυτό που καμία προμπτ δεν μπορεί να του δώσει: η ικανότητα τουαισθανομαιpou είναι, αυτό που υπάρχει, αυτό που λείπει — και να συμπεράνει τι πρέπει να κάνει.
