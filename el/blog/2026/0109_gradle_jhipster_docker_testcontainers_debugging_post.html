Η σκηνή: ένα έργο JHipster, ένα build που δεν φορτώνει πια

Το έργο`edster`είναι μια εφαρμογή JHipster που δημιουργήθηκε το 2024. Ο βασικός build script`build.gradle`έμεινε σταθερός για μήνες. Στη συνέχεια αποφασίζουμε να αναβαθμίσουμε την έκδοση:

Συστατικό

Στοχευμένη έκδοση

Gradle

9.4.1

Java

21.0.11-tem (Eclipse Temurin)

JHipster

8.x (πλαίσιο`tech.jhipster:jhipster-framework:8.11.0`)

Spring Boot

3.4.5

Κοτλιν

2.3.0

Docker Engine

29.4.1 (API 1.54)

Η αλλαγή έκδοσης Java γίνεται μέσω του SDKMAN :

sdk use java 21.0.11-tem

Πρώτη εκκίνηση:

$ ./gradlew build --no-daemon

FAILURE: Build failed with an exception.

* Where:
Build file '/home/.../edster/build.gradle' line: 18

* What went wrong:
An exception occurred applying plugin request [id: 'jhipster.cucumber-conventions']
> Failed to apply plugin 'jhipster.cucumber-conventions'.
   > Could not create task ':cucumberTest'.
      > Could not create task ':consoleLauncherTest'.
         > Could not set unknown property 'reportsDir' for task ':consoleLauncherTest'

Ακόμη δεν φτάνουμε από το φόρτωση του build script. Το πρόβλημα είναι στον`buildSrc/src/main/groovy/jhipster.cucumber-conventions.gradle`.

Σφάλμα 1: η φαντασματική μεταβλητή `reportsDir

Το σενάριο`jhipster.cucumber-conventions.gradle`περιέχει :

tasks.register('consoleLauncherTest', JavaExec) {
    dependsOn(testClasses)
    String cucumberReportsDir = file("$buildDir/reports/tests")
    outputs.dir(reportsDir)           // <-- reportsDir n'existe PAS
    classpath = sourceSets["test"].runtimeClasspath
    main = "org.junit.platform.console.ConsoleLauncher"
    // ...
}

Η ορισμένη μεταβλητή είναι`cucumberReportsDir`. Η που χρησιμοποιείται είναι`reportsDir`-- που δεν ορίζεται πουθενά.

Διορθωση : outputs.dir(cucumberReportsDir)

Σφάλμα 2: main = "…​" δεν υπάρχει πλέον στο Gradle 9

Αμέσως επανεκκίνηση:

Could not set unknown property 'main' for task ':consoleLauncherTest' of type org.gradle.api.tasks.JavaExec.

Το Gradle 9 αφαιρεί την ιδιότητα`main`στο όφελος του`mainClass`στις εργασίες`JavaExec`.

Διόρθωση:`mainClass = "org.junit.platform.console.ConsoleLauncher"`

Σφάλμα 3 : sourceCompatibility δεν είναι πια μια ιδιότητα του έργου

Νέο σφάλμα :

Could not set unknown property 'sourceCompatibility' for root project 'edster' of type org.gradle.api.Project.

Το ριζικό script είχε :

sourceCompatibility=17
targetCompatibility=17

Το Gradle 9 διαγράφει αυτές τις ιδιότητες στο επίπεδο ρίζας. Πρέπει να ζουν εντός ενός μπλοκ.java.

Διόρθωση:

java {
    sourceCompatibility = JavaVersion.VERSION_21
    targetCompatibility = JavaVersion.VERSION_21
}

Σφάλμα 4: η Groovy assertion με τρείς οπεράνδες

Το παλιό σενάριο περιείχε:

assert System.properties["java.specification.version"] == "17" || "21" || "24"

Στην Groovy,"21" et "24"`είναι strings truthy. Η έκφραση λύνει σε(…​ == "17") || true || true`, ó,τι είναι πάντα αληθές — αλλά η σύνταξη είναι μη έγκυρη για την επιθυμητή αυστηρή διδασκαλία.

Διορθωση:

assert System.properties["java.specification.version"] in ["17", "21", "23", "24"]

Σφάλμα 5 : η απόρρητη εξάρτηση compileKotlin → `openApiGenerate

Η build προχωρά. Η Κόμπιλαις Kotlin ήταν επιτυχής. Στη συνέχεια :

Task ':compileKotlin' uses this output of task ':openApiGenerate'
without declaring an explicit or implicit dependency.

Το Gradle 9 απορρίπτει τις υπόνυμες εξαρτήσεις μεταξύ των εργασιών. Επειδή`compileKotlin`διαβάζει τις γενημένες πηγές από`openApiGenerate`, πρέπει να δηλώσουμε τον σύνδεσμο.

Διόρθωσησε`build.gradle`:

afterEvaluate {
    tasks.named("compileKotlin").configure {
        dependsOn(tasks.named("openApiGenerate"))
    }
}

Le `afterEvaluate`είναι απαραίτητο επειδή`openApiGenerate`είναι μια επέκταση (plugin OpenAPI Generator) και όχι μια εργασία που είναι άμεσα προσβάσιμη κατά τη φάση της διαμόρφωσης.

Σφάλμα 6 : generateGitProperties σπάει στο `FilterOutputStream.write()

Η μεταγλώττιση του Java πέτυχε. Οι πόροι είναι επεξεργασμένοι. Στη συνέχεια:

> Task :generateGitProperties FAILED

No signature of method: java.io.FilterOutputStream.write() is applicable for argument types: (Integer) values: [103]

Το plugin`gradle-git-properties`Η έκδοση 2.5.0 δεν είναι συμβατή με Java 21 / Gradle 9. Έσωτερικό σφάλμα προσπαθεί να καλέσει`write(int)`μέσω Groovy σε μια ροή που την έκλεισε.

Διόρθωσησε`gradle.properties`:

gitPropertiesPluginVersion=2.5.7

Τελικά: Το Testcontainers εμφανίζεται στη σκηνή

Μέχρι τώρα, ήταν καθαρό "build script debugging". Κάθε σφάλμα ήταν μια ανυπακούστι Gradle 9 ή Java 21 στα scripts build. Μετά από τις έξι διόρθωσης παραπάνω, το`./gradlew assemble`περνάει με επιτυχία.

Αλλά`./gradlew build`εκτελεί επίσης τα τεστ, και τα τεστ Cucumber χρησιμοποιούν Testcontainers για να εκκινήσουν ένα εφημερές PostgreSQL.

Phase 1 : ο δρόμος docker-java

Πρώτο αντανακλαστικό: ο πελάτης Docker Java που χρησιμοποιείται από το Testcontainers στέλνει την έκδοση API`1.32`στο handshake HTTP, αλλά το Docker Engine 29.4.1 απαιτεί ένα ελάχιστο του`1.40`. Το πρόβλημα είναι στον πελάτη, όχι στον daemon.

Έλεγχος της έκδοσης του docker-java που έχει επιλυθεί από το Testcontainers 1.20.6 :

$ ./gradlew dependencies --configuration testRuntimeClasspath | grep docker-java

+--- com.github.docker-java:docker-java-api:3.4.1
+--- com.github.docker-java:docker-java-transport:3.4.1

docker-java 3.4.1, που ημερολογείται από το Testcontainers 1.20.6. Η τελευταία δημόσια έκδοση του docker-java είναι 3.5.1. Ας προσπαθούμε να αναγκάσουμε την αναβάθμιση έκδοσης via`resolutionStrategy`στο μπλοκ`configurations` de build.gradle</think>

configurations {
    all {
        resolutionStrategy.eachDependency { details ->
            if (details.requested.group == "com.github.docker-java"
                && details.requested.name.startsWith("docker-java")) {
                details.useVersion("3.5.1")
            }
        }
    }
}

Επαναφορά του build. Το ίδιο σφάλμα:`client version 1.32 is too old`.

Έλεγχος του cache του Gradle: τα JARs έχουν ξανα-βεβαίως ληφθεί, αλλά το σφάλμα παραμένει. το docker-java 3.5.1 συνεχίζει να στέλνει`1.32`. Αυτή η έκδοση δεν είναι άρα επαρκής για το Docker Engine 29.4.1.

Πράξη καθαρισμού: διακαθαρίστε πλήρως το cache του Gradle, για να είστε σίγουροι :

rm -rf ~/.gradle/caches
rm -rf /path/to/project/.gradle

Πλήρης επανεκκίνηση μετά καθαρισμού. Το ίδιο λάθος.

Φάση 2: έρευνα διαδικτύου και διαδρομή Αριάδνης GitHub

docker-java 3.5.1 είναι ανεπαρκές. Μόνο να ψάξουμε αν κάποιος αντιμετώπισε αυτό το ακριβές πρόβλημα.

Στοχευμένη αναζήτηση στα ζητήματα testcontainers-java και docker-java:

site:github.com/testcontainers "client version 1.32 is too old"
site:github.com/docker-java "client version 1.32" Docker Engine 29

Αμέσα πρώτα αποτελέσματα:

  • testcontainers-java#11210—[Bug]: client version 1.32 is too old. Minimum supported API version is 1.44

  • testcontainers-java#11212—[Bug]: Docker 29.0.0 could not find a valid Docker environment

  • testcontainers-java#11491—[Bug]: Incompatibility in Ubuntu Github runners with Docker Engine 29.1.*

Το νήμα της Αριάδνης είναι σαφές : Ο Docker Engine 29.x έχει αυξήσει την ελάχιστη έκδοση του API του σε`1.24`(παλιό λάθος) σε`1.40`. Testcontainers 1.20.x χρησιμοποιεί το docker-java 3.4.x το οποίο διαπραγματεύεται την έκδοση API στέλνοντας`1.32`. Ο δαίμονας αρνείται ευγενικά αλλά στερεά.

  2. Τα modules έχουν γίνειτονομασμένοι με το πρόθεμα `testcontainers-

Φάση 3: η παγίδα των μετονομασμένων artifacts

Η μετονομασία είναι βίαιη. Στον Testcontainers 2.x, κανένα από τα παλαιά ονόματα δεν λειτουργεί πλέον με αυτό το όνομα :

Παλαιό όνομα (1.x)

Νέο όνομα (2.x)

org.testcontainers:postgresql

org.testcontainers:testcontainers-postgresql

org.testcontainers:jdbc

org.testcontainers:testcontainers-jdbc

org.testcontainers:junit-jupiter

org.testcontainers:testcontainers-junit-jupiter

org.testcontainers:testcontainers

αμετάβλητο

Πρώτη προσπάθεια: εφαρμόστε τη BOM Testcontainers 2.0.5 και τα νέα ονόματα artifacts σε`build.gradle`.

dependencies {
    testImplementation platform("org.testcontainers:testcontainers-bom:2.0.5")
    testImplementation "org.testcontainers:testcontainers-postgresql"
    testImplementation "org.testcontainers:testcontainers-jdbc"
    testImplementation "org.testcontainers:testcontainers-junit-jupiter"
    testImplementation "org.testcontainers:testcontainers"
}

./gradlew build

FAILURE: Could not find org.testcontainers:jdbc:2.0.5.
Could not find org.testcontainers:junit-jupiter:2.0.5.

Το BOM του testcontainers-bom δεν είναι αρκετό.Γιατί; επειδή Spring Boot 3.4.5 εκθέτει το δικό του BOM διαχείρισης εξαρτήσεων (spring-boot-dependencies) ο οποίοςνικάστο BOM του Testcontainers στη διάσυνδεδεμένη επίλυση. Spring Boot διορθώνει`testcontainers` à 1.20.6, και άρα όλα τα artifacts που δεν είναι ρητά στο BOM του Spring Boot (όπως τα νέα`testcontainers-*) λύνουν προς τα παλαιά ονόματα`1.20.6-- που δεν υπάρχουν πια σε αυτήν την έκδοση.

Επιθεωρώντας το`dependencies --configuration testRuntimeClasspath`, βρίσκεται :

+--- org.testcontainers:testcontainers -> 1.20.6 (*)
|    \--- org.testcontainers:testcontainers:2.0.5 -> 1.20.6

Le →`δεικνύει την αντικατάσταση : Testcontainers 2.0.5 είναι απαιτούμενο, αλλά το Spring Boot αναγκάζει`1.20.6.

Τελική διόρθωσημέσα`build.gradle`:

configurations {
    all {
        resolutionStrategy.eachDependency { details ->
            if (details.requested.group == "com.github.docker-java"
                && details.requested.name.startsWith("docker-java")) {
                details.useVersion("3.7.1")
            }
            if (details.requested.group == "org.testcontainers"
                && details.requested.name == "testcontainers") {
                details.useVersion("2.0.5")
            }
        }
    }
}

dependencies {

    testImplementation "org.testcontainers:testcontainers-postgresql"
    testImplementation "org.testcontainers:testcontainers"
    // ... autres dépendances Spring Boot
}

Le `resolutionStrategy.eachDependency`είναι ο μοναδικός τρόπος να παρακάμπτει το BOM`spring-boot-dependencies`διαχειρίζεται από το πρόσθετο Spring Boot. Ο έλεγχος ισότητας σε`details.requested.name == "testcontainers"`Είναι intentional restrictive: αναγκάζουμε μόνο τον πυρήνα του module. Τα modules`testcontainers-*`ακολουθούν το BOM του Testcontainers 2.0.5 που δηλώσαμε ρητά.

Συμπέρασμα

Εάν η δημιουργία JHipster/Gradle σας αποτύχει μετά από μια αναβάθμιση Gradle 9 + Docker Engine 29, τα σφάλματα διαχωρίζονται σε δύο κατηγορίες:

Σφάλματα σε build script(τα 6 πρώτα) : Το Gradle 9 διαγράφει ιδιότητες και συντακτικές που δούλευαν για χρόνια (sourceCompatibility=, main =, reportsDir). Οι μετακινήσεις είναι μηχανικές ότανγνωρίζουμε την νέα API.

Σφάλματα χρόνου εκτέλεσης Docker(οι 2 τελευταίες): Docker Engine 29.4.1 απομακρύνει τους πελάτες API < 1.40. Testcontainers 1.20.6 (υποχρεωτικό από το Spring Boot 3.4.5) χρησιμοποιεί το docker-java 3.4.1 που στέλνει 1.32. Μόνο το Testcontainers 2.0.5 + docker-java 3.7.1 λύνει το πρόβλημα, με τη μετονομασία των artifacts και το ενσarcaσμα έκδοσης διά`resolutionStrategy.eachDependency`ο μοναδικός τρόπος για να αποφύγετε το εμνενό BOM του Spring Boot.

Το script Gradle στη ρίζα του έργου είναι τώρα καθαρό.`./gradlew build`τρέχει στο Java 21, Gradle 9.4.1, Spring Boot 3.4.5 και Docker Engine 29.4.1.
