Κλωνοποιήστε ένα αποθετήριο προσθήκης Gradle. Άνοιξτε ένα τερματικό. Τι πληκτρολογείτε; Επόμενο;`./gradlew tasks`, βεβαίως. Αλλά σε ποilon φάκελο ? Η ρίζα ? Η υποενότητα ? Απαιτείται πρώτα να διαβάσουμε ένα README για να μάθουμε πώς να κατασκευάσουμε; Αν διστάσετε, δεν θα…​ Μια δευτερόλεπτο, η αρχιτεκτονική του έργου είναι χαμένη.

Αυτό είναι πώς έλυσα αυτό το πρόβλημα μια για πάντα — και γιατί αυτό το pattern είναι σήμερα η υπογραφή όλων των plugins Gradle μου σε`foundry/public/`.

Το πρόβλημα: Τρεις αρχιτεκτονικές που μου έκαναν να χάσω χρόνο

Πριν από τη σύγκλιση στον τρέχοντα μοτίβο, έχω δοκιμάσει μεταξύ τριών προσεγγίσεων. κλασικοί τρόποι για να οργανώσετε ένα πρόσθετο Gradle. Κάθεμία είχε έναν αδύνατο έλλιπτος.

Επιλογή 1 : Το Απομόνωμενο Πλαγκιν (χωρίς dogfooding)

Το έργο περιέχει μόνο το πλαγκιντ. Δεν υπάρχει παράδειγμα κατανάλωσης. Δεν έργο που το ασκεί. Για να το δοκιμάσουμε, πρέπει να δημιουργήσουμε ένα εξωτερικό έργο, y αναφορά του plugin μέσω`mavenLocal`ή ένα συνθέτο build, και μόνο εδώ ελέγξτε ότι λειτουργεί

$ git clone mon-plugin
$ cd mon-plugin
$ ./gradlew build          # le plugin compile
$ # ... et maintenant ? comment je l'essaie ?

Ένα πρόσθετο Gradle χωρίς παράδειγμα χρήσης, είναι μια βιβλιοθήκη χωρίς δοκιμές ενσωμάτωσης. Ποτέ δεν ξέρεις αν η τελευταία αλλαγή έχει σπάσει την εμπειρία του χρήστη.

γεννάει`settings.gradle.kts`με`include("plugin")`. Ο root και το υπομέρος μοιράζονται τον ίδιο daemon και τις ίδιες ρυθμίσεις, τα ίδια κατάλογοι. Πρακτικό, αλλά συνδεδεμένο.

  • Ο rootπρέπεινα έχει την ίδια έκδοση του Gradle με το υπο-μέρος.

  • `libs.versions.toml`είναι κοινό — κοινοί καταλόγοι εκδόσεων, εξαρτήσεις

οι οποίοι φεύγουν από ένα module σε ένα άλλο.

  • Δεν είναι δυνατόν να χτίσετε το plugin ανεξάρτητα από το root.

  • Η CI πρέπει να χτίζει τα δύο modules, ακόμα κι αν μόνο το plugin έχει αλλάξει.

Επιλογή 3 : Η σύνθετη κατασκευή (includeBuild())

Χωρίζουμε τα δύο σε ξεχωριστά builds Gradle και τα συνδέουμε μέσω includeBuild("mon-plugin")`σε`settings.gradle.kts.

Αυτό είναι ήδη καλύτερο. Η κατασκευή του plugin είναι απομονωμένη. Αλλά ο καταναλωτής πρέπει να αναφέρεται ρηττά το εξωτερικό build — και την έξοδο του `./gradlew tasks`εξαρτάται από τη σωστή ρύθμιση της ρίζας συστατικό. Το κλώνημα δεν είναι zero-config: πρέπει να ξέρετε ότι το το plugin είναι σε ξεχωριστό φάκελο, που το root το αναφορά, κ.λπ.

.
├── settings.gradle.kts   → includeBuild("plugin-build/")
├── build.gradle.kts      → plugins { id("mon-plugin") }
└── plugin-build/
    ├── settings.gradle.kts
    └── build.gradle.kts

ψάχνα καλύτερο. Πολύ καλύτερο.

Η Λύση : Δύο ανεξάρτητες Builds, Μια ρίζα καταναλωτή

Εδώ είναι το pattern που τελικά υιοθέτησα:

├── build.gradle.kts              ← 3 lignes : apply plugin + dogfood
├── gradle/

Η ρίζα, αυτή, κάνει μόνο ένα πράγμα: να εφαρμόσει το plugin.

Τρεις οφέλη που, συνδυασμένοι, αξίζουν το κόστος της «διπλοποίησης» :

1. Εγγενής Dogfooding, άμεσος Feedback

Ο καλύτερος έλεγχος ενός plugin Gradle είναι να το χρησιμοποιήσετε. Δεν είναι ένας mocked unit test. Δεν είναι`GradleRunner`με ένα έργο του test. Ένας αληθινός build ο οποίος εφαρμόζει το plugin σε αληθινά αρχεία.

$ git clone bakery-gradle
$ cd bakery-gradle
$ ./gradlew bake    # ← le plugin est exercé immédiatement

Αν το plugin είναι σπασμένο, το root build το λέει. Δεν χρειάζεται να πάτε ψάχνε για ένα εξωτερικό έργο δοκιμής. Το dogfooding είναι το πρώτο Η εργασία που εκκινεί ένας νέος συνεισφέρον. Αυτό είναι ο τελικός smoke test.

Ο κανόνας είναι απλός: αν η ρίζα μεταγλωττίζει και`./gradlew tasks` Εμφανίζει τις εργασίες του plugin, το plugin είναι λειτουργικό. Χωρίς έκπληξη εν παραγωγή.

2. Κλωνοποίηση χωρίς ρύθμιση

Un `git clone && ./gradlew tasks`και ο πρόσφατα φθάσας βλέπει όλο περπατώ χωρίς να ρυθμίσω κάτι. ο`build.gradle.kts`η ρίζα είναι το ζωντανό έγγραφο χρήσης του plugin. Το`site.yml`παρά Εμφαίνει την αναμενόμενη ρύθμιση.

Συγκρίνετε με το εναλλακτικό : ένα README τριών παραγράφων που Εξηγεί πώς builder το plugin και πώς builder το έργο από δοκιμή. Ένας νέος συνεισφέρον διαβάζει το README σε διάγώνιο, κάνει λάθος, ανοίγει ένα issue — ενώ η πληροφορία θα μπορούσε να είναι executable.

Η πιο αξιόπιστη τεκμηρίωση δεν είναι αυτή που διαβάζεται. Αυτό είναι αυτή πουΕκτέλε. Η ρίζα του build είναι η τεκμηρίωση εκτελέσιμο του plugin.

3. Απομονωμένες κατασκευές, ανεξάρτητο CI

Το plugin έχει το δικό του Gradle wrapper, το δικό του κύκλο ζωής, τα δικά του τεστ. Μπορείτε:

  • Αναβαθμίστε το Gradle στο πρόσθετο χωρίς να αγγίξετε τη ρίζα

  • Προσθέστε μια εξάρτηση στο πρόσθετο χωρίς να διαρρεύει στον ριζικό

  • Σπάτε το plugin χωρίς να επηρεάξετε το ριζικό build (όσο μη

Μη δημοσιεύετε τη σπασμένη έκδοση)

  • Να έχετε μια CI που κάνει build/test το plugin, και μια άλλη που ασκεί το plugin

Αυτή η αρχιτεκτονική ενσωματώνεται φυσικά στον DAG N0→N3 από το χώρο εργασίας μου. Το μοτίβο είναι : το plugin N2 είναι ο κέντρο από τις δικές του εξαρτήσεις, η ρίζα N3 είναι ένα τερματικό που εφαρμόζει τους hubs*

Συμπέρασμα: Η φαινομενική διπλασια που κερδίζει χρόνο

Όταν δείχνω αυτή τη δομή σε κάποιον, η πρώτη αντίδραση είναι συχνά: « Αλλά έχεις δύο`gradlew`, δύο`settings.gradle.kts`, δύο`libs.versions.toml`— είναι διπλοποίηση !

Ναι. Και όχι.

Η « διπλοποίηση » είναι η δημιουργία ενός αντίγραφο της ίδιας πληροφορίας σε δύο τοποθεσίες. Εδώ, είναι δύο αρχεία διακριτά που εξυπηρετούν δύο διακριτές χρήσεις: το κατάλογο του plugin (30+ εξαρτήσεις για τον builder) και το κατάλογο της ρίζας (2-3 εξαρτήσεις για κατανάλωση). Το wrapper του plugin (κλειδωμένη έκδοση για την ανάπτυξη) και το wrapper της ρίζας (πιθανώς διαφορετική έκδοση, για άσκηση του plugin).

Αυτό δεν είναι διπλοποίηση. Είναι διαχωρισμού του υπευθυνότητες εφαρμοσμένη στο σύστημα build. Κάθε build Κάνει ένα πράγμα, και μόνο ένα. Η ρίζα καταναλώνει. Το πρόσθετο χτίζεται.

Το κόστος; Μια παραγγελία`publishToMavenLocal`μεσα στο build του plugin και το build της ρίζας. Το κέρδος; Μια αρχιτεκτονική σαφήνεια που διαγράφει ώρες αποσφαλμάτωσης στα επόμενα βήματα.

Αφού υλοποίησα αυτό το μοτίβο στο`bakery-gradle`, plantuml-gradle, codebase-gradle, και τα άλλα plugins του`foundry/public/, δεν έχω πιο ποτέ δεν έχω διστάσει όταν ανοίγω ένα τερματικό σε ένα από τα αποθετήριά μου. Ο πρώτος αντανακλαστικός —./gradlew tasks`— περιπατησε παντα, δωσε παντα τα σωστά εργασιές, και μου λέει αμέσως αν όλα είναι καλά

Αυτό είναι η σωστή αρχιτεκτονική. Δεν διαβάζεται στο README. Δοκιμάζεται σε ένα τερματικό, σε λιγότερο από δέκα δεuterόλεπτα.
