ข้อสังเกต: Prompt Engineering เป็นปราสาททราย

เป็นเวลาสามสัปดาห์ ฉันพัฒนาปลั๊กอิน Gradle ด้วย Opencode โดยใช้ LLM สามตัวที่แตกต่างกัน — Kimi K2.6, GLM-5.1 และ DeepSeek-V4-Pro (ตัวเดียวที่รอดชีวิต แต่นั่นเป็นอีกเรื่องหนึ่งได้กล่าวถึงแล้วที่นี่) วิธีการกำกับดูแลเอเจนต์ของฉันฉันได้บันทึกไว้อย่างละเอียดในบทความก่อนหน้า อาศัยไฟล์ AsciiDoc —AGENT.adoc, INDEX.adoc, PROMPT_REPRISE.adoc— ซึ่งโหลดกฎ แบ็กล็อก และประวัติราว 30,000 โทเค็นในทุกต้นเซสชัน

และแม้จะมีโครงสร้างพื้นฐานด้านเอกสารนี้ สองสิ่งก็ทำให้ฉันประหลาดใจ:

  1. LLM ลืม แม้จะมีกฎเด็ดขาดอยู่ที่ด้านบนของแต่ละไฟล์ EAGER เมื่อเกิน 60,000 โทเคนสะสม (บริบทเริ่มต้น + บทสนทนา) Kimi K2.6 เริ่มเสนอ`Write`เขียนทับไฟล์กำหนดค่า GLM-5.1 เข้าใจโทเคน Firebase ผิดว่าเป็น placeholder ที่ต้องแทนที่ กฎถูกเขียนไว้ — แต่ LLM ไม่ มองเห็น กฎเหล่านั้นอีกต่อไป

  2. การกำกับดูแลเองก็กลายเป็นปัญหา. หลังจากนำกลไก Hot/Warm/Coldบทความเกี่ยวกับการหมุนเวียนแบ็กอัป มาใช้เพื่อหลีกเลี่ยงการระเบิดของบริบท ไฟล์ EAGER ของฉันยังคงมี 1414 บรรทัดฉันได้บันทึกการตรวจสอบนี้ไว้ที่นี่ การกำกับดูแล — ซึ่งออกแบบมาเพื่อปกป้อง LLM จากความอิ่มตัว — กลับทำให้ LLM อิ่มตัว

ฉันต้องการกลไกการจัดแนวที่ไม่ขึ้นอยู่กับจำนวนโทเค็นในพรอมต์

สวนลับ : พื้นที่นอก CVS

นี่คือแนวคิดที่สำคัญที่สุด — และเป็นแนวคิดที่ขัดกับสามัญสำนึกที่สุด

ราก`workspace/ไม่มี.git/. เอกสารที่อาศัยอยู่ที่นั่น (`WORKSPACE_VISION.adoc, WORKSPACE_AS_PRODUCT.adoc, WORKSPACE_ORGANIZATION.adoc— และฉบับที่คุณกำลังอ่านอยู่ในขณะนี้ ซึ่งมาจากสิ่งนั้น) ไม่ได้มีไว้เพื่อถูกทำเวอร์ชัน แชร์ หรือแม้แต่ถูกอ่านซ้ำโดยใครอื่นนอกจากฉัน สิ่งเหล่านี้เป็นความคิดที่กำลังงอกงาม.

สวนลับเป็น out-of-CVS โดยธรรมชาติ การไม่มีระบบจัดการเวอร์ชันคือเงื่อนไขของเสรีภาพในการคิด เราไม่เขียนที่นั่นเพื่อให้มีคนอ่าน — เราเขียนเพื่อทำให้วิสัยทัศน์ของตนเองชัดเจนขึ้น

แต่เสรีภาพนี้มีราคาที่ต้องจ่าย: หนึ่ง`rm`โดยบังเอิญ และนั่นคือหลายเดือนแห่งการคิดเชิงกลยุทธ์ที่หายไป ทางแก้ไม่ใช่การทำเวอร์ชันสวน (นั่นจะเป็นการทำลายมัน) — แต่คือการมิเรอร์ในวงที่แคบที่สุด

กลไกสแนปช็อต

ฉันได้สร้าง`configuration/vision-archive/: สแนปช็อตที่ระบุวันที่ของทั้งหมด.adoc`ของราก ซึ่งถูกคอมมิตในรีโพซิทอรีส่วนตัว`configuration/`. แต่ละเซสชันการระดมสมองจะสร้างสแนปช็อต:

DATE=$(date +%Y-%m-%d)
mkdir -p /home/cheroliv/workspace/configuration/vision-archive/$DATE
cp /home/cheroliv/workspace/*.adoc /home/cheroliv/workspace/configuration/vision-archive/$DATE/
cd /home/cheroliv/workspace/configuration && git add vision-archive/ && \
  git commit -m "vision-archive: snapshot $DATE"

กระบวนการนี้ถูกกระตุ้นเมื่อสิ้นสุดเซสชันโดยตัว LLM เอง ซึ่งดำเนินงานการกำหนดเส้นทางโดยรวมนี้ แต่ละสแนปช็อตบันทึกสถานะทั้งหมดของความคิดเชิงกลยุทธ์ ณ จุดเวลา T

ประวัติ Git ของ`configuration/`กลายเป็นชีวประวัติความคิดเชิงกลยุทธ์ของฉัน. ฉันสามารถทำ`git log — vision-archive/`และดูการเปลี่ยนแปลงของการมองเห็นของฉัน ทีละเซสชัน ทีละวันที่

ตัวอย่างจริงของประวัติหลังจากวันทำงานหนึ่งวัน:

$ git -C configuration log --oneline -- vision-archive/
1089d1b vision-archive: fin de session finale 2026-05-03
6b21eaf vision-archive: fin de session 2026-05-03-1300
1690f82 vision-archive: post-article 2026-05-03
28e6593 vision-archive: post-migration 2026-05-03
3707b78 vision-archive: snapshot 2026-05-03 — jardin secret initial

ห้าสแนปช็อตในหนึ่งวัน แต่ละอันคือจุดกู้คืน แต่ละอันคือหมุดหมายในกำเนิดของกลยุทธ์

แฟ้ม`configuration/vision-archive/latest/`มี…​อย่างถาวรสำเนาการทำงานของสแนปช็อตล่าสุด ซึ่งใช้เป็นข้อมูลอ้างอิงด่วนโดยไม่ต้องนำทางผ่านประวัติ Git

และสำหรับ LLM นั้น มันเป็นออราเคิลแห่งความสอดคล้อง: เมื่อเขาสังเกตเห็นความขัดแย้งระหว่างการนำไปใช้ในปัจจุบันกับวิสัยทัศน์ที่ถูกเก็บถาวร ณ วันที่ก่อนหน้า เขาสามารถรายงานความขัดแย้งนั้นได้

`configuration/`ไม่ได้มีเพียงคลังเก็บแห่งนิมิตเท่านั้น หน้าที่หลัก — และในอนาคต — ของมันคือการเป็นเซิร์ฟเวอร์ Spring Cloud Config. ความลับทั้งหมด โทเค็น ข้อมูลรับรอง และคำอธิบายโครงสร้างพื้นฐานอยู่ที่นี่ ในที่เก็บ Git ส่วนตัวที่เข้าถึงได้เฉพาะเจ้าของเท่านั้น

ทำไมต้องเป็นรีโพแยกต่างหากแทนที่จะเป็นไฟล์`.env`ในแต่ละโปรเจกต์ ?

  • การ push ความลับโดยไม่ตั้งใจ : เป็นไปไม่ได้ ความลับอยู่ใน private repository ที่โปรเจกต์สาธารณะไม่สามารถอ้างอิงได้โดยผิดพลาด

  • Audit : ประวัติ Git ให้ร่องรอยของการเปลี่ยนแปลงการกำหนดค่าทุกครั้ง ใครเปลี่ยนอะไร เมื่อใด ด้วยแฮช SHA ใด

  • ย้อนกลับ :`git revert`บนการกำหนดค่าที่เสียหาย ทันที โดยไม่ต้องสำรองข้อมูลด้วยตนเอง

ห้องสมุด: office/ ในฐานะข้อมูลที่ใช้สอยได้

`office/`เป็นส่วนเอกสารคู่ขนานของงานพัฒนา ประกอบด้วยบทความบล็อก ข้อกำหนดทางเทคนิค สื่อการฝึกอบรม (ไดเรกทอรีหลักสูตร FPA 38 ไดเรกทอรี, SPG/SPD, สคีมา JSON, อนุกรมวิธาน Bloom/Harrow/Krathwohl) — ทุกสิ่งที่ประกอบเป็นสื่อการสอน.

แต่`office/`ไม่ใช่แค่ลิ้นชักเก็บเอกสาร มันคือแหล่งข้อมูลที่มีโครงสร้างว่าปลั๊กอิน Gradle ของ`foundry/`บริโภค บทความบล็อกใน`office/`เป็นรายการที่ปลั๊กอินจะแปลงเป็น HTML SPG AsciiDoc ใน`office/metiers/FPA/`เป็นอาร์ติแฟกต์ที่ออร์เคสเตรเตอร์จะพาร์สเพื่อสร้างสไลด์ ควิซ และแคปซูลวิดีโอ

Et le `build.gradle.kts`ที่รากของ`office/`ไม่ใช่โค้ดธุรกิจ — เป็นสคริปต์สำหรับการใช้ระบบนิเวศของปลั๊กอิน. เขาพูดว่า "นี่คือปลั๊กอิน Gradle ที่ฉันใช้ นี่คือบริบทของเวิร์กสเปซของฉัน

พีชคณิตเชิงสัมพันธ์ของเวิร์กสเปซและเดลตาที่สังเกตได้

เมื่อ LLM ไล่ดู`foundry/, เขามีโครงข่ายข้อมูลที่มีโครงสร้าง: โหนด (ปลั๊กอิน, ไฟล์, การทดสอบ, การพึ่งพา), เส้นเชื่อมที่มีชนิด (`import, depends_on, generates, tests), ความสัมพันธ์เชิงองค์ประกอบและเชิงลำดับ (`training-gradle`ดึงคลังอ้างอิง`slider-gradle`สร้างสไลด์ →`capsule-gradle`ตัดต่อวิดีโอ)

พีชคณิตนี้ไม่ได้เขียนไว้ที่ใดอย่างชัดเจน — แต่它具有*สังเกตได้* แต่ละ`build.gradle.kts`เปิดเผยส่วนที่ต้องพึ่งพา แต่ละ`INDEX.adoc`แสดงการอ้างอิงข้าม

เวกเตอร์ผสมของบริบท: RAG + pgvector + Graphify

พีชคณิตเชิงสัมพันธ์ไม่ใช่โครงสร้างทางทฤษฎี มันถูก ทำให้เป็นรูปธรรม โดยองค์ประกอบสามส่วนที่ก่อตัวเป็นเวกเตอร์คอมโพสิตของบริบทสำหรับ LLM

องค์ประกอบที่ 1 — RAG LangChain4j + PostgreSQL pgvector

ฉันมี LangChain4j ที่ใช้งานจริงในโปรดักชันแล้วในปลั๊กอินสองตัว:`slider-gradle`(ผู้ให้บริการ LLM 4 ราย) และ`plantuml-gradle`(7 ผู้ให้บริการ). เอ็มเบดดิง ONNX (AllMiniLmL6V2) จัดทำดัชนีข้อมูลของ`office/`และซอร์สโค้ดของ`foundry/`ใน PostgreSQL + pgvector

RAG นี้ทำงานบนสองมิติ:

  • ข้อมูลมิติ : เอกสาร`office/`(SPG, บทความ, หลักสูตรอบรม, สคีมา JSON)

  • มิติโค้ด : โค้ดเบส`foundry/`(ซอร์สโค้ด Kotlin, การทดสอบ Cucumber, AGENT.adoc)

จุดตัดครอบคลุมทั้ง อะไร (โดเมนธุรกิจ) และ อย่างไร (การนำไปปฏิบัติ)

องค์ประกอบ 2 — Knowledge Graph Graphify

Graphify ได้รับการผสานรวมไว้ใน`plantuml-gradle`(109 tests, 380/380 PASS) และสร้าง`graph.json`— กราฟความรู้แบบมีโครงสร้างที่มีโหนด เส้นเชื่อม และชุมชนที่ตรวจพบโดยอัตโนมัติ

ต่างจาก RAG ที่ทำงานโดยใช้ความคล้ายคลึงเชิงเวกเตอร์ (แบบคลุมเครือ) กราฟความรู้ทำงานโดยความสัมพันธ์ที่แน่นอน(ดีเทอร์มินิสติก) :`graphify query`สำหรับการสอบถามเชิงความหมาย (~50 โทเคน),`graphify path`เพื่อนำทาง,`graphify explain`เพื่ออธิบาย

องค์ประกอบที่ 3 — Graphify แบบเพิ่มทีละส่วน: กระจัดกระจาย, รวมได้, พร้อมใช้

LLM ไม่ใช่เพียงเครื่องสร้างข้อความธรรมดาอีกต่อไป มันคือผู้จัดการข้อมูลของระบบนิเวศ — ผู้ผลิต, ตัวจำแนกประเภท, เราเตอร์

สิ่งที่สถาปัตยกรรมนี้แก้ไข (และสิ่งที่มันไม่ได้แก้ไข)

ออนโทโลยีเชิงพื้นที่ไม่ได้ครอบคลุมทุกอย่าง ข้อกำหนดรูปแบบการเขียนโค้ด การตั้งชื่อ การตัดสินใจออกแบบสถาปัตยกรรม — ทั้งหมดนี้ยังคงอยู่ในพรอมต์ สิ่งที่ออนโทโลยีเชิงพื้นที่แก้ไขได้คือชั้นความปลอดภัยและการมองเห็น: ที่ซึ่งแต่ละไบต์ต้องอยู่ และใครที่สามารถมองเห็นมันได้

นี่คือสิ่งที่มันนำมาอย่างเป็นรูปธรรม:

  1. ไม่มี`git push`โดยบังเอิญของความลับ : ความลับอยู่ใน`configuration/(วงกลม 1) โครงการสาธารณะอยู่ใน`foundry/(วงกลม 4) ไม่มีเส้นทางใดตัดผ่านทั้งสอง

  2. ไม่มีโค้ดทางธุรกิจในข้อมูล :`office/มี.adoc`, YAML, JSON Schemas — แต่ไม่มี`.kt`. Le `build.gradle.kts`ซึ่งอาศัยอยู่ที่นั่นเป็นสคริปต์การบริโภค ไม่ใช่โค้ดธุรกิจ

  3. ไม่มีการเปิดเผยความคิดเชิงกลยุทธ์ : เอกสารวิสัยทัศน์อยู่ในสวนลับ (รูทที่อยู่นอก CVS) สแนปช็อตอยู่ใน`configuration/`(ตู้เซฟส่วนตัว) ไม่มีใคร แม้แต่ในวงความไว้วางใจที่ขยายออกไป อ่านจุดกำเนิดของกลยุทธ์

  4. การจัดลำดับความสำคัญอัตโนมัติ : LLM สังเกตเดลตาระหว่างพีชคณิตเชิงสัมพันธ์ (สิ่งที่มีอยู่) กับแผนที่ของผู้เชี่ยวชาญ (สิ่งที่จำเป็น) งานพัฒนาถัดไปเกิดขึ้นจากเดลตานี้
