하이브리드 아키텍처 : Supabase와 Spring Boot로 얻는 두 세계의 최고

게시: 14 January 2026

읽기 시간 : 12 minutes

Supabase의 간결함과 Spring Boot의 강력함 사이에서 선택하기보다 왜 두 가지를 결합하지 않을까요? 각 기술의 장점을 활용하는 하이브리드 아키텍처를 살펴보세요.

똑

[]

현대 건축의 가짜 딜레마

정적 프론트엔드를 사용해 현대적인 애플리케이션을 구축할 때, 종종 이진 선택에 직면하게 됩니다 :

  • 백엔드-어즈-어-서비스 솔루션에 모든 것을 걸다(Supabase, Firebase) - 간단하지만 제한적

  • 전체 백엔드 구축하기(Spring Boot, Node.js) - 강력하지만 복잡한

이 선택은 가짜 딜레마입니다. 하이브리드 아키텍처는 세 번째 길을 제시합니다: 각 기술을 그들이 가장 잘하는 곳에 사용하는 것.

건축 비전

전통적인 건축: 일체형

@startuml
skinparam backgroundColor #FEFEFE
skinparam componentStyle rectangle

package "전통적인 건축" {
  actor Utilisateur as user
  component "프론트엔드" as frontend #LightBlue
  component "모놀리식 백엔드" as backend #LightCoral {
    [Authentification]
    [CRUD]
    [Logique Métier]
    [Jobs]
    [APIs Tierces]
  }
  database "데이터베이스" as db #LightGray

  user --> frontend
  frontend --> backend : Toutes les requêtes
  backend --> db
}

note right of backend
  Tout passe par le backend
  même les opérations simples

  ⚠️ Point de congestion unique
  ⚠️ Complexité dès le départ
  ⚠️ Couplage fort
end note
@enduml

이 접근 방식에서는 가장 간단한 작업(글 읽기, 댓글 작성)이라 할지라도 백엔드를 경유해야 하며, 첫날부터 복잡성의 비용을 지불하게 됩니다.

BaaS 아키텍처: 모든 대리자

@startuml

  actor Utilisateur as user
  component "프론트엔드" as frontend #LightBlue

    [Auth]
    [Database]
    [Storage]
    [Edge Functions]
  }

  user --> frontend
  frontend --> baas : Toutes les opérations
}

note right of baas
  Développement rapide
  Pas de serveur à gérer

  ⚠️ Limité pour logique complexe
  ⚠️ Vendor lock-in
  ⚠️ Edge Functions contraintes
end note
@enduml

반면에, BaaS에 모든 것을 위임하는 것은 처음에는 매력적이지만, 비즈니스 로직이 복잡해지면 곧 한계가 드러납니다.

하이브리드 아키텍처 : 책임 분리

@startuml
skinparam backgroundColor #FEFEFE

  component "정적 사이트 JBake" as frontend #SkyBlue

  component "예약된 작업" as jobs
  component "통합" as integrations

frontend --> crud : Articles, Profils

frontend --> logic : Calculs, Rapports
frontend --> orchestration : Workflows
logic --> integrations : Stripe, APIs
orchestration --> db
jobs --> db

crud --> db
auth --> db

note bottom of db
  **Une seule source de vérité**
  Partagée entre Supabase et Spring Boot
end note

note right of auth
  **Gratuit jusqu'à 50k users**
  Configuration en quelques clics
  OAuth2 multi-providers
end note

note right of logic
  **Activé seulement si nécessaire**
  Kotlin + Coroutines
  Transactions complexes
end note
@enduml

하이브리드 아키텍처는 복잡성과 운영의 특성에 따라 책임을 명확히 분리한다.

흐름 오케스트레이션

플럭스 1 : 중앙 집중식 인증

@startuml
skinparam backgroundColor #FEFEFE
autonumber

actor "사용자" as user
participant "JBake" as jbake
participant "Supabase Auth" as auth
participant "스프링 부트" as spring
database "PostgreSQL" as db

== Authentification ==
user -> jbake : Clique "로그인"
jbake -> auth : Redirect OAuth2 (Google/GitHub)
auth -> user : Consent screen
user -> auth : Autorise
auth -> auth : Génère JWT
auth -> jbake : Retourne JWT + Refresh Token
jbake -> jbake : Stocke tokens (sessionStorage)

== Accès aux Ressources ==
group Opération Simple (CRUD)
  user -> jbake : Crée un article
  jbake -> db : POST avec JWT
  note right: Supabase Row Level Security\nvérifie le JWT automatiquement
  db -> jbake : Article créé
end

group Opération Complexe (Métier)
  user -> jbake : Génère un rapport
  jbake -> spring : POST /api/reports\navec JWT
  spring -> spring : Valide JWT Supabase
  spring -> spring : Extrait claims (user_id, roles)
  spring -> db : Requêtes complexes
  spring -> jbake : Rapport généré
end

note over auth, spring
  **Le JWT est universel**
  Valide par Supabase ET Spring Boot
  Pas de double authentification
end note
@enduml

핵심 포인트: 하나의 인증 프로세스, 하나의 JWT, 어디에서나 사용 가능.

플럭스 2 : 복잡한 비즈니스 프로세스의 오케스트레이션

@startuml
skinparam backgroundColor #FEFEFE
autonumber

actor "클라이언트" as user
participant "JBake" as jbake
participant "스프링 부트" as spring
participant "Supabase DB" as supadb
participant "스트라이프 API" as stripe
participant "재고 서비스" as inventory
participant "이메일 서비스" as email
database "PostgreSQL" as db

user -> jbake : Passe commande
jbake -> spring : POST /api/orders/create

== Orchestration Spring Boot ==
spring -> db : BEGIN TRANSACTION

par Vérifications Parallèles
  spring -> inventory : Vérifier stock
  inventory -> spring : Stock OK
else
  spring -> db : Vérifier profil client
  db -> spring : Client vérifié
end

spring -> stripe : Créer Payment Intent
stripe -> spring : Intent créé (ID: pi_xxx)

spring -> db : Créer Order (status: PENDING)
db -> spring : Order créé

spring -> stripe : Confirmer paiement
stripe -> spring : Paiement confirmé

spring -> db : Update Order (status: PAID)
spring -> inventory : Décrémenter stock
spring -> db : COMMIT TRANSACTION

par Notifications Asynchrones
  spring -> email : Email confirmation
else
  spring -> supadb : Insert notification
  note right: Notification temps réel\nvia Supabase Realtime
end

spring -> jbake : Order confirmé
jbake -> user : Affiche confirmation

note over spring
  **Responsabilités Spring Boot :**
  • Transaction ACID
  • Orchestration multi-services
  • Rollback automatique si erreur
  • Gestion des cas limites
end note
@enduml

Spring Boot가 제공하는 것: 여러 시스템을 포함하는 복잡한 프로세스의 신뢰할 수 있는 오케스트레이션, 트랜잭션 보장과 함께.

Flux 3 : 예약된 작업 및 동기화

@startuml
skinparam backgroundColor #FEFEFE

participant "스케줄러\n(Spring Boot)" as scheduler
participant "리포트 서비스" as report
participant "PostgreSQL" as db
participant "외부 API" as api
participant "이메일 서비스" as email
participant "Supabase 스토리지" as storage

== Job Quotidien : 2h00 ==
activate scheduler
scheduler -> report : Déclenche génération rapport

activate report
report -> db : Récupère données\ndes dernières 24h
db -> report : Dataset

report -> report : Calculs & Agrégations
report -> report : Génération PDF

report -> storage : Upload PDF
storage -> report : URL publique

report -> email : Envoie aux admins\navec lien PDF
deactivate report

== Job Hebdomadaire : Dimanche 3h00 ==
scheduler -> report : Synchronisation externe

activate report
report -> api : Fetch données externes
api -> report : Nouvelles données

report -> db : Mise à jour tables
report -> db : Nettoyage données obsolètes
deactivate report

== Job Mensuel : 1er du mois ==
scheduler -> report : Facturation

activate report
report -> db : Liste clients actifs
report -> report : Calcul montants
report -> api : Génération factures (Stripe)
report -> email : Envoi factures
deactivate report

deactivate scheduler

note right of scheduler
  **Impossible avec Supabase seul**
  Edge Functions non adaptées
  pour jobs longs et récurrents
end note
@enduml

Spring Boot가 제공하는 것: 상태 관리, 자동 재시도, 보장된 실행을 제공하는 신뢰할 수 있는 예약 작업

수평 확장

앱이 성장함에 따라 하이브리드 아키텍처는 자연스럽게 확장됩니다 :

Supabase:

  • 자동으로 수백만 건의 작업까지 확장

  • 읽기 성능을 위한 읽기 복제본

  • 시점 기반 복구 (보안)

스프링 부트 :

  • 로드 밸런서 뒤에 여러 인스턴스

  • Stateless 설계는 수평 확장을 용이하게 합니다.

  • 필요한 경우 쿠버네티스를 오케스트레이션에 사용

PostgreSQL :

  • 대용량 테이블 파티셔닝

  • 연결 풀링 (PgBouncer)

  • 샤딩은 정말로 필요합니다 (희귀함)

건축적 증언

스타트업 SaaS (50k 사용자)

_ 우리는 Supabase로 100% 시작했습니다. 5k 사용자 수준에서 우리는 Stripe 결제 청구와 월간 보고서를 위해 Spring Boot만 추가했습니다. 1년 후, 우리의 운영 중 80%가 여전히 Supabase를 통해 이루어집니다. Spring Boot는 비판적인 부분만 처리합니다. 이러한 분리를 통해 리팩터링 없이 확장이 가능했습니다. _

E-러닝 플랫폼 (10k 사용자)

_ Supabase의 OAuth2 인증 덕분에 3주 개발 시간을 절약할 수 있었습니다. 자동 생성된 API가 전체 강의 카탈로그를 처리합니다. Spring Boot는 PDF 인증서와 진행 이메일에만 사용됩니다. 간단하고 유지보수 가능하며 확장 가능한 아키텍처. </think> ___

B2B 마켓플레이스 (3k 사용자)

_ Spring Boot은 구매자와 판매자 간 거래를 관리합니다(중요). Supabase는 나머지 모든 것을 관리합니다: 프로필, 실시간 메시징, 문서. 그들이 동일한 PostgreSQL 데이터베이스를 공유한다는 사실 덕분에 복잡한 동기화를 피할 수 있습니다. 우리가 한 최고의 아키텍처 선택입니다. _
